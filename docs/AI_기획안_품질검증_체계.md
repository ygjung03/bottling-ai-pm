# AI 협업 기획안 자동 품질 검증 및 평가 체계

> **관리 정보**
>
> * **정본 관리:** `prompts/grader.yaml` ｜ **실행 스크립트:** `tests/test_fixed.py`
>
> * **초안 작성일:** 2026.08.30 ｜ **최종 확정:** 2026.09.21 ｜ **전면 갱신:** 2026.11.10

프롬프트 개선 과정에서 생성된 기획안의 품질 향상을 측정하기 위해 도입한 자동화 평가 시스템의 설계 철학, 검증 기준, 그리고 운영 내역을 정의한 문서이다.

## 1. 평가 점수 해석의 원칙

LLM 기반 에이전트 시스템을 평가할 때 발생할 수 있는 잠재적 왜곡을 통제하기 위해 두 가지 엄격한 원칙을 적용하였다.

* **절대적 품질이 아닌 '상대적 변화량' 중심 검증**

  * 기획안을 생성하는 모델과 채점하는 모델이 모두 Gemini(`gemini-3.5-flash-lite`)로 동일하여, 자체 평가에 따른 편향(Self-Bias)이 발생할 여지가 있음을 인지하였다.

  * 이에 따라 "4.59점짜리 우수 품질"과 같은 절대적 수치 대신, "고치기 전 4.26점에서 고친 뒤 4.59점으로 상승"과 같이 개선 전후의 상대적인 움직임만을 성과 지표로 활용하였다.

* **평가 체계 변경 시점에 따른 데이터 정합성 유지**

  * 평가 항목 개수가 변경된 시점(10/30 오전 5개 항목 → 오후 6개 항목) 전후의 데이터를 분리하여 해석하였다. 항목 증가에 따른 평균 점수 변동이 기획안 품질 저하로 오인되지 않도록, 같은 항목 수로 채점한 결과끼리만 비교하였다.

## 2. 핵심 평가 항목 및 점수 기준 (5점 척도)

기획안의 품질을 다각도로 진단하기 위해 6가지 항목을 정의하였으며, 평가의 변별력과 채점 효율성을 위해 **5점·3점·1점을 명시적으로 정의**하고 4점과 2점은 그 사이의 중간 단계로 설정하였다.

| 평가 항목 | 측정 목적 | 5점 기준 (우수) | 3점 기준 (보통/개선 필요) | 1점 기준 (미흡) |
| ----- | ----- | ----- | ----- | ----- |
| **실행 가능성** | 즉시 현장 적용 가능 여부 | 협력사가 제공할 산출물이 명확하고 바로 전달 가능 | 실행 자체는 가능하나 확인해야 할 조건이 남아 있음 | 납품 조건이 불명확하여 즉시 실행 불가 |
| **자원 정합성** | 가용 자원 내 실현 가능 여부 | 협력사 공급 품목과 자사 준비 사항이 명확하고 실제 존재함 | 협력사에 확인할 항목이 한두 가지 있거나, 매장에 상시 보유한 설비(맥주·맥주잔·셀프탭·조리기구)를 협업 준비물로 기재함 | 메뉴에 명시된 항목을 양측 모두 준비 불가 |
| **상권 근거** | 데이터 기반 타깃 설정 여부 | 손님층과 요일이 상권 분석 값에 근거하며 비율·객단가가 반영됨 | 근거를 제시하기는 하였으나 수치 없이 서술만 있음 | 근거가 부재하거나 입력값에 없는 수치를 허구로 기입 |
| **페어링 적절성** | 맥주와 메뉴 간 정합성 | 스타일·도수·맛 등의 근거가 명확하고 논리적임 | 어울리는 이유는 적었으나 막연하거나, 스타일·도수·맛 중 근거가 하나뿐임 | 구체적 근거 없이 「잘 어울린다」 수준이거나 미보유·논알콜 맥주 선택 |
| **홍보 실효성** | 대외 게시물 완성도 | 수정 없이 즉시 게시 가능하며 해시태그 등 실용성 높음 | 대외 게시가 가능하나 일부 표현이 어색하여 문구 수정이 필요함 | 문구 자체가 아닌 설명문 형태이거나 실무 활용 불가 |
| **배경 설득력** | 타깃 매장 특화 수준 | 해당 매장에 특화된 문장이며 모든 사실이 입력값에 근거함 | 틀린 서술은 없으나 동일 업종의 타 매장에도 대체로 성립하는 문장 | 가게 이름만 바꿔도 범용적으로 쓰이는 문장 |

* **배경 설득력 검증 (교체 테스트):** 문장에서 가게 이름만 다른 가게로 변경했을 때도 어색함 없이 성립한다면 해당 매장 특화성이 결핍된 것으로 판단한다. 협력사 사장님이 가장 먼저 읽는 문단이므로 별도 항목으로 분리하였다.

* **참신성 제외:** 주관적 판단 영역이며 프롬프트로 제어가 불가능하므로 평가 항목에서 배제하였다 (9/21 결정).

## 3. 통과 기준(Threshold) 폐지 및 집계 방식

* **임계값 폐지:** 초기 도입했던 「평균 3.5점 이상, 1점 항목 없음」의 합격선은 객관적 근거가 부족하여 전면 폐지하였다. 본 시스템의 목적은 합격/불합격을 가리는 것이 아니라 버전 간 상대적 비교에 있기 때문이다.

* **결과 집계 원칙:** 항목별 점수와 전체 평균을 산출하되, **단 한 항목이라도 누락된 건은 평균 산출에서 제외**하여 항목 수가 다른 데이터 간의 비교 오류를 원천 차단하였다.

## 4. 하이브리드 검증: 코드와 LLM의 역할 분담

판정 기준이 명확하고 기계적으로 처리 가능한 영역은 **코드가 수행**하고, 맥락과 텍스트 해석이 필요한 영역은 **LLM이 담당**하도록 역할을 이원화하였다.

* **코드 기반 검증:** 추천 근거에 관측 건수(예: 「72건 관측」)나 특정 시간대(예: 「17-21시」)가 섞여 들어간 경우, 코드가 이를 감지하여 상권 근거 점수를 **1점 감점**한다. 동일한 문장을 두고 LLM 채점이 1점과 5점을 번갈아 내놓았기 때문에, 패턴으로 판별이 가능한 영역을 코드로 이관한 것이다.
  *(※ 관측 건수는 데이터 신뢰도를 가늠하는 내부 지표일 뿐, 협력사 사장님이 읽을 제안서에 노출할 내용이 아니라는 비즈니스 로직에 기인함)*

* **LLM 기반 검증:** 텍스트의 맥락 파악, 페어링 적절성, 배경 설득력 등 정성적 판단 영역은 LLM 채점자에 위임하였다.

## 5. 입력 동기화 (Input Synchronization)

프롬프트 체인 고도화 과정에서 채점 오류를 방지하기 위한 핵심 원칙을 수립하였다.

* **문제 상황:** 기획안 생성 단계에는 가게 특성(예: 「자양역 1번 출구 도보 5분」)을 주입했으나, 채점 프롬프트에는 해당 문맥을 누락하여 정상적인 기획안이 「사실을 지어냈다(Hallucination)」로 오인되어 1점 처리를 받는 오류가 발생하였다. (이로 인해 「블로그 후기 수집 기능이 오히려 품질을 떨어뜨린다」는 잘못된 결론이 도출될 뻔함)

* **해결 원칙:** 생성 체인에 넣는 입력을 늘릴 때는 평가 체계의 정확한 검증을 위해 채점 프롬프트(prompts/grader.yaml)의 입력에도 동일한 값을 반영해야한다. 이 원칙에 따라 가게 특성과 근처 행사 정보가 채점 입력에 추가되었다.

## 6. 테스트 케이스 설계 (9개 테스트 셋)

`tests/fixtures/testset.json`에 정의된 9개의 테스트 케이스는 협력사 업종 4종 × 회차(1차/2차)를 두 축으로 설계되었다.

| 케이스 ID | 협력사 업종 | 회차 | 대상일 | 검증 중점 사항 |
| ----- | ----- | ----- | ----- | ----- |
| C1 \~ C2 | 제과·디저트 | 1차 / 2차 | 10/9 | 정보 부재 시 환각(Hallucination) 방지 및 납품 제약 조건 준수 여부 |
| C3 \~ C4 | 카페 | 1차 / 2차 | 10/9 | 음료 납품 불가, 냉장 보관, 하루 30개 등 제약 조건 반영 여부 |
| C5 \~ C6 | 분식·스낵 | 1차 / 2차 | 10/9 | 조리 시간 제약, 포장 용기 주체, 상호 표기 요청 반영 여부 |
| C7 \~ C8 | 피자·튀김·그릴 | 1차 / 2차 | 10/9 | 화덕 조리 시간, 조각 포장 주체, 일일 생산량 한계 준수 여부 |
| C9 | 제과·디저트 | 1차 | **10/2** | 판매 기간 외의 행사를 홍보에 부당하게 끌어다 쓰는지 검증 (9/26 추가) |

* **회차별 검증 목적:** 1차(협력사 소통 전)는 빈칸을 임의로 지어내지 않는지 검증하고, 2차(협력사 입력 폼 접수 후)는 전달받은 제약 조건을 정확히 이행하는지 검증한다.

* **데이터 현실성:** 협력사명·메뉴·가격 등 테스트셋의 값은 전부 가상이나, **매장 특성 정보만은 동일 업종 실제 매장의 블로그 후기에서 수집한 값을 사용**하였다. 특성까지 가공하면 「해당 매장만의 사실」이라는 성질이 사라져 배경 설득력 평가가 성립하지 않기 때문이다. 또한 상권 통계에 피자 전용 분류가 부재하여 `치킨전문점` 통계로 대응하는 등 공공데이터의 제약을 감안하여 구성하였다.

### C9 테스트 케이스 추가 배경 (예외 상황 검증 및 테스트 엄밀성 확보)

* **시스템 아키텍처 및 검증 구조**

  인근 행사 목록은 코드가 실행일 임박순으로 정렬해 전달하고, AI 마케터가 문맥을 읽어 유효한 행사를 선별한다. 이후 결과물에 판매 기간이 지난 행사가 포함되었는지 코드가 2차로 교차 검증(날짜 기준)하여 위반 시 재호출(Retry)하는 안전장치를 갖추고 있다. 다만, 행사명이 「드론쇼」처럼 축약되어 텍스트 직접 대조가 어렵기 때문에 날짜 표기를 기준으로 판정하며, 날짜 없이 행사가 언급될 경우에는 코드로 포착하기 어려운 사각지대가 존재한다.

* **기존 테스트의 구조적 한계**

  기존 8개 테스트 케이스는 협업 실행일이 모두 10/9로 고정되어 있었고, 당일 마침 인근에서 드론쇼가 개최되어 목록 최상단의 행사를 그대로 가져와도 정답이 되는 구조였다. 이로 인해 AI가 만료된 행사를 실제로 필터링하는지 엄밀하게 검증하기에 한계가 있었다.

* **C9 케이스를 통한 검증 고도화**

  이를 보완하기 위해 판매 기간을 10/2부터 3일간으로 한정하는 C9 테스트 케이스를 새롭게 도입하였다. 이 조건에서는 목록 상단의 행사들이 모두 판매 종료 이후에 해당하므로, AI가 상위 행사를 무분별하게 끌어오지 않고 기간 내 행사를 올바르게 연계하거나 「연계 없음」으로 처리하는지 철저히 검증할 수 있다. 이를 통해 자동 코드 검사가 닿지 않는 영역까지 방어하는 테스트의 완성도를 높였다.

## 7. 자동화 파이프라인 및 운영 방식

CLI 기반의 스크립트를 통해 평가 프로세스를 자동화하였다.

```
python -m tests.test_fixed --snapshot     # 입력 데이터를 스냅샷으로 고정 (데이터 시계열 변동 통제)
python -m tests.test_fixed --run          # 9건의 테스트 케이스 기반 기획안 생성
python -m tests.test_fixed --grade        # 생성 결과 채점 수행
python -m tests.test_fixed --report       # 소요 시간, 비용, 재호출·되감기 횟수 집계
```

* **스냅샷 고정:** 상권 컨텍스트 데이터는 최근 4주치를 동적으로 읽어오므로, 실행 시점에 따라 데이터가 달라지는 변수를 통제하기 위해 최초 실행 시 `snapshot.json`에 데이터를 박아두고 이후 테스트는 해당 스냅샷을 참조하도록 설계하였다.

* **생성과 채점의 조건:** 버전 간 차이를 정확히 비교하기 위해 채점 시 temperature=0으로 고정하여 일관성을 유도했다. 그럼에도 LLM 채점은 같은 기획안에 다른 점수를 내는 경우가 있었다. 한편, 기획안 생성은 고정 테스트에서도 운영 체인을 그대로 사용하여 매 실행마다 결과가 달라진다. 이 두 가지 변동 요소를 고려하여, 버전 간 비교는 평균값 비교에 그치지 않고 케이스별 증감 방향까지 함께 추적하여 분석의 신뢰성을 높였다(8장).

* **채점 단위:** 1개 케이스당 기획안이 3안(단품·세트·포장) 생성되어 전수 채점 시 27안이 되므로, 버전 간 동일 지점을 비교하기 위해 **세트 안 1건만을 선별하여 채점**한다.

* **버전 식별:** 결과 파일명의 버전값은 `prompts` 폴더 내용의 해시이다. 커밋 이전에도 값이 변경되므로 수정과 실행을 반복하는 튜닝 과정에서도 버전별 결과가 혼재되지 않는다 (`tests/results_{버전}.json`, `tests/grades_{버전}.json`).

* **운영 비용:** 채점은 무료 키로 9회 호출하며 1\~2분이 소요된다. 전달되는 데이터가 자체 생성물과 공공 상권 데이터뿐이므로 유료 키를 사용할 사안이 아니다.

## 8. 최신 검증 성과 (10/30 실험 결과)

「블로그 후기 기반 매장 특성 수집 기능」 도입 전후의 효과를 측정하기 위해 채점 기준을 고정한 상태에서 9건의 기획안을 비교 채점하였다.

**해석 방법:** 실제 채점 점수는 5점·3점·1점에 몰려 있고 케이스는 9건뿐이라, 1건만 5점에서 1점으로 바뀌어도 평균이 0.44점 움직인다. 평균만 보면 이런 한두 건의 변화가 항목 전체의 변화처럼 보이므로, 이번 비교에서는 평균과 함께 어느 케이스가 어느 방향으로 바뀌었는지를 확인하였다.

| 평가 항목 | 특성 반영 전 | 특성 반영 후 | 증감 (Diff) |
| ----- | ----- | ----- | ----- |
| 실행 가능성 | 5.00 | 5.00 | — |
| 자원 정합성 | 4.78 | 4.78 | — |
| 상권 근거 | 4.56 | 4.11 | −0.45 |
| 페어링 적절성 | 5.00 | 4.78 | −0.22 |
| 홍보 실효성 | 4.33 | 3.89 | −0.44 |
| **배경 설득력** | **1.89** | **5.00** | **+3.11** |
| **전체 평균** | **4.26** | **4.59** | **+0.33** |

같은 결과를 점수별 건수와 바뀐 케이스로 나누면 다음과 같다. 9건 모두 5점·3점·1점만 나오고 4점과 2점은 나오지 않았다.

| 평가 항목 | 반영 전 (5점/3점/1점) | 반영 후 (5점/3점/1점) | 점수가 바뀐 케이스 |
| ----- | ----- | ----- | ----- |
| 실행 가능성 | 9 / 0 / 0 | 9 / 0 / 0 | 없음 |
| 자원 정합성 | 8 / 1 / 0 | 8 / 1 / 0 | C7 ↑, C8 ↓ |
| 상권 근거 | 7 / 2 / 0 | 6 / 2 / 1 | C6 ↓, C8 ↓, C9 ↑ |
| 페어링 적절성 | 9 / 0 / 0 | 8 / 1 / 0 | C7 ↓ |
| 홍보 실효성 | 7 / 1 / 1 | 6 / 1 / 2 | C2 ↓, C5 ↓, C8 ↑ |
| **배경 설득력** | **1 / 2 / 6** | **9 / 0 / 0** | C5(기존 5점)를 제외한 **8건 모두 ↑** |

* **배경 설득력 (개선):** 총 9건 중 8건의 점수가 상승하고 하락한 건은 없어 명확한 개선으로 판단한다. 특히 최고점(5점) 건수가 1건에서 9건으로 대폭 늘어난 반면, 최저점(1점) 건수는 6건에서 0건으로 완전히 해소되었다. 다수의 케이스가 동일한 방향으로 일관되게 움직였다는 점에서, 이는 단순한 실행 변동성(흔들림)으로 인한 결과가 아니다.

* **기타 항목 (판단 유보):** 나머지 항목은 유의미한 개선이나 악화로 단정하기 어렵다. 평균 변화 폭이 −0.22~−0.45점으로 미미하고 1~3건의 변동에 기인하며, 동일 항목 내에서도 상승과 하락이 혼재되어 나타났다. 예를 들어 '자원 정합성'의 경우 전체 평균은 동일하지만 C7은 상승하고 C8은 하락하는 등 케이스별 증감이 엇갈렸다.

### [참고] 초기 수동 채점(9/21, 8건)이 도출한 핵심 인사이트

수동 채점 결과 전체 평균 4.2점(3.2\~4.8 분포)을 기록하였으며, 코드로 선별할 수 없는 4가지 오류 유형을 발견하여 이후 프롬프트 고도화의 핵심 백로그로 활용하였다.

1. **명칭 불일치:** 세트 메뉴명 내 맥주와 페어링 맥주 간의 매칭 오류

2. **조리 설비 귀속 오류:** 바틀링이 준비할 자원에 협력사의 화덕 설비가 혼입되는 현상 

3. **제약 반영 누락:** 협력사가 제출한 보관 방법 및 상호 표기 요청이 누락되는 일관성 저하 문제

4. **근거 건수 누락:** 상권 근거에 비율은 제시되었으나 몇 건의 관측에서 산출된 값인지가 누락되던 문제. **단, 이 항목은 이후 판단이 반대로 전환되었다** — 관측 건수는 데이터 신뢰도를 가늠하는 내부 지표일 뿐 제안서에 노출할 내용이 아니라고 판단하여, 현재는 기재하지 않는 것이 규칙이며 기재된 경우 코드가 감점한다 (4장 참고).
