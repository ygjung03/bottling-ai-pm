# 2. 9/22까지 반드시 완료할 작업

9/22 기획안에 필요한 핵심 작업은 다음 세 가지이다.

```text
T22  기획안 생성 화면       ← 초안 완료
 ↓
T44  협업 제안서 출력
 ↓
T46  최종 기획안 도출

T21  협력사 입력 폼
      └─ 위 문서에 들어갈 실제 협력사 정보를 입력
```

따라서 **9/22까지 반드시 완료해야 하는 작업은 T44·T21·T46, 그리고 T27(배포)**이다.

T22는 이미 초안이 나왔으므로 이후에는 T44 → T46으로 연결되는 흐름을 완성하면 된다.
T21은 기존 가상 데이터를 실제 협력사 정보로 교체하는 작업이다.
T27은 배포가 완료되지 않으면 대표님이 화면을 사용할 수 없으므로 함께 포함한다.

나머지 작업은 일정이 부족할 경우 일부 제외할 수 있지만, **T44·T21·T27·T46은 제외하지 않는다.**

## 4-2. T21에서 함께 변경할 내용: 메뉴와 가격

8/31 2차 방문에서 대표님이 *"협업사에서 완성한 걸 가지고 와서 파는 게 제일 적합하다"* 고 하셨고, 이에 따라 **협업 형태를 완제품 매입 후 판매로 한정**하였다 (기획서 6-1).

**완제품은 협력사가 이미 완성해서 판매하고 있는 제품을 뜻한다.**

그런데 (2) 셰프의 입력은 아직 그 결정을 반영하지 못한 상태이다. 현재 협력사 정보로 **대표 메뉴 1개와 보유 식재료 목록**을 받고 있으며, 프롬프트는 *"협력사가 보유한 식재료로 만들 수 있는 것만 제안한다"* 고 지시하고 있다. 즉 **식재료를 기준으로 새 메뉴를 만드는 구조**이다.

가격 정보도 부족하다. 현재 확보한 값은 완제품 납품 희망 단가 하나뿐이며, **협력사가 실제로 얼마에 판매하는지는 알 수 없다.**

또한 준비 기간을 3일로 제한하고 있어(C007), 협력사에 신메뉴 개발을 요구하는 것은 애초에 실행 가능한 요구가 아니다.

따라서 입력 정보를 다음과 같이 변경한다.

| 구분      | 현재                  | 변경 후                      |
| ------- | ------------------- | ------------------------- |
| 폼 입력    | 대표 메뉴 1개 + 보유 식재료   | **판매 중인 메뉴와 가격 3～5개**     |
| (2)의 역할 | 식재료를 바탕으로 신메뉴 창작    | **기존 메뉴를 기준으로 구성·가격대 변형** |
| 매입가 근거  | 희망 단가 1개            | **실제 판매가 확보**             |

이렇게 변경하면 **U18(매입가 근거 부족)** 문제도 상당 부분 해소된다.

예를 들어 협력사가 제품을 2,000원에 판매하고 있다면, 이를 1,200원에 매입하는 제안은 **실제 판매가를 기준으로 한 가격 제안**이 된다.

식재료 정보는 폐기하지 않는다.
기존 메뉴를 변형할 때 **어떤 재료를 추가하거나 변경할 수 있는지 판단하는 자료**로 계속 활용한다.

## 5-2. 추천 엔진(T15·T16) 설계 변경 경위

T15·T16에 착수하기 전에 현재 점수 구조가 왜 단순화되어 있는지 먼저 확인할 필요가 있다.

기존 추천 점수는 원래 다음 네 항목으로 구성되어 있었다.

```text
Score = 0.30·S_distance
      + 0.30·S_complement
      + 0.25·S_timing
      + 0.15·S_trend
```

| 항목             |  가중치 | 의미                   |
| -------------- | ---: | -------------------- |
| `S_distance`   | 0.30 | 거리가 가까운가             |
| `S_complement` | 0.30 | 업종이 겹치지 않는가          |
| `S_timing`     | 0.25 | 저녁 시간대에 판매가 활발한 업종인가 |
| `S_trend`      | 0.15 | 해당 상권이 성장하고 있는가      |

현재는 다음 두 항목만 사용한다.

```text
Score = 0.50·S_distance
      + 0.50·S_complement
```

두 항목을 제외한 이유는 서로 다르다.

---

### `S_timing`은 전제가 바뀌어 제외

원래는

> “바틀링이 15시에 영업을 시작하므로 저녁형 업종과 협업하는 것이 적합하다.”

는 전제를 두었다.

그러나 8/31에 협업 형태를 **완제품 매입으로 확정**하면서 이 전제가 더 이상 성립하지 않는다.

협력사는 낮에 제품을 제조해서 납품하면 되기 때문에, 바틀링과 영업시간이 겹칠 필요가 없다.

오히려 저녁 매출이 높은 가게일수록 자체 영업으로 바빠 **납품 여력이 부족할 가능성**도 있다.

반대로

> “저녁에 한가한 가게가 납품하기 좋다.”

고 적용하는 방안도 검토했지만 채택하지 않았다.

매출이 적은 이유가 **납품 여력이 있어서인지, 단순히 매장 규모나 수요가 작아서인지 구분할 수 없기 때문**이다.

따라서 `S_timing`은 추천 점수에서는 제외한다.

다만 시간대 데이터 자체를 버리는 것은 아니다.

컨텍스트 빌더에서 이미 두 업종의 시간대별 매출 비중을 제공하고 있으므로(기획서 6-3 ⑩), **추천 단계에서는 누구와 협업할지를 판단하고, 이후 (2) 셰프 단계에서 어떻게 협업할지를 판단하는 구조**로 사용한다.

---

### `S_trend`는 변별력이 없어 제외

이 항목은 원래 **상권 단위 지표**로 설계하였다. 그러나 **바틀링이 서울시 주요상권 82곳에 포함되지 않는다.** 반경 3km로 검색해도 뚝섬 관련 상권이 없어, 상권코드를 전제한 설계를 모두 행정동 단위로 전환하였다 (명세서 2-4).

문제는 행정동 단위로 바꾸면 **후보 사이에 차이가 거의 없어진다**는 점이다.

추천 후보는 모두 반경 1km 안에 있어 대부분 같은 행정동(자양3동)에 속하고, 일부만 인접 행정동(성수동 등)에 걸친다. 같은 행정동이면 상권변화지표 등급도 같으므로, **대부분의 후보가 동일한 점수를 받아 순위를 가르지 못한다.**

데이터를 아직 적재하지 못한 것도 사실이지만, 그것이 본질적인 이유는 아니다. 실제로 원래 가중치도 0.15로 네 항목 중 가장 낮았다.

따라서 **CSV를 확보했더라도 적재하면 바로 복구되는 항목은 아니다.** 적재한 뒤 후보별 등급이 실제로 갈리는지 먼저 확인해야 하며, 대부분 같은 값이라면 추가하지 않는다.

## 5-3. 추천 엔진의 현재 핵심 문제: 변별력

현재 두 항목만 사용하면 다음 문제가 발생할 수 있다.

반경 1km 안에 제과점이 여러 곳 있을 경우, 업종이 모두 동일하게 평가되어 `S_complement`가 모두 1.0이 될 수 있다.

그 경우 결과적으로

> **“협업 추천”이라기보다 “가까운 순으로 정렬”하는 결과**

가 될 가능성이 있다.

따라서 T15 구현 후 **A가 실제 데이터 결과를 직접 확인하고 추천 기준의 적절성을 판단한다.**

상위 후보와 점수 분포를 바탕으로 현재 기준을 유지할지, 추가 항목을 적용할지 결정한다.
U5(가중치)와 U6(상보성 점수) 역시 A의 판단에 따라 확정한다.

---

## 5-4. 추가할 수 있는 항목

두 항목만으로 변별력이 부족할 경우 지표를 추가한다.

**추가 여부와 어떤 지표를 쓸지는 A가 판단한다.**

먼저 두 항목으로 T15를 실행해 실제 순위를 확인한 뒤 결정한다. 결과를 보기 전에는 무엇이 부족한지 알 수 없고, 근거 없이 지표를 추가하면 순위만 바뀔 뿐 무엇이 순위를 바꾸었는지 확인할 수 없다.

지표를 추가할 때는 **후보마다 값이 실제로 달라지는지 먼저 확인한다.** 대부분의 후보가 같은 값을 받는 지표는 가중치를 조정해도 순위를 가르지 못한다. `S_trend`가 그 경우에 해당한다.

## 5-5. 추천 엔진 구현 시 주의사항

### 업종을 매핑할 수 없는 후보는 제외한다

임의의 값을 넣어 순위에 포함시키지 않는다.

특히 중립값 0.5는 실제 상보성과 관계없는 값이고, 0은 사실상 제외하면서 목록에는 남는 문제가 있다.

따라서 **분류할 수 없는 업종은 점수 계산 전에 후보에서 제외한다.**

또한 제외된 후보 수를 화면에 표시한다.

## 5-6. T24 파트너 추천 화면

T24는 명세서 4-3에 정의된 세 가지 경로로 구성한다.

```text
A. 추천받기
   → 필터 → 순위 → 선택

B. 직접 지정
   → 상호 검색 또는 직접 입력
   → 점수는 산출하지 않음

C. 메뉴로 찾기
   → U17 성공 시 메뉴·가격 기반으로 탐색
   → U17 실패 시 지도 링크만 제공
```

A 경로는 기존 대시보드에서 구현한 **협업 후보 지도와 pydeck 구성을 그대로 재사용**한다.

| **본문 페이지 수집**    | **가능** — `PostView.naver`에서 5,780자 확인 |
| 검색을 통한 후기 표본 수집  | 미확인 — API 키 필요                        |
| 음식점 후기의 가격 표기 비율 | 미확인 — 표본 수집 필요                        |

이는 9/3에 차단된 플레이스 메뉴 API와는 **별도의 경로**이다.

검증 과정은 `tests/probe_naver_blog.py`에 기록해 두었다.

### API 계정 문제가 남아 있다

키 발급 경로가 변경되었다.

```text
2026-07-31  개발자센터 신규 신청 차단
2027-06-30  개발자센터 지원 종료
이후        NAVER API HUB(NCP)에서만 발급
            → NCP 계정은 결제수단 등록 필요
```

무료 쿼터는 일 25,000건이고 예상 사용량은 **기획안 1건당 약 10건**이므로 실제 과금 가능성은 매우 낮다.

다만 기술적인 비용과 별개로 **누구 명의로 NCP 계정을 개설할지**를 먼저 정해야 한다.

또한 명세서 8-2에서는 사업 종료 후 6개월간 서비스를 방치하는 상황까지 가정하고 있기 때문에, 이후 API 이관 과정까지 고려하면 인수인계 항목이 하나 더 늘어난다.

계정 관리가 어려울 경우를 대비해 대체 경로도 마련해 두었다.

> **블로그 수집 실패 → 지도 링크를 제공하고 대표님이 직접 확인**

# 6. 지금 확인해야 할 사항

## ① U16 — 메뉴 이미지 생성 품질

T43의 선행 조건이다.

아직 실제 이미지 생성 모델을 호출해 품질을 확인하지 않았기 때문에, **9/10에 먼저 검증한다.**

* 결과가 양호하면 → 9/11 T43 착수
* 결과가 미달이면 → T43 제외

이미지가 없어도 협업 제안서 자체는 발송할 수 있다.

**9/13까지 품질을 확인하지 못하면 T43은 제외한다.**

## ② 리드타임 기준선 확보

기획서 7-1의 핵심 지표다.

9/12 협업에서 다음 정보를 확보해야 한다.

* 착수일
* 실제 투입 시간
* 참여 인원

협업이 끝난 뒤에는 해당 정보를 다시 확보하기 어렵기 때문에 **실행 시점에 바로 기록해야 한다.**

또한 자료 확보 전에 DB 스키마를 수정해야 한다.

현재 `plans.context_snapshot`과 `plans.final_output`이 `NOT NULL`이라 **AI PM을 사용하지 않은 협업 건은 INSERT 단계에서 차단되는 문제가 있다.**

## ③ 체인 응답 시간이 30초에 근접

현재 체인 처리 시간이 약 **18～30초**로 변동한다.

명세서 목표는 **19～24초**이다.

최근 (4) 출력이 길어지면서 시간이 늘어난 것으로 보이며, M2의 타겟 3분할까지 추가하면 기준을 확실히 초과할 가능성이 있다.

따라서 **T18 프롬프트 튜닝에서 (4)의 출력 길이와 응답 시간을 함께 조정한다.**

---

## ④ T14 고정 테스트셋 착수 여부

명세서에는

> “프롬프트를 수정하기 전에 반드시 만든다.”

고 되어 있다.

하지만 이미 T42에서 4종 프롬프트를 전면 수정한 상태다.

지금 T14를 만들면 T18 전후 비교에는 활용할 수 있지만, 작성에 반나절이 필요하다.

따라서 **9/22 필수 작업을 우선 확보한 뒤 여유가 있을 때 진행하는 방향**으로 판단한다.

# 7. 일정이 부족할 경우 제외 순서

여유가 부족해질 경우 아래 순서대로 제외한다.

**단, 9/22와 10/9 일정은 유지한다.**

```text
1. U17 블로그 수집
   → 계정이 개설되지 않으면 자동 제외

2. T14 고정 테스트셋
   → T18 전후 비교를 포기하는 대신 마감 일정 확보

3. T24 파트너 추천 화면
   → 직접 지정 경로로 대체 가능

4. T23 채택·폐기
   → 기록이 늦어질 뿐 기획안 자체는 생성 가능

5. T43 메뉴 이미지
   → U16 품질이 미달이면 제외

6. T17 자동 검증
   → 경고 기능은 빠지지만 기획안 생성 자체는 가능
```

### 절대 제외하지 않는 작업

```text
T44  협업 제안서 출력
T21  협력사 입력 폼
T27  배포
T46  10/9 협업 기획안 도출
```

즉, **B는 “협업 정보 입력 → 제안서 출력 → 기획안 도출 → 배포”를 완성하고, A는 추천·데이터 계열을 병렬로 진행한다.**
