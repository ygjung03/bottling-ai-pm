# T22 기획안 생성 화면 — 개선 요청

**2026.9.8** ｜ 대상: `app/pages/2_기획안_생성.py`

동작은 한다. **읽기가 어렵다.** 아래 다섯 가지를 고친다.

---

## ① 입력란이 가로로 너무 길다

협력사 선택과 날짜 입력이 화면 폭을 다 쓴다. 고를 항목이 몇 개 안 되는데 폭만 넓어 허전하다.

```
협력사   [ ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ ▼ ]   [기획안 생성]
실행일   [ 2026/09/16 ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ ]
```

**폭을 줄인다.** `st.columns`로 좌측 3～4 비율만 쓰고 나머지는 비워둔다.

---

## ② 생성 버튼 위치

지금 우측 상단에 떠 있어 입력 흐름과 끊긴다. **입력을 다 채운 뒤 누르는 것이므로 마지막에 와야 한다.**

```
협력사   [ ▼ ]
실행일   ○ 날짜 지정  ○ 희망 기간
         [ 2026/09/16 ]

         [ 기획안 생성 ]
─────────────────────────────  ← 구분선은 버튼 아래
```

---

## ③ 상자 안에 내용이 잘려도 티가 나지 않는다

높이가 고정된 상자에 내용이 넘치면 **잘린 채로 보인다.** 스크롤이 되는지조차 알 수 없어 내용이 더 있다는 것을 모른다.

**두 가지 중 하나로 처리한다.**

| | 방법 |
|---|---|
| **A** | 높이 고정을 풀고 내용만큼 늘린다 |
| **B** | 고정하되 스크롤바를 항상 보이게 한다 |

**A를 권한다.** 기획안은 한 번에 훑는 문서라 세로로 길어도 괜찮다. 상자마다 스크롤하게 만들면 오히려 읽기 어렵다.

길이가 크게 차이 나는 항목(예상 리스크, 추천 근거)만 `st.expander`로 접는다.

## ④ 정보 배치가 어색하다 — 가장 크게 고칠 곳

### 지금

```
┌ 협력사가 준비 ────────┐   ┌ 바틀링이 준비 ────────┐
│ · 제과점 완제품 디저트  │   │ · 바틀링 라거          │
│                       │   │ · 포장재               │
│ 판매가                 │   │                       │
│ 14,000원              │   │ 맥주 500ml             │
│ 원가 1,200원 · 협의    │   │ 6,000원                │
│ 보관 냉장 2일          │   │ 라거 4.5도, 가벼움      │
└───────────────────────┘   └───────────────────────┘
```

**문제가 셋이다.**

**a. 판매가가 「협력사가 준비」 안에 있다.** 14,000원은 손님에게 받는 돈이지 협력사가 받는 돈이 아니다. 협력사가 받는 것은 매입가 1,200원이다. **돈 정보가 역할 박스에 섞여 누가 얼마를 받는지 흐려진다.**

**b. 손님이 내는 총액이 화면에 없다.** 디저트 14,000원과 맥주 6,000원이 별도인데 **합계 20,000원이 어디에도 없다.** 「세트」라는 이름과 어긋난다.

**c. 맥주 정보가 「바틀링이 준비」에 섞여 있다.** 페어링은 기획의 핵심 판단인데 준비물 목록처럼 보인다.

### 이렇게 바꾼다

**돈을 따로 떼어내고, 역할 박스에는 품목과 조건만 남긴다.**

```
제과점 완제품 디저트 맥주 세트                    [메뉴 이미지]
제과점 완제품 디저트 1개 + 바틀링 라거 500ml

┌ 선정 사유 ──────────────────────────────────────────────┐
│ 페어링 맥주 단가와 세트 판매가를 고려할 때 바틀링 매출     │
│ 기여도가 가장 높고 제과점 17-21시 객단가와 정합성이 높음   │
└─────────────────────────────────────────────────────────┘

── 가격 ──────────────────────────────────────────────────

   손님이 내는 값        협력사에 주는 값        바틀링 마진
   20,000원              1,200원                18,800원
   디저트 14,000          협의 대상               94%
   + 맥주 6,000

── 구성과 역할 ────────────────────────────────────────────

┌ 협력사가 준비 ────────┐   ┌ 바틀링이 준비 ────────┐
│ · 제과점 완제품 디저트  │   │ · 바틀링 라거 500ml    │
│                       │   │ · 포장재               │
│ 보관   냉장 2일        │   │                       │
│ 납품   1회 수량 협의    │   │ 페어링 이유            │
│                       │   │ 라거 4.5도, 가벼운     │
│                       │   │ 탄산감이 디저트와 균형  │
└───────────────────────┘   └───────────────────────┘
```

**핵심은 「가격」 블록을 따로 두는 것이다.** `st.metric` 세 개를 한 줄에 놓으면 된다.

| 지표 | 값 | 아래 설명 |
|---|---|---|
| 손님이 내는 값 | 디저트 판매가 + 맥주 판매가 | 내역 |
| 협력사에 주는 값 | 매입가 | 협의 대상 여부 |
| 바틀링 마진 | 총액 − 매입가 | 마진율 |

> **마진을 자동으로 계산해 보여주는 것이 중요하다.** 대표님이 실행 여부를 판단하는 가장 직접적인 수치다. 지금은 세 숫자가 흩어져 있어 직접 계산해야 한다.

> **맥주값을 합산하는 근거** — 세트로 파는 구성이므로 손님은 두 값을 함께 낸다. 다만 맥주는 바틀링 자체 상품이라 매입가가 없다. 그래서 마진 계산에서 맥주값은 그대로 남는다.

## ⑤ 남은 것

**a. 「메뉴 이미지 — T43에서 생성」 자리표시자**

미구현 상태가 화면에 그대로 보인다. **이미지가 없으면 그 영역 자체를 감춘다.** 대표님이 보는 화면에 개발 티켓 번호가 나오면 안 된다.

**b. 「협업 제안서 — T44에서 구현 예정」도 마찬가지**

미구현이면 섹션을 감춘다.

**c. 홍보 일정 표에 세로 스크롤바가 보인다**

행이 두 개뿐인데 스크롤이 생겼다. `st.dataframe` 대신 `st.table`을 쓰거나 높이를 자동으로 맞춘다.

### 참고할 것

**a. 가격을 내역 → 합계 순으로 쌓는다**

```
국물 떡볶이 (봄봄분식)          ₩6,000
아이스 아메리카노 (커피한잔)     ₩3,500
닭강정 미니 (황금닭강정)         ₩5,000
개별 합산가                    ₩14,500
─────────────────────────────────────
세트 판매가                    ₩12,900
                     ₩1,600 절약 (11% 할인)
```

**우리 화면에도 이 형태가 맞다.** 디저트 14,000 + 맥주 6,000 = 20,000원을 이렇게 쌓으면 총액이 자연스럽게 드러난다.

**b. 문서 머리에 식별 정보를 둔다**

```
OFFICIAL PROPOSAL DOCUMENT        문서번호: 2026-MAPO-001
소상공인 협업 세트메뉴 기획안        작성일: 2026.09.08
                                  버전: v1.0
```

협력사에 보내는 문서이므로 언제 만든 어느 버전인지가 있어야 한다. **T44에서 쓴다.**

**c. 합의 사항과 서명란**

제안서 끝에 조항과 서명란을 둔다. 협력사가 검토하고 확정하는 문서라는 성격이 드러난다. **T44에서 쓴다.**

**d. 섹션에 번호를 붙인다**

`1 사업 개요` / `2 참여 상점 및 기여 메뉴` / `3 합의 사항`. 문서로 읽힐 때 위치를 잡기 쉽다.

### 따르지 말 것

> **협업 구조가 다르다.** 시안은 **3개 상점이 세트를 만들어 수익을 나누는** 구조다. 우리는 **바틀링이 협력사 완제품을 매입해 파는** 구조다 (기획서 6-1).
>
> - 「수익 배분 비율」이 아니라 **매입가 하나**다. 협력사는 판매량과 무관하게 매입가를 받는다
> - 참여 주체가 3곳이 아니라 **바틀링과 협력사 둘**이다
> - 「세트 쿠폰을 3개 상점 어디서든 판매」 같은 구조가 없다
>
> **내용은 명세서 1-4의 출력 스키마를 따른다.** 시안에서 가져올 것은 배치와 순서다.

> **Streamlit으로 만들 수 있는 범위에서 한다.** 시안은 React 앱이라 카드 그림자·상단 탭·색상 배지 같은 것이 자유롭다. Streamlit은 `st.container(border=True)`·`st.columns`·`st.metric`·`st.tabs` 조합이 전부다.
>
> **CSS 우회로 시안을 그대로 재현하지 않는다** (명세서 4-0-2). 유지가 어렵고 실증 중에 깨지면 대응할 시간이 없다.

## 참고 — 이 화면의 목적

명세서 4-2에 적힌 대로 **대표님이 이 문서만 보고 실행 여부를 정할 수 있어야 한다.**

그래서 순서가 이렇게 되는 것이 자연스럽다.

```
① 무엇을 파는가      메뉴명 · 구성 · 이미지
② 왜 이 안인가       선정 사유
③ 얼마가 남는가      가격 · 마진        ← 판단의 핵심
④ 누가 무엇을 하는가  역할 · 조건
⑤ 어떻게 알리는가    홍보 일정 · 문구
⑥ 무엇이 걸리는가    준비물 · 리스크
```

지금 화면은 ③이 ④ 안에 섞여 있어 판단이 어렵다.
