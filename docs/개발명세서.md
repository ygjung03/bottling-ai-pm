## 0. 선행 설계 결정

시스템 설계 과정에서 답이 필요했던 7가지 쟁점과, 그에 대한 팀 내부 결론.

> **배경** — 8/19 멘토링에서 아래 질문을 준비했으나 실질적인 답변을 얻지 못했다. 착수를 미룰 수 없어 팀 판단으로 결정했다.
> **따라서 D1·D2·D4는 검증되지 않은 판단이며, 3주차(T26·T18)에 실측으로 재검토한다.**

### D1. 사례가 5～10건뿐일 때 어떻게 반영할 것인가

**질문** — 협업 사례가 사업 종료 시점에도 5～10건 수준으로 예상된다. 파인튜닝은 불가능한 규모인데, 프롬프트에 예시로 넣는 few-shot 외에 더 나은 방법이 있는가?

**결정** — **3중 배치.** 용도별로 나눈다.

| 용도 | 방식 | 이유 |
|---|---|---|
| 하드 제약 | 폐기 사유를 규칙으로 추출 → 지시문 | 반드시 지켜야 할 것 |
| 스타일·수준 | few-shot **2～3건만**, 압축 형태 | 사례를 통으로 넣으면 표면 모방 발생 (붕어빵 사례가 많으면 계속 붕어빵류 제안) |
| 최종 검수 | 체크리스트 자가점검 | 출력 직전 스스로 확인 |

> 사례가 쌓여도 전부 넣지 않는다. 예시가 많을수록 출력 다양성이 줄고, 프롬프트 중간부는 주의가 덜 간다.

### D2. 폐기된 기획안을 부정 예시로 넣어도 되는가

**질문** — "이런 결과는 피하라"는 부정 예시가 실제로 효과가 있는가? 있다면 주입 위치나 표현에서 유의할 점은?

**결정** — **원문 그대로 넣지 않고, 폐기 사유를 긍정형 제약으로 변환**해 주입한다.

```
[X]  "이 기획안은 폐기됨: [준비 2주짜리 기획안 전문]"
[O]  "준비 기간은 3일 이내로 제한한다"
```

> LLM은 부정문 처리가 취약하다. "붕어빵을 제안하지 마라"고 하면 오히려 붕어빵이 나올 수 있다.
> 부정 예시를 쓸 경우 사례 전문이 아닌 **폐기 사유 한 줄만**, 긍정 예시와 **물리적으로 분리된 섹션**에 둔다.

### D3. 수치를 어떻게 프롬프트에 넘길 것인가

**질문** — 컨텍스트 빌더가 수치를 문장으로 바꾸는 과정에서 정보 손실이 발생한다. 어느 수준까지 해석해서 전달해야 하는가? 원수치를 함께 주는 편이 나은가? LLM이 없는 값을 만들어내는 것을 어떻게 막는가?

**결정** — **원수치와 해석을 병기**하고, **출력 후 코드로 대조 검증**한다.

```
금요일 19~22시 매출 비중 34% (주중 최고)
```

해석만 주면 근거를 제시하지 못하고, 원수치만 주면 잘못 읽는다. 환각 방지는 세 겹으로 둔다.

1. 없는 항목은 **"데이터 없음"으로 명시** — 누락하면 모델이 지어낸다
2. 지시문에 *"입력에 없는 숫자를 만들지 말 것, 직접 계산하지 말 것"* 명시
3. [중요] **후처리 검증** — 출력의 `추천_근거`에 나온 숫자가 입력 컨텍스트에 존재하는지 정규식으로 대조 (5-1의 A3)

> 3번이 핵심이다. 프롬프트로 막는 데는 한계가 있으나 코드 대조는 확실하다.

### D4. 페르소나를 병렬로 돌릴 것인가 순차로 돌릴 것인가

**질문** — 응답 시간 때문에 (2) 셰프와 (3) 마케터를 병렬로 두면 서로를 참조하지 않아 메뉴와 이벤트가 어긋난다. 순차로 바꾸면 정합성은 나아지나 느려진다. 어느 쪽이 유리한가?

**결정** — **순차 + 3안 병행.** (1)→(2)가 3안 동등 제시→(3)이 3안 각각 홍보 생성→(4)가 순위 결정.

- 시간 차이가 크지 않다. 실측 결과 4단계 순차가 **약 17초**로 확인되어(6-2-3) 병렬화의 실익이 사라졌다
- 반면 정합성 문제는 실질적이다. 마케터가 메뉴를 모르면 "가을 콜라보 이벤트" 같은 공허한 결과가 나온다
- **순위 결정권을 (4)로 일원화**한다

> [주의] **미검증.** T26에서 현행과 병렬안을 각 10회 생성해 정합성을 비교한다.

### D5. 정답이 없는 생성물의 품질을 어떻게 측정할 것인가

**질문** — 기획안처럼 정답이 정의되지 않는 출력의 품질을 어떻게 재는가? 프롬프트 수정이 개선인지 퇴보인지 판별할 방법이 대표님의 주관적 판정뿐이다.

**결정** — **3층 구조.** LLM-as-judge는 채택하지 않는다.

| 층 | 방법 | 주체 | 비용 |
|---|---|---|---|
| 1 | 자동 검증 — 스키마·필수필드·수치대조·제약위반 | 코드 | 0 |
| 2 | 루브릭 채점 — 5항목 × 1～5점 | 대표님 | 건당 2분 |
| 3 | 채택률 — 3안 중 채택 비율 | 자동 집계 | 0 |

> LLM-as-judge는 judge 자체를 검증해야 하고, 같은 모델이면 자기 출력에 후한 편향이 있다.
> [중요] **고정 테스트셋(5-5)이 전제 조건이다.**
> 프롬프트를 수정한 뒤 결과가 나빠졌을 때, 프롬프트 탓인지 입력이 달라진 탓인지 구분할 수 없기 때문이다.
> 입력 8건을 고정해두고 버전마다 같은 8건을 재생성하면, 통과율·평균점수의 차이가 곧 프롬프트의 차이가 된다.

### D6. 대표님이 데이터를 신뢰하지 않는 상황을 어떻게 풀 것인가

**질문** — 현장방문 보고서에 *"상권 데이터를 영업전략에 반영하기 어렵다"*는 대표님 의견이 기록되어 있다. 우리 설계는 공공 상권데이터를 (1) 상권분석가의 주 입력으로 삼는데, 근거를 어떤 형태로 제시해야 수용도가 올라가는가?

**결정** — 네 가지를 적용한다.

1. **일반론이 아니라 행동으로** — "금요일 19～22시 매출 비중이 높습니다" [X] → "이번 금요일 19시에 붕어빵 팝업을 여세요" [O]
2. [중요] **아는 것부터 검증받기** — 대표님이 이미 아는 사실을 먼저 보여주고("맞네"), 그다음 모르는 것을 제시한다
3. **실시간 지표를 앞세우기** — 분기 데이터보다 "지금 뚝섬 혼잡도"가 설득력이 크다 → 대시보드를 W3으로 앞당김(4-4)
4. **예측과 실제를 나란히 기록** — 적중률이 쌓이면 가장 강한 근거가 된다

### D7. 사업 종료 후 비개발자가 유지할 수 있게 하려면

운영 주체가 사업 종료 후 개발 지식이 없는 소상공인 본인이 된다. **프롬프트를 코드 외부 파일로 분리**하고, 목표를 "직접 개발"이 아니라 **"방치해도 돌아감 + 외주가 이어받을 수 있음"**으로 잡는다. 상세는 8장.

### D4 변경에 따른 체인 구조

```
(1) 상권분석가 → (2) 셰프 → (3) 제휴 마케터 → (4) AI 컨설턴트
   상권 진단      메뉴 3안      3안 각각의        3안 재평가·
                 (동등, 순위X)   홍보 기획        순위 확정
    ~1.9초        ~3.7초         ~4.3초           ~7.1초     약 17초
```

**각 단계의 역할 경계**

| 단계 | 하는 것 | 하지 않는 것 |
|---|---|---|
| (2) 셰프 | 서로 다른 접근의 메뉴 **3안을 동등하게** 제시 | 순위를 매기지 않는다 |
| (3) 마케터 | **3안 각각**에 대한 홍보 기획 | 메뉴를 평가하거나 고르지 않는다 |
| (4) 컨설턴트 | 메뉴+홍보 3세트를 받아 **순위 확정** 및 정합성 교정 | 메뉴를 새로 만들지 않는다 |

**왜 이 구조인가**

- **순위 결정권이 (4)로 일원화된다.**
- **대표님이 3안을 동등한 형태로 비교**할 수 있다. 일부만 홍보 기획이 있으면 *"홍보가 없어서 안 골랐다"*는 노이즈가 채택률 지표를 오염시킨다

**(3)의 토큰 절감 방식** — 3안을 독립적으로 쓰면 상권·협력사·시점이 같아 내용의 상당 부분이 중복된다. 프롬프트에서 다음을 지시한다.

```
1. 세 안에 공통 적용되는 홍보 축을 먼저 1개 작성한다.
2. 각 안마다 다른 부분만 별도로 작성한다. 공통 내용을 반복하지 않는다.
```

## 1. 프롬프트 명세

### 1-0. 공통 규칙

모든 프롬프트는 `prompts/` 디렉터리에 **YAML 파일로 분리**한다. 코드에는 파일명만 남긴다.

> ⚠️ **변수 치환에 `str.format()`을 쓰지 않는다.** 프롬프트에 출력 스키마용 중괄호가 있어 충돌한다. 상세는 6-2-4 참조.

```
prompts/
  common_rules.yaml      # 전 페르소나 공통 지시
  p1_analyst.yaml
  p2_chef.yaml
  p3_marketer.yaml
  p4_consultant.yaml
  constraints.yaml       # 폐기 사유에서 추출한 하드 제약 (누적 갱신)
  fewshot.yaml           # 채택 사례 2~3건 (회전)
```

**공통 지시문 (모든 프롬프트 앞단에 삽입)**

```
[출력 규칙]
- 반드시 지정된 JSON 스키마로만 응답한다. 설명 문장을 앞뒤에 붙이지 않는다.
- 입력에 제시되지 않은 수치를 만들어내지 않는다.
- 계산이 필요한 경우 직접 계산하지 않고, 입력에 있는 값을 그대로 인용한다.
- 근거로 인용하는 수치는 반드시 입력 컨텍스트에 존재하는 값이어야 한다.
- 정보가 없는 항목은 추정하지 말고 "데이터 없음"으로 표기한다.
```

### 1-1. (1) 상권분석가

> **2026-08-29 갱신.** 프롬프트 전문은 `prompts/p1_analyst.yaml`이 원본이다.
> 여기에는 설계 의도와 절 구조만 남긴다. 파일이 자주 바뀌어 전문을 옮기면 문서가 늘 뒤처진다.
> 검증: `tests/test_p1.py`

**입력**

| 변수 | 출처 |
|---|---|
| `{target_date}` | 사용자 입력 (`2026-09-18`) |
| `{context}` | 컨텍스트 빌더 출력 (6-3) |

**절 구조**

| 절 | 역할 |
|---|---|
| `[등급 체계]` | 인구 4단계와 상권 4단계가 서로 다름을 알린다 |
| `[데이터 읽는 법]` | 컨텍스트의 각 표기가 무엇을 뜻하는지 |
| `[지켜야 할 것]` | 위반하면 안 되는 것 |
| `[지시]` | 무엇을 산출할 것인가 |
| `[출력 스키마]` | JSON 형태 |

「데이터 읽는 법」과 「지켜야 할 것」을 나눈 것은, 8/27까지 `[해석 기준]`과 `[해석 원칙]`이라는 비슷한 이름의 두 절이 있어 무엇이 사실 설명이고 무엇이 금지인지 구분되지 않았기 때문이다.

**설계 의도**

**등급 체계를 먼저 알린다.** 인구는 `여유 < 보통 < 약간 붐빔 < 붐빔`, 상권은 `한산한 < 보통 < 바쁜 < 분주한`으로 다르다. `'보통'`이 양쪽에 있어 혼동하기 쉽다.

**"관측 N건"을 측정 횟수로만 읽게 한다.** 실제로 관측 8건인 구간을 "상권 활동이 활발하다"의 근거로 쓴 적이 있다. 수집 횟수는 사람 수도 매출도 아니다.

**`(참고)` 순위를 그대로 받지 않게 한다.** 2건짜리 판정이 17건 구간보다 앞설 수 있으므로 근거 건수를 함께 보게 한다.

**근거 크기에 맞춰 서술 강도를 조절하게 한다.** 다만 *"건수가 적으면 판단하지 마라"*로 쓰면 표본이 1～5건인 현재 데이터에서 공략 시간대가 매번 비어버린다. 그래서 **판단은 하되 확신의 정도를 낮추라**는 형태로 지시하고, *"건수가 적다는 이유로 시간대 선정 자체를 비우지는 마라"*를 덧붙였다.

**방문객 구성의 두 축을 구분하게 한다.** 인구 비중과 소비 비중은 다르다. 뚝섬역 40대는 인구 16% / 소비 31%다. 메뉴 가격대를 정할 때는 소비 쪽을 본다.

**분기 매출과 실시간 지표가 어긋날 수 있음을 알린다.** 실시간 인구는 사람 수이고 분기 매출은 금액이라 애초에 다른 것을 잰다. 실제로 실시간 인구는 17-21시가 최다인데 매출은 21-24시가 61%다. 어느 쪽을 택할지는 협업의 목적에 달렸다.

**영업시간 밖 구간도 읽되 공략 시간대로는 고르지 않게 한다.** 새벽 데이터로 "이 동네는 주민 비율이 높다"를 파악하는 것은 유용하다.

**영업시간**

```
월요일          정기휴무
화·수요일       15:00 - 23:00
목·금·토·일요일  15:00 - 22:30
```

대상 시점이 월요일이면 공략 시간대를 비우고 그 사실을 주의사항에 기록한다.

#### 메뉴 이미지 생성

대표님 직접 요구다. 협업 제안서에 글만 있는 것보다 이해가 빠르다.

**LLM 호출과 분리한다.**

```
(2) 셰프  →  메뉴 3안 (텍스트)
                ↓
          이미지 생성 (별도 호출)
                ↓
          img/plans/{날짜}_{안id}.png
```

**분리하는 이유가 셋이다.**

**① 실패해도 기획안은 나와야 한다.** 이미지 생성이 실패하거나 느려도 텍스트 기획안은 완성되어야 한다. 같은 호출에 묶으면 하나가 막힐 때 전체가 막힌다.

**② 응답 시간이 늘어난다.** 지금 4단계에 약 20초인데 이미지 3장을 더하면 체감이 크게 달라진다. 화면에서는 텍스트를 먼저 보여주고 이미지는 나중에 채운다.

**③ 재생성이 잦을 것이다.** 이미지는 마음에 안 들면 다시 뽑게 된다. 체인 전체를 다시 돌리지 않고 이미지만 재생성할 수 있어야 한다.

**프롬프트 구성**

```
{메뉴명} / {구성}
협업 메뉴 사진. 맥주와 함께 놓인 구도.
음식 사진, 자연광, 배경 단순
```

> **모델 선정이 필요하다 (U16).** 실제 호출과 품질 확인이 먼저다. 결과가 쓸 만하지 않으면 이 기능을 뺀다.

> **생성 실패는 정상 흐름으로 다룬다.** `메뉴_이미지`를 `null`로 두고 제안서에서 그 자리를 생략한다. 오류로 처리하지 않는다.

#### 유행 메뉴 반영

메뉴 검색 경로로 시작한 경우, 대표님이 입력한 메뉴명이 `{trend_menu}`로 전달된다.

```
"두바이 초콜릿 (대표님 지정)"
```

**세 안 모두 그 메뉴를 축으로 삼는다.** 그 메뉴를 다루는 곳을 골라 온 흐름이므로(유행메뉴 검색 설계) 다른 메뉴를 제안하면 검색한 의미가 없다. **접근을 달리하는 것은 구성과 가격대이지 메뉴 자체가 아니다.**

```
A안  두바이 초콜릿 붕어빵 2개        (단품)
B안  두바이 초콜릿 붕어빵 + 맥주 세트  (세트)
C안  미니 사이즈 3개 구성            (원가 절감형)
```

메뉴 검색 경로가 아니면 `데이터 없음`으로 넘긴다.

> **협력사 자원에 관련 재료가 없는 경우는 앞 단계 문제다.** 블로그 언급이 있다고 지금도 파는 것은 아니어서, 협력사가 입력 폼에 적은 재료에 그 메뉴 관련이 없을 수 있다. 그때는 (2)가 억지로 만들지 말고 무엇이 없어서 불가능한지 `공통_주의사항`에 적는다.

##### 홍보가 이 프로젝트의 실제 병목이다

기존 협업 3건의 결과를 들었다. **세 건 모두 홍보에서 아쉬웠다.**

| 협업 | 무엇이 문제였나 |
|---|---|
| **떡붕** (드론쇼 기간) | 유동인구는 많았으나 유인 요인 부족. **현수막만으로는 부족** |

##### 규칙 셋을 주입한다 (1-5)

세 건의 실패 원인이 조금씩 달라 규칙을 셋으로 나눴다.

**`주체` 필드를 새로 둔다.** 누가 올리는지가 명확해야 협업 제안서에 역할분담으로 옮길 수 있다(1-4).

> 협력사에 홍보를 요청하는 것은 **협력사가 얻는 것**과 맞물린다. 상대에게 노출을 부탁하려면 상대도 얻는 것이 있어야 한다. (4)의 `상호_이익`이 이와 연결된다.

**설계 의도**

**공통 홍보축을 먼저 쓰고 안별로는 차이만 쓴다.** 타겟·공략 시점·채널 전략·행사 연계는 세 안이 공유하므로 한 번만 쓴다. 세 안마다 반복하면 출력이 세 배가 된다.

이 구조의 한계는 9-1 M2에 적었다. 메뉴에 따라 손님층이 갈릴 수 있으나, 안별 타겟 보정을 넣으면 (4)가 순위를 매길 근거가 사라진다.

**홍보 일정은 공통 축에 둔다.** 세 안의 메뉴가 달라도 알리는 시점과 채널은 같다. 안별로 다른 것은 무엇을 알리는지(소재)이고, 그것은 `차별_포인트`에 담긴다.

**"데이터 없음"인 항목에 기대는 목표를 세우지 않게 한다.** 바틀링 SNS 팔로워 수를 모르는데 "도달 1만"을 적으면 근거가 없다. `계정 정보 확인 후 산정`으로 적게 한다.

**타겟을 통계가 아니라 사람으로 쓰게 한다.** 비중을 그대로 옮겨 적은 적이 있다. `"20대 21% / 40대 18%"`가 아니라 `"퇴근길에 한강으로 나온 20～30대 직장인"`이어야 홍보 대상이 된다. 근거 수치는 뒤에 괄호로 짧게 덧붙인다.

**홍보 문구를 그대로 게시할 수 있는 완성된 문장으로 쓰게 한다.** *"~를 강조하는 문구"* 같은 설명은 대표가 바로 쓸 수 없다. 루브릭의 「홍보 실효성」 5점 기준이 "바로 게시 가능"이다.

**준비물은 홍보·이벤트용만 적게 한다.** 조리 장비는 (2)의 `필요_장비`가 이미 다룬다. 냉장고와 전자레인지를 준비물로 적은 적이 있다.

**기간·소요 기간을 마케터가 정하게 한다.** 데이터에서 오는 값이 아니므로 `데이터 없음`으로 두면 안 된다.

**기존 협업의 실패를 반복하지 않게 한다.** `{past_cases}`로 세 건의 결과를 준다. 다만 **규칙(`constraints`)이 이미 그것을 반영하고 있으므로**, 사례는 왜 그 규칙이 있는지를 이해하는 맥락으로만 쓴다. 사례를 직접 흉내내게 하지 않는다.

#### 2차 방문으로 추가된 출력 (8/31)

대표님 요구는 **협업 제안서로 그대로 쓸 수 있어야 한다**는 것이었다.

> *"역할분담, 얻어가는 게 서로 뭔지 확실히. 직관적으로 이해할 수 있게. 배경 설명"*

**협력사가 읽고 판단하는 문서**이므로 바틀링 입장만 적혀 있으면 안 된다.

##### ① 역할분담

누가 무엇을 하는지 양쪽으로 나눠 적는다.

```json
"역할분담": {
  "바틀링": ["완제품 매입", "매장 판매", "SNS 홍보"],
  "협력사": ["메뉴 제작", "협업 기간 물량 확보", "자체 계정 홍보"]
}
```

**「완제품 매입」이 기본형이다 (3-5).** 협력사가 만들어 오고 바틀링이 파는 구조이므로 역할이 명확히 갈린다.

##### ② 상호 이익

각자 무엇을 얻는지 적는다. **한쪽만 이득이면 협업이 성사되지 않는다.**

```json
"상호_이익": {
  "바틀링": "맥주와 어울리는 안주 확보. 신규 손님 유입",
  "협력사": "저녁 시간대 신규 판로. 바틀링 고객층에 노출"
}
```

**협력사 쪽을 구체적으로 쓰게 한다.** 「홍보 효과」 같은 막연한 말이 아니라, 그 가게가 실제로 얻는 것을 적어야 제안이 설득력을 갖는다.

##### ③ 배경

왜 이 협업을 제안하는지 상권 근거로 설명한다. 협력사 입장에서는 **"왜 하필 우리인가"**에 대한 답이다.

```json
"배경": "뚝섬역 17-21시 소비 연령이 30대 30%로 가장 높고, 이 시간대에
        디저트류 결제가 관측됩니다. 귀사의 주력 메뉴와 맞물립니다."
```

##### ④ 매입가

**기존 협업의 분배 방식이 제각각이었다 (8/31 청취).**

| 협업 | 분배 |
|---|---|
| 떡붕 | 바틀링 20% / 떡붕 80% |
| 화덕피자 | 바틀링 100% (재료 직접 구매, 기계만 지원) |
| 카페 위켄드 | 바틀링 100% (매입 후 판매) |

대표님 요구는 *"AI가 판매가를 주고, 하나 팔 때 재료비가 얼마 들어가니까 마진율을 참고해서 분배율을 추천하는 식으로"*였다. **두 단계로 나뉜다.**

```
① 재료비 + 마진율  →  판매가          — (2) 셰프가 한다
② 판매가 - 매입가  →  각자의 몫       — (4) 컨설턴트가 한다
```

**협업을 완제품 매입 하나로 한정했으므로**(기획서 6-1) **「분배율」이 아니라 매입가가 협의 대상이다.** 협력사는 판매량과 무관하게 매입가를 받는다.

```json
"매입": {
  "제안_매입가": "1,500원 — 판매가 4,000원 대비 38%",
  "근거": "협력사 희망 단가 1,500원. 없으면 시중가와 원가 구조로 추정",
  "협력사_수익": "개당 1,500원 × 납품 수량",
  "협의_필요": true
}
```

> **매입가는 AI가 정할 수 없다.** 협력사의 원가를 우리가 모르고, 결국 양측이 협의할 값이다. **제안값과 근거를 내되 `협의_필요`를 항상 `true`로 둔다.** 대표님이 그 숫자를 출발점으로 삼아 협상하시면 된다.

> **`partners.wholesale_price`가 있으면 그 값을 쓴다** (2-1). 협력사가 폼에 희망 단가를 적었다면 추정할 필요가 없다. 비어 있을 때만 시중가와 마진 기준값으로 추정하고 `추정`임을 밝힌다.

> **수익 배분·위탁 방식은 이번 범위 밖이다** (기획서 6-1). 되돌릴 수 있도록 규칙(C005)으로 분리해 두었다.

##### ⑤ 메뉴 이미지

(2) 셰프가 생성한 이미지 경로를 그대로 옮긴다. 생성 실패 시 `null`로 두고 제안서에서 생략한다. 상세는 1-2 참조.

**설계 의도**

**비교가 성립하는 이유를 명시한다.** 세 안은 같은 시점·같은 손님을 두고 만들어졌고 공통 홍보축이 함께 적용되므로 조건이 같다. 이 전제가 있어야 순위를 매길 수 있다.

**제외는 실행 불가일 때만 한다.** 검수 1·2·6번 위반이 아니면 반드시 순위에 넣는다. *"메뉴가 덜 매력적"*, *"페어링 단가가 낮음"*을 이유로 안을 제외한 적이 있는데, 그것은 순위를 낮게 산정할 근거이지 제외 사유가 아니다. **대표가 세 안을 나란히 놓고 골라야 채택률이 오염되지 않는다**(D4).

**순위를 반드시 확정하게 한다.** *"우열을 가리기 어렵다"*로 끝내면 대표가 판단할 수 없다. 비슷하면 무엇을 더 중히 봤는지 밝히고 정하게 한다.

**후순위 사유를 적게 한다.** 왜 1위가 아닌지가 없으면 2·3위 안을 검토할 수 없다.

**원가가 `산출 불가`인 것을 이유로 순위를 낮추지 않게 한다.** 협력사 식재료 단가를 아직 받지 못한 것은 안의 문제가 아니다. 다만 그 사실은 예상 리스크에 적게 한다.

**1위 안은 그대로 실행할 수 있게 모은다.** 메뉴·홍보·준비물을 한데 옮겨, 대표가 이 문서만 보고 실행 여부를 정할 수 있어야 한다(4-2).

**역할분담과 상호 이익은 1위 안에만 쓴다.** 세 안 모두에 쓰면 출력이 세 배가 되고, 실제로 제안서로 나가는 것은 채택된 안 하나다. 2·3위는 순위와 사유까지만 적는다.

**매입가는 협의 대상임을 명시한다.** 협력사의 원가를 우리가 모르므로 AI가 정할 수 없는 값이다. 제안값과 근거를 내되 `협의_필요`를 항상 `true`로 두어, 대표님이 그 숫자를 출발점으로 협상하시게 한다.

### 1-5. constraints.yaml — 폐기 사유의 긍정형 변환

> **2026-09-03 갱신.** 2차 방문(8/31)에서 기존 협업 3건의 경과를 들었다. 가상 예시를 실제 사례에서 뽑은 규칙으로 교체했다.

폐기가 발생할 때마다 사유를 **긍정 제약**으로 바꿔 누적한다. 원문은 넣지 않는다.

**LLM은 부정문 처리가 취약하다.** *"준비 기간이 길면 안 된다"*보다 *"준비 기간은 3일 이내로 제안한다"*가 지켜진다.

#### 기존 협업 3건에서 뽑은 규칙 (8/31)

시스템 도입 전에 대표님이 직접 하셨던 협업이다. **세 건 모두 홍보에서 아쉬웠다.**

| 협업 | 결과 |
|---|---|
| **떡붕** (드론쇼 기간) | 유동인구는 많았으나 유인 요인 부족. 현수막만으로는 부족 |
| **YARR 화덕피자** | 반응은 괜찮았으나 맛이 대중적이지 않았음 |
| **카페 위켄드** | 파는지도 모를 정도로 인지 부족. 소요 대비 효과 없어 중단 |

대표님 말씀이 *"길게 꾸준히 하든가, 하기 전에 사람들이 많이 인지할 수 있게 콘텐츠를 뽑든가"*였다.

```yaml
constraints:
  # ── 홍보 (3건 공통 실패 요인) ──
  - id: C001
    origin: "떡붕 — 유동인구는 많았으나 현수막만으로는 유인이 부족했다 (2025)"
    rule: "홍보는 실행 최소 1주 전부터 시작하고, 현장 게시물 외에 온라인 사전 콘텐츠를 하나 이상 포함한다."
    target: p3

  - id: C002
    origin: "카페 위켄드 — 파는지도 모를 정도로 인지가 부족했다 (2025)"
    rule: "협업 사실을 알리는 콘텐츠를 실행 전에 배치한다. 실행 기간에만 알리는 구성은 피한다."
    target: p3

  - id: C003
    origin: "카페 위켄드 — 짧게 한 번으로는 효과가 없어 중단했다 (2025)"
    rule: "실행 기간은 최소 3일 이상으로 제안한다. 하루짜리 이벤트는 인지가 쌓이기 전에 끝난다."
    target: p3

  # ── 메뉴 ──
  - id: C004
    origin: "YARR 화덕피자 — 맛이 대중적이지 않았다 (2025)"
    rule: "익숙한 맛을 기본으로 하고, 새로운 요소는 한 가지만 둔다."
    target: p2

  # ── 실행 조건 ──
  - id: C005
    origin: "2차 방문 — 완제품 매입 형태가 가장 적합하다 (8/31)"
    rule: "협력사가 완성한 것을 받아 그대로 판매하는 구성으로 만든다. 바틀링에서 조리하거나 조합하는 단계를 두지 않는다."
    target: p2

  - id: C006
    origin: "떡붕 — 반죽은 당일 소진해야 한다 (8/31)"
    rule: "완제품의 보관 방법과 유통 기한을 밝힌다. 당일 소진해야 하는 품목은 1회 납품 수량을 함께 제안한다."
    target: p2

  - id: C007
    origin: "2차 방문 — 준비 기간이 길면 실행이 밀린다"
    rule: "준비 기간은 3일 이내로 제안한다."
    target: p2
```

> [주의] `origin`은 이력 추적용이며 **프롬프트에는 `rule`만 주입**한다.

> **`target`을 새로 두었다.** 규칙이 늘면서 (2) 셰프와 (3) 마케터에 각각 해당하는 것이 갈렸다. 모든 규칙을 모든 단계에 넣으면 프롬프트가 길어지고, 관계없는 제약이 판단을 흐린다.
>
> `target`이 없는 규칙은 (2)·(3)·(4) 모두에 넣는다.

#### 왜 홍보 규칙이 셋인가

세 건 모두 홍보에서 아쉬웠으나 **원인이 조금씩 다르다.**

| 규칙 | 문제 |
|---|---|
| C001 | **채널이 부족** — 현수막 하나뿐 |
| C002 | **시점이 늦음** — 실행 기간에만 알림 |
| C003 | **기간이 짧음** — 인지가 쌓이기 전에 끝남 |

#### 협업 형태 단일화로 바뀐 규칙 (9/3)

협업을 **완제품 매입 하나로 한정**하면서(기획서 6-1) C005·C006이 달라졌다.

| | 전 | 후 |
|---|---|---|
| **C005** | 매입 형태를 「우선 검토」 | 매입 형태로 **고정**. 조리 단계를 두지 않는다 |
| **C006** | 장비 리드타임 우회 | **완제품 보관 조건**을 밝힌다 |
| **C007** | (C006에 포함) | 준비 기간 3일 — 별도 규칙으로 분리 |

**C006이 통째로 바뀐 이유** — 원래는 붕어빵기계 1주 예약을 피하려는 규칙이었다. 매입 형태에서는 **협력사가 자기 장비로 만들므로 그 문제가 없다.** 대여는 「가게 자체 메뉴 개발」(기획서 3-5 ⑦)로 옮겨졌다.

대신 매입에서 새로 생기는 문제를 담았다. 떡붕의 *"반죽은 당일 소진해야 한다"*처럼 **완제품의 보관 조건이 기획의 전제**가 된다. 당일 소진 품목이면 1회 납품 수량이 곧 판매 가능 수량이다.

하나로 묶으면 *"홍보를 잘 하라"*가 되어 지시가 되지 않는다. **셋으로 나누면 각각이 검증 가능한 형태가 된다** — 사전 콘텐츠가 있는가, 실행 전에 배치되었는가, 기간이 3일 이상인가.

#### 새 규칙을 넣는 기준

폐기가 발생하면 **사유를 규칙으로 바꿀 수 있는지 먼저 본다.**

| | 예 |
|---|---|
| **규칙이 되는 것** | 준비 기간, 원가율, 홍보 시점, 조리 형태 — **다음에 지킬 수 있는 조건** |
| **규칙이 안 되는 것** | *"메뉴가 매력 없었다"*, *"타이밍이 나빴다"* — 판단이지 조건이 아니다 |

후자는 `fewshot.yaml`의 반례로 넣거나, 루브릭 채점 시 참고로만 쓴다. **규칙으로 만들면 *"매력 있게 만들어라"* 같은 지시가 되어 아무것도 바꾸지 못한다.**

#### 규칙이 쌓이면

실증 구간(9/21～10/16)에 협업이 1건뿐이라 **규칙은 크게 늘지 않는다.** 위 7건이 사실상 전부일 가능성이 높다.

다만 프롬프트 튜닝(T18)에서 반복적으로 나타나는 문제는 규칙으로 승격할 수 있다. 예를 들어 세 안의 페어링이 계속 저가 라인에 몰리면 그것을 `constraints`로 옮긴다. **지금은 프롬프트 본문에 적혀 있으나, 규칙으로 분리하면 이력이 남는다.**

**협업 형태를 좁힌 것도 되돌릴 수 있다.** C005는 「매입 형태로 고정」이지만, 실증 이후 다른 형태를 다루기로 하면 이 규칙만 고치면 된다. 규칙으로 분리해 두었기에 프롬프트 본문을 건드리지 않아도 된다.

### 2-1. partners — 협력사 마스터

> **2026-09-03 갱신.** 협업 형태가 「완제품 매입」 중심이 되어 희망 단가를 받는다.

```sql
CREATE TABLE partners (
  id                BIGSERIAL PRIMARY KEY,
  name              TEXT        NOT NULL,
  category          TEXT        NOT NULL,          -- 업종 (음식점업/제과업 등)
  signature_menu    TEXT,                          -- 대표 메뉴
  ingredients       TEXT[]      NOT NULL DEFAULT '{}',
  equipment         TEXT[]      NOT NULL DEFAULT '{}',
  collab_types      TEXT[]      NOT NULL DEFAULT '{}',  -- 팝업출장/재료납품/콘텐츠
  available_slots   TEXT,                          -- "주중 오후"
  sns_channel       TEXT,
  sns_followers     INTEGER,
  sns_content_type  TEXT,                          -- 릴스/피드/스토리
  wholesale_price   INTEGER,                       -- 완제품 납품 희망 단가 (원)
  blockers          TEXT[]      NOT NULL DEFAULT '{}',  -- 절대 불가 조건
  lat               DOUBLE PRECISION,
  lng               DOUBLE PRECISION,
  invite_code       TEXT UNIQUE NOT NULL,          -- 폼 접근용
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

> `blockers`는 (2) 셰프 프롬프트에 **하드 제약**으로 주입되며, (4)의 체크리스트 6번에서 재검증된다.

**`wholesale_price`를 새로 둔다.** 협업 형태가 「완제품 매입」이 기본이 되어(1-2 ①) **매입가가 원가를 대체한다.**

지금 (2) 셰프의 `예상_원가`가 `산출 불가`로 나오는 것은 협력사 식재료 단가를 모르기 때문이다. 완제품 매입이면 **식재료 단가를 알 필요가 없다.** 협력사가 얼마에 주는지만 알면 된다.

| 값이 있으면 | 값이 없으면 |
|---|---|
| (2)의 `예상_원가`가 실제 수치로 채워진다 | 지금처럼 `산출 불가` |
| (4)의 `제안_매입가`가 근거를 얻는다 | 시중가와 원가 구조로 추정 |

> **선택 항목으로 둔다 (NULL 허용).** 협력사가 미리 정하지 못할 수 있고, 결국 양측이 협의할 값이다. 강제하면 폼 이탈이 늘어난다(4-1의 「3분 이내」 목표).

**`sns_content_type`도 새로 둔다.** (3) 마케터가 협력사 채널을 함께 쓰도록 바뀌어(1-3), 그 계정이 주로 어떤 형식을 올리는지 알아야 한다. 릴스 중심 계정에 피드 게시물을 요청하면 협력사가 부담스러워한다.

> 이미 `chain/inputs.py`의 `SEED_PARTNER`에는 이 필드가 들어 있었다.

### 2-2. beers — 바틀링 맥주 라인업 (월 1회 교체)

> **2026-08-29 갱신.** 자료요청서 A-1 회신으로 스타일·도수가 확정되어 11종을 적재했다. `is_fixed` 컬럼을 추가했다.

대표님이 **월 1회 3종을 교체**하므로 코드에 하드코딩하지 않는다. 과거 기획안 재현을 위해 이력을 남긴다.

```sql
CREATE TABLE beers (
  id            BIGSERIAL PRIMARY KEY,
  name          TEXT NOT NULL,            -- 갈매기 IPA
  price_per_ml  NUMERIC(5,1) NOT NULL,    -- 20.0
  style         TEXT,                     -- IPA / 라거 / 위트에일 / 켈러비어
  abv           NUMERIC(3,1),             -- 도수 %
  ibu           INTEGER,                  -- 쓴맛
  flavor_notes  TEXT[],                   -- {과일향, 시트러스, 쌉쌀함}
  brewery       TEXT,
  is_alcohol    BOOLEAN NOT NULL DEFAULT true,
  is_fixed      BOOLEAN NOT NULL DEFAULT false,  -- true = 고정 메뉴, false = 교체 가능
  valid_from    DATE NOT NULL,            -- 라인업 적용 시작일
  valid_to      DATE,                     -- NULL이면 현재 판매 중
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_beers_valid ON beers (valid_to, valid_from DESC);
```

**적재 현황 (8/29)**

셀프탭 12개 중 **고정 5 + 교체 6 = 11종**이 판매 중이다. 흔들흔들(사워, 6도)은 8/28 확인 시점에 판매 목록에서 빠져 있어 제외했다 — 단가를 알 수 없어 추정으로 채우지 않았다.

| 구분 | 맥주 |
|---|---|
| **고정** | (논알콜) 체리에이드 8 · 바틀링 라거 12 · 37디그리스라거 14 · 카이저돔 켈러비어 16 · 빅웨이브 20 |
| **교체 가능** | 맘마미아 16 · 캄캄 16 · 산토리 프리미엄 몰츠 18 · 워터멜론 위트에일 20 · 갈매기 IPA 20 · 끽비어 삐약 ver2 20 |

숫자는 원/ml. 500ml 기준 4,000～10,000원이다. 적재는 `scripts/seed_beers.py`.

**`is_fixed`가 필요한 이유** — 기획부터 실행까지 며칠이 걸리고 실증 구간(9/21～10/16) 안에도 교체가 일어난다. 어느 것이 남아 있을 맥주인지 알아야 실행 시점에 없는 맥주로 기획하는 일을 피한다. 컨텍스트에는 `[고정]` / `[교체 가능]`으로 표시된다.

**조회 규칙**

```sql
-- 현재 라인업
SELECT * FROM beers WHERE valid_to IS NULL;
-- 특정 시점 라인업 (과거 기획안 재현)
SELECT * FROM beers WHERE valid_from <= :d AND (valid_to IS NULL OR valid_to > :d);
```

`chain/inputs.build_beer_list()`가 이것을 프롬프트용 문자열로 만든다. **저가 순으로 정렬**하는데, 단가가 페어링 판단의 근거이므로(1-4) 순서가 있으면 어느 것이 고가 라인인지 바로 읽힌다.

**논알콜을 목록에서 빼지 않는다.** 페어링에서 제외하는 것은 프롬프트의 지시이지 데이터의 성질이 아니다. 여기서 지우면 *"논알콜은 제외한다"*는 지시가 무엇을 가리키는지 알 수 없어진다.

**교체 절차** — 관리 화면(4-5)에서 처리한다.
1. CSV 업로드 또는 폼 입력으로 신규 라인업 등록
2. 기존 행의 `valid_to`를 교체일로 일괄 갱신
3. `style`·`abv`·`flavor_notes`가 비면 **경고 표시** — 페어링 품질에 직결된다

> [주의] 빅웨이브의 스타일이 미확정이다. 대표님이 `골든에일?`로 물음표를 붙여 회신하셨다 (U15). 이 맥주가 실제로 페어링에 선택되고 있어, 스타일이 다르면 홍보 문구까지 어긋난다.

### 2-3. market_context — 상권 시계열 (30분 배치 누적)

> **2026-08-22 갱신.** 실제 API 응답 확인 결과를 반영해 스키마를 재설계했다. 근거는 6-2 참조.

**통합 API(`citydata`) 1회 호출로 인구·상권·날씨를 모두 수신한다.**

```sql
CREATE TABLE market_context (
  id                BIGSERIAL PRIMARY KEY,
  collected_at      TIMESTAMPTZ NOT NULL,   -- API의 PPLTN_TIME (예정 시각 아님)
  spot              TEXT        NOT NULL,   -- 뚝섬한강공원 | 뚝섬역
  area_cd           TEXT,                   -- POI093 | POI025

  -- 인구
  congestion_level  TEXT,                   -- 여유 | 보통 | 약간 붐빔 | 붐빔
  congestion_msg    TEXT,                   -- 서울시가 제공하는 완성 문장
  population_min    INTEGER,
  population_max    INTEGER,
  ppltn_rates       JSONB,                  -- 성별·연령대·거주/비거주 비중
  forecast_12h      JSONB,                  -- 12시간 예측 배열

  -- 상권 (뚝섬한강공원은 데이터 없음 → NULL)
  cmrcl_level       TEXT,                   -- 한산한 | 보통 | 바쁜 | 분주한
  pay_count         INTEGER,
  pay_amt_min       BIGINT,
  pay_amt_max       BIGINT,
  food_pay          JSONB,                  -- 음식·음료 중분류별 결제 현황
  cmrcl_rates       JSONB,                  -- 결제자 성별·연령 비중

  -- 날씨
  temp              NUMERIC(4,1),
  humidity          INTEGER,
  precpt_type       TEXT,                   -- 없음 | 비 | 눈 ...
  pcp_msg           TEXT,

  raw               JSONB,                  -- CITYDATA 원본 전체
  UNIQUE (collected_at, spot)
);
CREATE INDEX idx_mc_spot_time ON market_context (spot, collected_at DESC);
```

**`food_pay` 구조** — 음식 결제가 단일 값이 아니라 중분류 4종으로 온다.

```json
{
  "한식":                  {"level": "한산한", "count": 7,  "amt_min": 250000, "amt_max": 300000, "store_cnt": 148},
  "일식/중식/양식":         {"level": "분주한", "count": 5,  "amt_min": 650000, "amt_max": 700000, "store_cnt": 123},
  "제과/커피/패스트푸드":    {"level": "바쁜",   "count": 12, "amt_min": 200000, "amt_max": 250000, "store_cnt": 68},
  "기타요식":              {"level": "한산한", "count": 7,  "amt_min": 90000,  "amt_max": 100000, "store_cnt": 191}
}
```

> **협력사 업종별 매칭이 가능해진다.** 붕어빵집이면 `제과/커피/패스트푸드`, 피자집이면 `일식/중식/양식`을 보면 되므로, 추천 엔진의 `S_timing`(3-2) 산출이 정교해진다.

**지점별 수신 데이터**

| 지점 | 인구 | 상권 | 날씨 |
|---|---|---|---|
| 뚝섬한강공원 (POI093) | O | **없음** | O |
| 뚝섬역 (POI025) | O | O | O |

한강공원은 상권 데이터 자체가 존재하지 않는다. 개별 상권 API를 직접 호출하면 `ERROR-500`이 반환되지만, 통합 API로 부르면 정상 응답에 해당 필드만 `None`으로 와서 예외 처리가 불필요하다.

→ **한강 상권의 소비 지표는 뚝섬역 데이터를 대리 지표로 사용한다.** 바틀링이 역과 한강 사이에 위치하므로 합리적 근사다.

### 2-4. sales_profile — 분기 매출 프로파일

> **2026-08-25 갱신.** 상권 단위 → **행정동 단위**로 전환. 사유는 아래 참조.
> **2026-08-29 적재 완료.** A 담당 T08. 205건 (5개 분기, 분기당 38～42업종).

```sql
CREATE TABLE sales_profile (
  id              BIGSERIAL PRIMARY KEY,
  quarter         TEXT NOT NULL,        -- 2026Q1
  dong_code       TEXT NOT NULL,        -- 행정안전부 주민등록 행정기관코드
  dong_name       TEXT NOT NULL,        -- 자양3동
  industry_code   TEXT,
  industry_name   TEXT NOT NULL,
  sales_amount    BIGINT,               -- 매출 금액 (원)
  sales_count     INTEGER,              -- 매출 건수 (거래 건수)
  weekday_ratio   JSONB,                -- {"월": 0.12, ..., "일": 0.18}
  timeband_ratio  JSONB,                -- {"00-06": 0.03, "06-11": ..., "21-24": 0.21}
  gender_ratio    JSONB,                -- {"남": 0.52, "여": 0.48}
  age_ratio       JSONB,                -- {"10": 0.02, ..., "60_이상": 0.09}
  UNIQUE (quarter, dong_code, industry_code)
);
```

**확정 사항**

| 항목 | 내용 | 확정 |
|---|---|---|
| `sales_count` | **매출 건수(거래 건수)**. 점포 수가 아니다 | 8/25 |
| `timeband_ratio` 키 | `"00-06"` `"06-11"` `"11-14"` `"14-17"` `"17-21"` `"21-24"` 6구간 | 8/25 |
| 비중 | 원본은 금액으로만 오므로 **적재 시 계산**한다 | 8/25 |
| **비중 기준** | **매출 금액**. 방문 인원 비율이 아니다 | 8/29 |
| **분기 범위** | 2025Q1 ～ **2026Q1** (5개 분기) | 8/29 |
| **업종 수** | 44종 (5개 분기 합집합. 분기마다 38～42종) | 8/29 |

**공공데이터라 최신 분기가 현재보다 수개월 뒤처진다.** 2026년 8월 시점에 2026Q1이 최신이다. 컨텍스트에 이 사실을 명시해 지금 상황으로 오해하지 않게 한다.

**성별·연령 비중의 합이 100%가 아니다.** 미상 결제가 3～6% 있다. 실측으로 호프-간이주점 2025Q4가 `남 66.97 + 여 30.17 = 97.14`다. `남 67%`를 보고 `여 33%`로 계산하면 안 된다.

> **객단가를 산출할 수 있다.** `sales_amount ÷ sales_count`로 업종별 평균 결제액이 나온다.
> 실측으로 호프-간이주점 44,918원 / 제과점 10,140원(2026Q1)이다. 협업 메뉴 가격대를 정하는 근거가 되어 (1) 상권분석가 입력에 포함했다.

**컨텍스트 빌더가 쓰는 방식 (6-3 원칙 ⑩)**

44종 전부를 실으면 컨텍스트가 감당되지 않는다. **바틀링 업종과 협력사 업종 둘만** 싣는다. 두 업종은 다섯 분기에 모두 존재한다.

| 대상 | 값 |
|---|---|
| 바틀링 | `호프-간이주점` (`BOTTLING_INDUSTRY` 상수) |
| 협력사 | `partners.category` → `INDUSTRY_MAP` → `industry_name` |

두 출처의 업종명이 다르다. 협력사는 사람이 고르는 분류(`제과·디저트`)이고 매출 데이터는 공공데이터의 서비스 업종명(`제과점`)이다. **피자 전용 업종은 없어** 3-3의 「피자·튀김·그릴」은 `치킨전문점`으로 대응한다.

매출·건수는 5개 분기를 모두 적고 비중은 최신 분기만 적는다. **금액에서 추세가 드러나므로** 코드가 증감을 판정할 필요가 없고, 비중은 분기별 차이가 작다(21-24시가 다섯 분기 내내 57～62%).

5개 분기를 다 싣는 것이 중요한 이유가 있다. 호프-간이주점은 `2025Q4 194M → 2026Q1 122M`로 최신 분기에 37% 줄었으나, `2025Q1 107M → 2026Q1 122M`으로 **같은 1분기끼리는 늘었다.** 최신 하나만 보이면 "매출 급감"으로 잘못 읽힌다.

#### [중요] 상권 단위를 쓸 수 없다

**바틀링이 서울시 「주요상권 82곳」에 포함되지 않는다.** 반경 3km로 검색해도 뚝섬 관련 상권이 없다. 따라서 상권코드를 전제한 설계를 모두 행정동 단위로 전환한다.

| 대상 | 전환 |
|---|---|
| `sales_profile` | 상권코드 → **행정동 코드 (자양3동)** |
| `S_trend` (3-2) | 상권변화지표-상권 → **상권변화지표-행정동** |
| V5 영역-상권 | **불필요** — 상권코드를 쓰지 않으므로 |
| T07 상권코드 판정 | **불필요** — 같은 이유 |

#### [중요] 축이 조합되지 않고 독립 합계로 온다

CSV가 요일·시간대·성별·연령을 **각각 독립 합계**로만 제공한다. `금요일 × 20대 × 여성` 같은 조합은 존재하지 않는다.

```
(불가) weekday × time_band × age_group 조합 행
(가능) 요일별 총합 / 시간대별 총합 / 성별 총합 / 연령별 총합
```

컬럼 조합형 스키마로는 담을 수 없어 **축별 비중을 JSONB**로 저장한다.

**컨텍스트 빌더(6-3)에 미치는 영향** — 조합 표현을 쓸 수 없으므로 축별 순위로 서술한다.

```
(불가) 주류업종 금요일 19～22시 매출 비중 34%
(가능) 요일 최고 토 23% / 시간대 최고 21-24 61% / 연령 최고 40 34%
```

정보 손실은 있으나 각 축의 순위는 그대로 파악할 수 있어 실용상 문제가 없다.

#### 남은 한계

**축별 객단가를 낼 수 없다.** CSV 원본에는 금액과 건수가 축마다 모두 있으나 적재 시 금액만 비중으로 변환했다. 실측으로 2026Q1 호프-간이주점의 21-24시는 금액 61% / 건수 55%로, 심야 손님의 객단가가 저녁보다 높다. 이 차이를 지금은 볼 수 없다. 상세는 9-1 M3.

### 2-7. plans — 생성 기획안 (Step4의 실체)

> **2026-09-03 갱신.** 2차 방문 요구로 메뉴 이미지·날짜 선정 방식·메뉴 검색 경로가 추가되었다.

```sql
CREATE TABLE plans (
  id                BIGSERIAL PRIMARY KEY,
  partner_id        BIGINT REFERENCES partners(id),
  partner_source    TEXT    NOT NULL DEFAULT 'recommended',
                    -- recommended | manual | menu_search
  trend_menu        TEXT,                 -- 메뉴 검색으로 시작한 경우 그 메뉴명
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
```

#### 추가한 컬럼

| 컬럼 | 왜 |
|---|---|
| `partner_source` | `menu_search` 추가 — 경로가 셋이 되었다 (4-3) |
| `trend_menu` | 메뉴 검색으로 시작한 경우 그 메뉴명. (2)에 전달되고 나중에 결과 비교에 쓴다 |
| `date_mode` `range_from` `range_to` `date_reason` | 날짜 지정과 희망 기간 두 방식 (4-2) |
| `menu_images` | 안별 이미지 경로. 생성 실패는 `null` |
| `image_model` | 재현용. 모델을 바꾸면 결과가 달라진다 |
| `image_latency_ms` | 이미지 생성은 별도 호출이라 4단계 시간과 분리한다 |
| **`lead_time_min`** | **기획 리드타임.** 실증 협업이 1건이라 이것이 주 지표다 (기획서 7-1) |
| **`agreed_wholesale`** | AI가 제안한 매입가와 실제 협의 결과를 비교한다 |
| **`retail_price`** `sold_qty` | 매입가와 판매가의 차이로 실제 이익을 낸다 |

**`lead_time_min`이 새 주 지표다.** 실증 협업이 10/9 한 건뿐이라 실행률·성공률로는 성과를 말할 수 없다. 문제 정의가 *"기획안을 내기까지 소요가 많음"*이었으므로 리드타임이 본래의 지표다.

```
9/12 블랙스미스   AI PM 없이 사람이 기획 — 기준선
10/9 협업         AI PM으로 기획
```

**9/12 협업도 이 테이블에 기록한다.** AI PM으로 생성한 것이 아니므로 `p1_output`～`final_output`은 비고 `lead_time_min`과 `performance`만 채운다. `status='executed'`, `note`에 *"AI PM 미사용 — 기준선"*으로 표시한다.

> 비교 대상이 없으면 리드타임 수치가 의미를 갖지 못한다. **기준선을 같은 테이블에 두는 것이 중요하다.**

#### 매입가는 제안값과 확정값을 함께 남긴다

협업이 완제품 매입 하나이므로(기획서 6-1) **매입가가 이 협업의 핵심 조건**이다.

```
final_output.순위[0].매입.제안_매입가   AI 가 제안한 값
agreed_wholesale                      협의로 확정된 값
```

**둘을 비교하면 AI 제안의 정확도를 잴 수 있다.** 제안이 1,500원이었는데 실제로 2,500원에 합의됐다면, 다음 제안에서 추정 근거를 다시 봐야 한다.

**`partners.wholesale_price`와도 다르다.**

| 값 | 성격 |
|---|---|
| `partners.wholesale_price` | 협력사가 폼에 적은 **희망 단가** |
| `final_output ... 제안_매입가` | AI가 낸 **제안값** |
| `plans.agreed_wholesale` | 양측이 합의한 **확정값** |

셋이 다를 수 있고, 그 차이가 곧 협상 여지다. 사례가 쌓이면 *"희망 단가보다 평균 얼마쯤에서 합의된다"*를 알 수 있다.

**`retail_price`와 `sold_qty`도 함께 받는다.** 매입가만으로는 실제 이익을 알 수 없다.

`retail_price`는 **손님이 실제로 낸 값**이다. AI가 제안한 판매가와 다를 수 있으므로 따로 받는다. 대표님이 4,000원 제안을 보고 3,500원에 파실 수 있다.

```
협력사 → (매입가 주고 사옴) → 바틀링 → (판매가 받고 팖) → 손님
```

**실제 예시** — 붕어빵 협업을 3일간 진행한 경우

| 값 | 컬럼 | 수치 |
|---|---|---|
| 협력사 희망 단가 | `partners.wholesale_price` | 1,200원 |
| AI 제안 매입가 | `final_output ... 제안_매입가` | 1,500원 |
| **협의 확정 매입가** | **`agreed_wholesale`** | **1,400원** |
| AI 제안 판매가 | `final_output ... 판매가_제안` | 4,000원 |
| **실제 판매가** | **`retail_price`** | **3,500원** |
| **판매 수량** | **`sold_qty`** | **80개** |

```
개당 마진   3,500 - 1,400 = 2,100원
총 이익     2,100 × 80    = 168,000원
협력사 수익 1,400 × 80    = 112,000원
```

**이 표가 있으면 AI 제안의 정확도가 드러난다.** 매입가는 100원 낮게, 판매가는 500원 높게 제안했다. 다음 기획에서 판매가 추정을 낮춰 잡을 근거가 된다.

> **`wholesale`과 `retail`로 이름을 나눈 것은** 어느 쪽이 사는 값이고 파는 값인지 헷갈리지 않기 위해서다. `partners.wholesale_price`와도 이름이 이어진다.

> 실증이 1건이라 이 수치로 통계를 말할 수는 없다. 다만 **한 건이라도 실제 숫자가 있으면** 최종보고서에 *"이 협업으로 얼마가 남았다"*를 쓸 수 있다.

#### `date_reason`이 필요한 이유

희망 기간 방식(`date_mode='range'`)에서는 **AI가 날짜를 고른다.** 왜 그 날짜인지가 남아야 대표님이 판단할 수 있다.

```
"10/9(목) 선정 — 기간 내 목요일 중 인근 행사(광진 뮤직 페스타)와 겹치고,
 목요일 17-21시 관측이 6건으로 기간 내 최다"
```

날짜 지정 방식이면 `NULL`이다.

#### `performance` 구조 (8/31 확정)

쿠폰 앱 관리자 사이트 접근을 허용받았고, 협업 전용 쿠폰도 만들 수 있다.

```json
{
  "insta_reach": 0,
  "insta_save": 0,
  "stamp_count": 0,
  "coupon_issued": 0,
  "coupon_used": 0,
  "revisit_within_2w": 0,
  "coupon_id": "협업 전용 쿠폰 식별자"
}
```

> **`coupon_id`가 있어야 이 협업의 효과를 가릴 수 있다.** 기존 웰컴 쿠폰과 섞이면 어느 쪽으로 온 손님인지 구분되지 않는다.

> **`revisit_within_2w`는 개인 단위 이력이 필요하다.** 집계된 숫자로는 *"협업일에 온 손님 중 몇 명이 2주 안에 다시 왔나"*를 셀 수 없다. 이름·연락처는 필요 없고 같은 사람인지만 구분되면 된다.

> **few-shot 회전**: `status='adopted'` 중 `rubric_score` 평균이 높은 **최근 3건**을 `fewshot.yaml`에 자동 반영한다.
> **제약 축적**: `status='rejected'`의 `reject_reason`을 사람이 검토해 `constraints.yaml`에 긍정형으로 추가한다. (자동화하지 않음)
> 다만 실증 협업이 1건이라 **회전할 사례가 쌓이지 않는다.** 기존 협업 3건에서 뽑은 규칙(1-5)이 사실상 전부일 가능성이 높다.

## 3. 추천 엔진 — 스코어링

### 3-1. 후보 선정

```
1. nearby_stores에서 바틀링 좌표 기준 반경 1,000m 이내 조회
2. 업종 필터: 음식점업 · 제과업 · 카페 · 소매(식품) 만 유지
3. 프랜차이즈 추정 제외 (동일 상호가 서울시 내 5개 이상)
4. 남은 후보에 대해 3-2 점수 산출
```

### 3-1-1. 데이터 단위가 세 종류로 갈린다

바틀링이 주요상권 82곳에 미포함되어(2-4) 데이터 단위가 통일되지 않는다. **다만 각 항목이 답하는 질문이 달라 정합 문제는 발생하지 않는다.**

| 단위 | 데이터 | 쓰이는 곳 |
|---|---|---|
| **행정동** (자양3동) | 추정매출 · 상권변화지표 | `S_timing` · `S_trend` · 컨텍스트 빌더 |
| **좌표 반경** | 상가정보 · 문화행사 | `S_distance` · 인근 행사 |
| **지점** (POI093/POI025) | 실시간 인구·상권·날씨 | 컨텍스트 빌더 |

```
S_distance    좌표 반경
S_complement  업종 매핑 (단위 무관)
S_timing      행정동
S_trend       행정동
```

#### 결합 연산은 존재한다 — 정규화로 해소된다

추천 엔진은 네 항목을 가중 합산하므로 **서로 다른 단위의 값을 더한다.** 원본 값은 이렇게 제각각이다.

| 항목 | 원본 | 단위 |
|---|---|---|
| 거리 | 320 | 미터 |
| 업종 상보성 | 제과·디저트 | 문자열 |
| 시간대 | 0.31 | 비중 |
| 상권변화 | 3등급 | 등급 |

**각 항목을 0～1로 정규화하면 단위가 사라진다.** 떡붕(320m, 제과·디저트) 기준 계산 예시다.

```
S_distance    1 - (320 / 1000)        = 0.68
S_complement  제과·디저트 → 매핑표      = 1.00
S_timing      14-17·17-21·21-24 합     = 0.72
S_trend       4등급 중 3번째 → 0.67    = 0.67

Score = 0.30×0.68 + 0.30×1.00 + 0.25×0.72 + 0.15×0.67
      = 0.204 + 0.300 + 0.180 + 0.101
      = 0.785
```

가중치 합이 1이므로 최종 점수도 0～1에 놓이며, 다른 후보와 직접 비교할 수 있다.

**정규화하지 않으면** 단위가 큰 항목이 점수를 지배한다.

```
0.30 × 320  = 96.0     ← 거리가 나머지를 압도
0.25 × 0.72 =  0.18
```

가중치가 무의미해지므로 **정규화는 선택이 아니라 전제**다.

#### 해상도 차이는 의도된 것이다

`S_distance`는 점포별로 다르나, 나머지 세 항목은 **같은 업종·같은 행정동이면 동일한 값**이다.

| | 떡붕 (320m) | A카페 (850m) |
|---|---|---|
| `S_distance` | 0.68 | 0.15 |
| `S_timing` | 0.72 | 0.72 |

`S_timing`이 측정하려는 것은 *"이 점포가 저녁에 잘 팔리는가"*가 아니라 **"이 업종이 저녁에 팔리는 업종인가"**다. 바틀링이 15시 개점이므로 저녁형 업종과의 협업이 유리하다는 판단에 쓰이며, 이는 업종 단위로 보는 것이 옳다.

개별 점포의 시간대별 매출은 공공데이터로 취득할 수 없다.

→ 구조상 **「업종 점수 + 거리 보정」**에 가깝다.

**실질적 쟁점은 지역 차이이며, 아래에서 다룬다.**

#### [미확정] 행정동 통계를 반경 전체에 적용하는 문제

`nearby_stores`는 반경 1km 기준이라 **성동구 성수동 점포가 포함**된다. 자양3동 통계를 성수동 점포에 적용하게 된다.

**해결 방향** — V8 응답에 `adongNm`(행정동명)이 있으므로, 점포별 소속 행정동의 통계를 적용할 수 있다. 다만 반경 1km에 걸리는 행정동을 모두 수집해야 한다.

**T15(추천 엔진) 구현 시 결정한다.** 반경 내 행정동이 2～3개면 전부 수집하고, 그보다 많으면 자양3동 통계를 일괄 적용하되 한계로 기록한다.

### 3-2. 점수 산출식

> **2026-09-03 재작성.** 협업 형태를 완제품 매입으로 한정하면서(기획서 6-1) `S_timing`이 무의미해졌다. `S_trend`는 데이터가 없다. **네 항목이 둘로 줄었다.**

```
Score = 0.50·S_distance + 0.50·S_complement
```

| 항목 | 가중 | 산출 방법 | 범위 |
|---|---|---|---|
| `S_distance` | 0.50 | `1 - (distance_m / 1000)` | 0～1 |
| `S_complement` | 0.50 | 업종 상보성 매핑표 (3-3) | 0～1 |

> **가중치는 임의 설정값이다.** 실제 데이터로 상위 후보를 뽑아본 뒤 대표님 피드백으로 조정한다 (U5).

#### `S_timing`을 뺀 이유

원래 `timeband_ratio`의 `14-17`+`17-21`+`21-24` 합을 썼다. 취지는 *"바틀링이 15시 개점이니 저녁형 업종과 협업하는 것이 낫다"*였고, **협력사가 함께 장사한다는 전제**였다.

**완제품 매입에서는 그 전제가 성립하지 않는다.** 협력사는 낮에 만들어 넘기면 되므로 자기 영업시간이 바틀링과 겹칠 이유가 없다. 오히려 저녁에 바쁜 가게는 납품할 여력이 없을 수 있다.

**뒤집어 쓰는 것도 검토했으나 채택하지 않았다.** *"저녁에 안 바쁜 가게가 납품 여력이 있다"*는 논리인데, **매출이 적은 것이 여유인지 가게가 작아서인지 구분할 수 없다.** 근거 없는 방향으로 순위를 매기면 오히려 왜곡된다.

> **협업 형태에 따라 다르게 쓰는 방법도 있으나 순서가 맞지 않는다.** 형태는 협력사를 고른 뒤 정해지는데 추천은 그 전 단계다. 점수를 낼 때는 그 가게가 어떤 형태를 원하는지 모른다.

**데이터를 버리는 것이 아니다.** 컨텍스트 빌더가 이미 바틀링과 협력사 두 업종의 시간대 비중을 싣고 있다(6-3 ⑩). **협력사가 정해지고 형태를 아는 (2) 셰프가 그것을 보고 판단한다.**

```
추천 (3-2)      「누구와」  →  거리와 업종만으로 충분
(1)(2) 이후     「어떻게」  →  시간대 데이터가 여기서 쓰인다
```

#### `S_trend`를 뺀 이유

**상권변화지표-행정동 데이터가 적재되지 않았다.** V7 검증이 W2로 이월된 상태다.

**모든 후보가 똑같이 없으므로 잣대는 어긋나지 않는다.** 항목 자체를 빼면 된다.

> **빼도 큰 손실은 아닐 것으로 본다.** 가중치가 0.15로 가장 낮았고, 후보가 모두 반경 1km 안이라 상권 등급이 같을 가능성이 크다. 같은 값이면 순위를 가르지 못한다.
>
> 적재된 뒤에 더해 보고 순위가 얼마나 바뀌는지 보면, 이 항목의 값어치도 함께 판단할 수 있다.

#### 두 항목만 남은 것을 어떻게 볼 것인가

**추천 엔진이 단순해졌고, 그만큼 값어치도 줄었다.** 정직하게 적어둔다.

```
Score = 0.50·(가까운가) + 0.50·(우리와 안 겹치는 업종인가)
```

**다만 협업 상대를 고르는 데 이 둘이 핵심인 것도 사실이다.** 가깝지 않으면 완제품을 받아 오기 어렵고, 업종이 겹치면 경쟁이 된다.

**남은 문제는 변별력이다.** 반경 1km 안의 제과점이 여럿이면 `S_complement`가 모두 1.0으로 같아져 **거리만으로 순위가 정해진다.** 그러면 추천이라기보다 「가까운 순 정렬」에 가깝다.

> **이 한계를 T15 구현 후 실제 데이터로 확인한다.** 상위 10곳을 뽑아 대표님께 보여드리고, ① 이건 아닌 것 ② 빠진 것을 여쭙는다(U5). 순위가 거리순과 거의 같으면 항목을 더할지 판단한다.

**더할 수 있는 후보**

| 항목 | 근거 |
|---|---|
| **객단가 정합** | 협력사 업종 객단가가 바틀링 판매가와 너무 벌어지면 소량 납품을 꺼린다. 제과점 10,140원 / 호프 44,918원처럼 차이가 크다 |
| 상권변화지표 | V7 적재 후 |
| 블로그 언급 수 | 메뉴 검색 경로에서 이미 쓰나(3-5) 일반 추천에도 넣을 수 있다 |

**지금 넣지 않는 이유는 시간이다.** T09 적재도 되지 않았고 9/22 기획안 마감이 우선이다. 상세는 9-1 참조.

#### 매핑되지 않는 업종은 후보에서 제외한다

`nearby_stores`의 업종과 `INDUSTRY_MAP`(3-3)이 완전히 겹치지 않는다. 두 데이터의 분류 체계가 다르기 때문이다.

**매핑되지 않는 점포는 뺀다.** `S_complement`를 임의값으로 채우면 근거 없는 점수가 순위에 섞인다. 중립값 0.5를 주면 실제 상보성과 무관한 값이 되고, 0을 주면 사실상 제외이면서 목록에는 남아 혼란만 준다.

**제외한 수는 화면에 표시한다.**

```
추천 후보 12곳
※ 업종을 분류할 수 없는 23곳은 제외했습니다
```

540곳 중 상당수가 빠질 수 있다. 얼마나 빠지는지 보이지 않으면 *"왜 이 가게가 없지"* 하게 된다.

> **실제로 얼마나 겹치는지는 T09 적재 후에 알 수 있다.** 겹치는 업종이 너무 적으면 이 방침을 다시 봐야 한다. 후보가 몇 곳 안 남으면 추천 자체가 무의미해진다.

### 3-3. 업종 상보성 매핑

> **2026-09-03 갱신.** `sales_profile` 적재로 실제 업종명이 확인되었다.

바틀링(주류 판매, 안주 취약)을 기준으로 한 상보성 점수.

| 상대 업종 | 점수 | `sales_profile.industry_name` | 근거 |
|---|---|---|---|
| 제과·디저트 (붕어빵, 떡, 베이커리) | 1.0 | `제과점` | 기존 협업 실적 있음, 완제품 매입 용이 |
| 피자·튀김·그릴 | 0.9 | **`치킨전문점`** | 맥주 페어링 적합. **피자 전용 업종 없음** |
| 분식·스낵 | 0.8 | `분식전문점` | 간편 조합 |
| 카페 | 0.6 | `커피-음료` | 논알콜 라인 연계 |
| 한식·중식 (좌석 중심) | 0.4 | `한식음식점` `중식음식점` | 테이크아웃 전환 난이도 |
| 주류 판매점 | 0.1 | `호프-간이주점` | 직접 경쟁 |

**두 출처의 업종명이 다르다.** 협력사 분류(`partners.category`)는 사람이 고르는 값이고, 매출 데이터(`sales_profile.industry_name`)는 공공데이터의 서비스 업종명이다. 매핑은 `context/builder.py`의 `INDUSTRY_MAP`에 있다.

> **자양3동에 피자 전용 업종이 없다.** 44개 업종을 확인했으나 `피자전문점`이 없어 `치킨전문점`으로 대응한다. 「피자·튀김·그릴」이라는 묶음 자체가 그것을 감안한 이름이다.
>
> T14 테스트셋의 협력사 유형 4종을 정할 때도 이 점을 반영한다. 피자 유형 케이스는 `치킨전문점` 매출 데이터로 돌아간다.

> **`S_complement`는 매핑표 없이도 계산된다.** `partners.category`만 있으면 되고 `sales_profile`은 필요 없다. 반면 `S_timing`은 매출 데이터가 있어야 하므로, 매핑이 실패하면 그 항목을 뺀 나머지로 점수를 낸다.

**매핑에 없는 업종은 후보에서 제외한다** (3-2). `S_complement`를 임의값으로 채우면 잣대가 달라진다. 중립값 0.5를 주면 근거 없는 점수가 순위에 섞이고, 0을 주면 사실상 제외이면서 목록에는 남아 혼란만 준다.

**제외된 수는 화면에 표시한다.** 얼마나 빠졌는지 보이지 않으면 대표님이 아는 가게가 없을 때 이유를 알 수 없다.

### 3-5. 메뉴 검색 경로 (2차 방문 요구)

대표님이 **유행하는 메뉴 이름을 넣으면** 그 메뉴를 다루는 가게를 찾아 후보로 올린다. 추천받기와 다른 경로이며, 화면은 4-3의 경로 C다.

```
메뉴명 입력  →  관련 업종 점포 추림  →  블로그 언급 수 조회  →  후보 목록
```

#### 후보 선정

3-1의 필터를 그대로 쓰되 **업종을 더 좁힌다.** 메뉴에 따라 관련 업종이 다르므로 매핑이 필요하다.

| 메뉴 성격 | 대상 업종 |
|---|---|
| 디저트·빵류 | `제과점` `커피-음료` |
| 음료 | `커피-음료` |
| 튀김·그릴 | `치킨전문점` `패스트푸드점` |
| 분식 | `분식전문점` |

**메뉴명에서 업종을 자동으로 가리지 않는다.** *"두바이 초콜릿"*이 제과인지 카페인지 코드가 판단할 근거가 없다. **대표님이 업종을 함께 고르게 한다** — `multiselect`로 두고 기본값은 전체다.

#### 취급 여부 확인

`nearby_stores`에 메뉴 정보가 없으므로 **간접 확인**한다.

```
네이버 블로그 검색 API — "{상호} {메뉴명}"
        ↓
결과 수를 그대로 표시  (판다고 단정하지 않음)
```

| 표시 | 뜻 |
|---|---|
| 관련 언급 12건 | 블로그에 언급이 있다 |
| 관련 언급 0건 | 확인되지 않음. **안 판다는 뜻은 아니다** |

**언급 수로 후보를 지우지 않는다.** 작은 가게는 언급 자체가 적다. 0건인 곳은 목록에서 빼는 대신 **접어서 보여준다**(아래 참조).

> **메뉴 자동 수집은 채택하지 않았다 (9/3).** 공식 API는 메뉴를 제공하지 않고, 비공식 경로는 첫 요청부터 캡차가 걸린다. 근거는 `tests/probe_naver_menu.py`와 「유행메뉴 검색 설계」 참조.

#### 순위와 표시

**언급이 확인된 곳을 먼저 보이고, 나머지는 접어둔다.**

```
관련 언급이 확인된 곳  3곳

  블랙스미스 (커피-음료, 도보 7분)
    관련 언급 12건 · 추천 점수 0.81
    [네이버 지도에서 메뉴 보기 →]

  ○○베이커리 (제과점, 도보 8분)
    관련 언급 3건 · 추천 점수 0.65
    [네이버 지도에서 메뉴 보기 →]

[ 언급이 확인되지 않은 곳 8곳 더 보기 ▾ ]
```

**0건인 후보를 목록에서 지우지 않는다.** 작은 가게는 블로그에 이름이 오르지 않는다. 지우면 **가까운 제과점이 통째로 사라져** 검색 결과가 비어버릴 수 있다.

**접어두면 두 가지가 함께 해결된다.**

| | |
|---|---|
| **필터가 작동한다** | 언급 있는 곳이 먼저 보여 메뉴 검색의 뜻이 산다 |
| **걸러진 것이 보인다** | 8곳이 그냥 사라지면 *"왜 이 가게가 없지"* 싶으시다 |

> **임계값을 두지 않는다.** *"3건 이상만"* 같은 기준을 정할 근거가 없다. 검색어에 따라 결과가 크게 달라진다 — *"두바이 초콜릿"*은 언급이 많겠지만 *"흑임자 크림"*은 0건일 수 있다. **0건이냐 아니냐로만 나눈다.**

**펼친 목록에는 안내를 붙인다.**

```
※ 블로그에 언급이 없어도 취급할 수 있습니다. 지도에서 확인해 보세요.
```

**각 묶음 안의 정렬은 선택할 수 있다.**

| 기준 | 쓰임 |
|---|---|
| **관련 언급 수** | 그 메뉴를 확실히 다루는 곳 우선 (기본값) |
| 추천 점수 | 협업 실행 가능성 우선 |

메뉴로 찾는 경로이므로 기본값은 언급 수다. 그 메뉴를 하려고 검색한 것이기 때문이다.

**추천 점수와 언급 수를 하나로 합치지 않는다.** 성격이 다르다. 언급이 많아도 거리가 멀면 협업이 어렵고, 언급이 없어도 가까운 제과점이면 해볼 만하다. **어느 쪽을 중히 볼지는 대표님이 정하실 문제다.**

#### 출력

3-4에 두 필드를 더한다.

```json
{
  ...3-4 필드...,
  "mention_count": 12,
  "mention_query": "블랙스미스 두바이 초콜릿"
}
```

`mention_query`를 남기는 것은 **검색어가 엉뚱했을 때 확인하기 위해서**다. 상호에 지점명이 붙어 있으면(`블랙스미스 자양점`) 검색 결과가 0건이 될 수 있다.

#### 확인이 필요한 것 (U17)

**「가게명 + 메뉴명」 검색이 실제로 유효한지 아직 확인하지 않았다.**

| 확인 | 방법 |
|---|---|
| 결과가 그 가게에 관한 것인가 | 블랙스미스·아데프로 실제 검색 |
| 상호가 흔하면 어떻게 되는가 | 동명 가게가 섞이는지 |
| 일일 호출 제한 | API 문서 확인 |

**검색 결과가 쓸 만하지 않으면 언급 수를 빼고 지도 링크만 제공**하는 형태로 축소한다. 그래도 「그 메뉴를 다룰 만한 업종의 가까운 가게 목록」은 나온다.

### 4-2. 기획안 생성 (핵심 화면)

**상단 — 입력**

```
[협력사 선택 ▼]   [ ● 날짜 지정  ○ 희망 기간 ]   [ 기획안 생성 ]
                   [ 2026-10-09 ]
```

**날짜 입력이 두 방식이 되었다 (2차 방문 요구).**

| 방식 | 입력 | 쓰임 |
|---|---|---|
| **날짜 지정** | `date_input` 단일 | 실행일이 정해진 경우 |
| **희망 기간** | `date_input` 2개 (시작·끝) | *"9월 중 아무 때나"* — AI가 후보 날짜를 제안 |

> **희망 기간 방식은 체인 구조에 영향을 준다.** 지금 (1)은 `target_date` 하나를 받아 그 날짜만 분석한다. 여러 날짜를 비교하려면 (1) 앞에 날짜 선정 단계를 두거나 (1)이 복수 날짜를 처리해야 한다. 상세는 9-1 M1.
>
> **1차 구현은 단순하게 한다.** 기간 안의 각 요일에 대해 (1)만 돌려 비교하고, 가장 유리한 날짜를 골라 그 뒤 단계를 진행한다. 요일이 7개이므로 (1)을 최대 7회 호출한다(약 30초). 행사가 있는 날은 우선 고려한다.

**생성 중 — 진행 표시 (필수)**

```python
with st.status("기획안 생성 중...", expanded=True) as s:
    st.write("(1) 상권 분석 중...")
    st.write("(2) 협업 메뉴 개발 중...")
    st.write("(3) 홍보 기획 중...")
    st.write("(4) 최종 검토 중...")
    s.update(label="기획안 완성. 메뉴 이미지 생성 중...", state="running")
    st.write("메뉴 이미지 생성 중...")
    s.update(label="완료", state="complete")
```

> 실측 4단계 합계 **약 19～24초**(6-2-3, 8/29 재측정). 동기 방식으로 충분하다.
> 단계별 표시는 유지한다 — 20초도 무반응이면 길게 느껴지고, 어느 단계에서 실패했는지 보여야 한다.

**[중요] 이미지 생성은 텍스트 완성 후에 한다.** 텍스트 기획안을 먼저 화면에 띄우고 이미지는 뒤에 채운다. 이미지 생성이 실패하거나 느려도 기획안은 볼 수 있어야 한다(1-2 ④).

**하단 — 결과**

- `st.tabs(["1순위", "2순위", "3순위"])` — **세 탭 모두 동일한 완성도**로 표시한다
- 각 탭 구성:
  - 메뉴명(헤더) → **메뉴 이미지** → **선정/후순위 사유**
  - 페어링 맥주(강조 배지, 원/ml 병기) → 구성·재료·장비 표
  - **조리 주체** (완제품 매입 / 반제품 / 바틀링 조리)
  - 원가·판매가 → **분배 방식과 제안 매입가**
  - 이벤트 → **홍보 일정 표** → 홍보문구(복사 버튼)
  - 준비물·소요기간 → **추천 근거**(expander) → 리스크
- **1순위 탭에만 협업 제안서 영역**을 둔다 (아래 참조)
- 제외된 안이 있으면 별도 `st.warning`으로 제외 사유 표시
- `st.expander("검수 결과")` — 안별 체크리스트 6항목 O/-
- 하단 고정: **[이 안으로 채택] [전체 폐기]**. 폐기 시 사유 입력 필수(`text_area`)
- 채택 시 → 어느 안을 채택했는지 `plans.adopted_option`에 기록 + 실행일·매출 입력란 노출

### 4-3. 파트너 추천 — 세 경로 병행

대표님이 **이미 협업할 가게를 정해둔 경우**가 실제로는 더 많다. 추천 결과에서만 고르게 하면 시스템을 우회하게 되므로, 직접 지정 경로를 같은 화면에 둔다.

**2차 방문으로 메뉴 검색 경로가 추가되었다.**

```
┌─ A: 추천받기 ─────┐ ┌─ B: 직접 지정 ────┐ ┌─ C: 메뉴로 찾기 ──┐
│ 필터 → 순위 → 선택 │ │ 상호 검색 또는 입력│ │ 메뉴명 → 후보 목록│
└─────────┬─────────┘ └─────────┬─────────┘ └─────────┬─────────┘
          └─────────────────────┴─────────────────────┘
                                ▼
                     partners 등록 여부 확인
                                ▼
                [등록됨] → 기획안 생성으로
                [미등록] → 초대 링크 생성 → 협력사 입력 대기
```

**경로 A — 추천받기**
- 좌: 필터 (`slider` 반경, `multiselect` 업종)
- 우: `st.dataframe` — 순위 / 상호 / 업종 / 거리 / 점수
- 행 선택 → 상세 패널에 항목별 점수 막대 + `reason` 문장
- 지도는 `st.map`으로 최소 구현

**경로 B — 직접 지정**
- `st.text_input`으로 상호 검색 → `nearby_stores`에서 부분 일치 조회
- 검색 결과에 없으면 **직접 입력 폼** (상호 / 업종 / 주소) — 반경 1km 밖이거나 데이터에 없는 가게 대응
- **추천 점수를 계산하지 않는다.** 상대가 이미 정해져 있어 비교 대상이 없고, 반경 밖이면 점수를 낼 근거 자체가 없다. (4)에 넘기는 `rec_reason`에 *"대표님 직접 지정"*을 명시한다

**경로 C — 메뉴로 찾기 (신규)**
- `st.text_input`으로 메뉴명 입력 + `multiselect`로 대상 업종 선택
- **언급이 확인된 곳을 먼저 보이고, 0건인 곳은 `st.expander`로 접는다**
- 각 후보에 **블로그 언급 수** + **추천 점수** + **네이버 지도 링크** 표시

```
관련 언급이 확인된 곳  3곳

  블랙스미스 (커피-음료, 도보 7분)
    관련 언급 12건 · 추천 점수 0.81
    [네이버 지도에서 메뉴 보기 →]

[ 언급이 확인되지 않은 곳 8곳 더 보기 ▾ ]
  ※ 블로그에 언급이 없어도 취급할 수 있습니다. 지도에서 확인해 보세요.
```

> **0건인 후보를 지우지 않고 접는다.** 작은 가게는 블로그에 이름이 오르지 않아, 지우면 가까운 제과점이 통째로 사라질 수 있다. 접어두면 필터가 작동하면서도 무엇이 걸러졌는지 보인다 (3-5).

> **메뉴 자동 수집은 채택하지 않았다 (9/3).** 네이버가 자동 접근을 캡차로 막아 서버에서 얻을 수 없다. 근거와 상세는 「유행메뉴 검색 설계」 참조.

> 선택한 메뉴명은 `plans.trend_menu`에 기록하고 (2) 셰프에 전달한다. **세 안 모두 그 메뉴를 축으로 삼는다**(1-2 ⑤).

**공통 — 이후 처리**
- `partners`에 이미 있으면 → 바로 4-2로
- 없으면 → `invite_code` 발급 후 초대 링크 표시 (복사 버튼)
- 링크를 협력사에 전달 → 입력 완료 시 대표님 화면에 알림

> `plans` 테이블에 `partner_source` 컬럼(`recommended` | `manual` | `menu_search`)을 두어 경로별 결과 품질을 나중에 비교한다. 추천으로 고른 협업과 직접 지정한 협업 중 어느 쪽이 잘 됐는지를 보면 추천 엔진의 값어치를 판단할 수 있다.

#### A3 구현

```python
import re

def check_numbers(basis: dict, context_text: str) -> dict:
    """추천_근거의 수치가 컨텍스트에 실재하는지 본다."""
    nums = re.findall(r'\d[\d,\.]*', json.dumps(basis, ensure_ascii=False))
    ctx = context_text.replace(',', '')
    missing = [n for n in set(nums)
               if len(n) >= 2 and n.replace(',', '') not in ctx]
    return {"passed": not missing, "missing": missing}
```

**`추천_근거`만 검사한다.** 판매가·매입가·수량처럼 새로 만드는 숫자는 컨텍스트에 없는 것이 정상이다. 전체를 대조하면 오탐만 쌓인다.

#### 이미 만들어 둔 검사를 활용한다

`tests/test_p1.py`～`test_p4.py`에 **검사 40여 종이 있다.** T17은 그중 **자동 재생성이 필요한 것만 골라 체인에 붙이는 작업**이다. 새로 짜지 않는다.

|---|---|
| `test_p1` | 영업시간 위반, 근거 건수 누락, 지어낸 등급 인용 |

### 5-3. 3층 — 채택률

`adopted / generated`. 프롬프트 버전별로 집계한다.

### 5-4. 퍼널 분석 — 두 축

멘토링에서 제안받은 항목. 성격이 다른 두 퍼널을 각각 구성한다.

#### 퍼널 A — 협업 이벤트 성과 (외부 데이터)

```
인스타 도달 ─→ 저장·공유 ─→ 신규 적립 ─→ 재방문 적립
  (노출)        (관심)       (획득)       (유지)
```

| 단계 | 지표 | 출처 |
|---|---|---|
| 노출 | 게시물 도달 수 | 인스타 인사이트 캡처 |
| 관심 | 저장·공유·프로필 방문 | 인스타 인사이트 |
| 참고 | 뚝섬 유동인구 | **실시간 도시데이터** (대리 지표) |
| 획득 | 신규 적립 건수 | 쿠폰 앱 대시보드 |
| **유지** | **재방문 적립 비율** | 쿠폰 앱 대시보드 |

**마지막 단계가 핵심이다.** 협업으로 온 손님이 다시 오는가 — 대표님 과제가 "한강 상권 비수기 극복"이므로, 일회성 화제로 끝나는지 단골이 되는지가 사업 목적과 직결된다.

**한계**
- "매장 방문" 단계는 측정 수단이 없다 (입장객 카운트 불가)
- 쿠폰 앱 이용률이 100%가 아니므로 절대 수치는 왜곡된다 → **상대 비교로만 해석**
- 표본이 협업 1～3건이므로 통계적 유의성은 주장하지 않는다

#### 퍼널 B — AI PM 시스템 (내부 데이터) [중요]

```
추천 노출 ─→ 파트너 선택 ─→ 기획안 생성 ─→ 채택 ─→ 실행 ─→ 성과 기록
  10곳         1곳          3안         1안     ?건     ?건
```

| 단계 | 지표 | 산출 |
|---|---|---|
| 노출 | 추천 후보 표시 수 | 화면 로그 |
| 선택 | 파트너 확정 건수 | `plans.partner_id` |
| 생성 | 기획안 생성 건수 | `plans` 행 수 |
| **채택** | `adopted / generated` | `plans.status` |
| 실행 | `executed / adopted` | `plans.executed_at` |
| 기록 | 성과 입력 완료 건수 | `plans.performance` |

**퍼널 B를 주 지표로 삼는다.** 이유:

1. **데이터가 전부 내부에 있다.** 대표님께 추가 요청이 필요 없다
2. 매출이 평가 기준이 아니라면, 심사에서 볼 것은 *"AI PM이 실제로 작동했는가"*이며 퍼널 B가 그것을 직접 보여준다
3. **어느 단계에서 새는지가 곧 개선 방향이다** — 생성은 많은데 채택이 없으면 프롬프트 품질 문제, 채택은 되는데 실행이 안 되면 현실성 문제
4. 추천 경로(`partner_source='recommended'`)와 직접 지정(`manual`)을 분리해 비교할 수 있다

**최종보고서 서술 예시**

> 기획안 12건 생성 → 5건 채택(42%) → 3건 실행(60%) → 실행 3건 중 2건에서 재방문 증가 확인

### 6-2-1. V1·V2·V3 검증 결과 (2026-08-22, 완료)

**결론: 통합 API(`citydata`) 단독 사용으로 확정한다.**

```
GET http://openapi.seoul.go.kr:8088/{KEY}/json/citydata/1/5/{장소명}
```

**대조 방법** — 개별 API 응답(V1·V2)과 통합 API 응답을 필드 경로 및 값 단위로 전수 비교했다. 리스트는 첫 원소가 아니라 전 원소를 포함했다.

| 비교 대상 | 결과 |
|---|---|
| 인구 데이터 블록 | **완전 일치** (파이썬 객체 `==` 비교 True) |
| 상권 데이터 블록 | **완전 일치** |
| `CMRCL_RSB` 5개 항목 | 완전 일치 |
| `FCST_PPLTN` 12개 항목 | 완전 일치 |
| 개별에만 있는 필드 | **없음** |

래퍼(최상위) 구조만 다르다. 개별 상권 API의 `AREA_NM`·`AREA_CD`는 통합에서 `CITYDATA` 하위로 이동했고, `list_total_count`는 의미가 다르다(개별=`CMRCL_RSB` 개수, 통합=조회 장소 수). 정보 손실은 없다.

**통합 API를 채택하는 근거 4가지**

| # | 근거 |
|---|---|
| 1 | **호출 횟수 절감** — 4회(2지점 × 2API) → **2회** |
| 2 | **날씨 데이터 확보** — `WEATHER_STTS`가 함께 온다. 기온·습도·강수형태·강수메시지. **한강 상권에서 날씨는 결정적 변수**이므로 이득이 크다 |
| 3 | **응답 형식 통일** — 개별 API는 결과 코드 키가 서로 다르다(`RESULT.CODE` vs `resultCode`). 통합만 쓰면 파싱 분기가 사라진다 |
| 4 | **에러 처리 단순화** — 뚝섬한강공원 상권을 개별 호출하면 `ERROR-500`이지만, 통합에서는 정상 응답에 해당 필드만 `None`이다 |

추가로 `EVENT_STTS`(행사), `ROAD_TRAFFIC_STTS`(교통), `PRK_STTS`(주차) 등도 함께 오지만 현재는 사용하지 않는다. `raw` 컬럼에 `CITYDATA` 전체를 보존하므로 나중에 필요하면 파싱만 추가하면 된다.

**확인된 응답 특성**

| 항목 | 내용 | 대응 |
|---|---|---|
| 숫자가 문자열 | `"3000"` 형태 | `_int()` / `_float()` 헬퍼로 변환 |
| 혼잡도 자연어 문장 | `AREA_CONGEST_MSG`에 완성 문장 제공 | `congestion_msg`에 보존. 컨텍스트 빌더에서 참고 인용 |
| 시각 필드 | `PPLTN_TIME` (5분 단위 갱신) | `collected_at`에 사용. 30분 주기 수집에서 중복 없음 |
| 지점 코드 | 뚝섬한강공원 `POI093` / 뚝섬역 `POI025` | 호출은 한글명으로 한다 |

**남은 한계** — 위 검증은 **한 시점 스냅샷 1건** 기준이다. 시간대·요일에 따라 필드 구성이 달라질 가능성은 배제하지 못한다. `raw`에 원본을 보존하는 이유다.

#### [주의] 프롬프트 렌더링에 `str.format()`을 쓰지 않는다

프롬프트 본문에 출력 스키마용 JSON 중괄호가 포함되어 있어, `format()`이 이를 치환 변수로 오인한다.

```
[출력 스키마]
{"공략_시간대": [...], "타겟_고객층": {...}}
     ↑ format() 이 변수명으로 읽어 KeyError 발생
```

**전달된 변수명만 골라 문자열 치환**하는 방식으로 대체했다.

```python
for k, v in vars_.items():
    out = out.replace("{" + k + "}", str(v))
```

추가로 YAML의 `inputs` 목록과 대조해 **치환되지 않은 변수가 남으면 예외를 낸다.** 변수명 오타·전달 누락을 조기에 잡기 위함이다.

조합 데이터가 없으므로 축별 순위로 서술한다. 정보 손실은 있으나 각 축의 순위는 그대로 파악할 수 있다.

#### 8/25 규격을 다시 고친 이유

8/25 규격은 **코드가 판정하고 결과만 문장으로 내놓는** 구조였다. `'여유' (6건 중 5건)`처럼 대표 등급을 세우고, 최고·최저 두 구간만 보여주고, *"시간대에 따른 차이 없음"* 같은 결론을 코드가 서술했다.

그 방식의 문제는 세 가지였다.

**판정 근거가 사라진다.** 대표 등급만 보이면 LLM은 그 판정이 6건 중 5건인지 2건 중 2건인지 알 수 없다. 근거의 크기를 모른 채 결론만 받는다.

**나머지 구간이 버려진다.** 최고·최저 둘만 보여주면 6구간 중 4구간의 분포가 출력에 나오지 않는다.

**임계값에 근거가 없다.** `표본 3배 차이`, `SPREAD_MAX = 5` 같은 상수를 두었으나 왜 3배이고 왜 5인지 설명할 수 없었다.

그래서 **전 구간 분포를 그대로 나열하고, 코드의 판정은 `(참고)` 줄로 분리**하는 방식으로 바꿨다. 집계의 정확성은 코드가 보장하되(D3), 해석은 LLM이 근거를 직접 보고 하도록 한다.

#### 출력 원칙

**① 관측 사실을 그대로 제시한다**

표본이 적다는 이유로 항목을 생략하거나 다른 값으로 대체하지 않는다. 건수를 밝히고 해석은 LLM에 맡긴다.

초기에는 *"같은 요일 표본이 6건 미만이면 전체 평균으로 대체"* 같은 임계값을 두었으나 폐기했다. 전체 수집 기간이 4주 남짓이라 어떤 기준을 두어도 근거가 약하고, **조건을 넘었다는 이유로 "금요일 피크는 19시" 같은 단정을 만들면 오히려 왜곡된다.**

**② 대표 등급을 세우지 않는다**

4단계 분포를 항상 그대로 적는다. **0건 등급도 생략하지 않는다.** 언급이 없으면 관측이 0인지 항목 자체가 누락된 것인지 구분되지 않아 오해를 부른다.

```
17-21시 관측 5건 — '붐빔' 0 / '약간 붐빔' 0 / '보통' 2 / '여유' 3
```

8/25 규격의 「최빈값 과반」 판정은 폐기했다. 과반이라는 기준 자체에 근거가 없고, 분포를 보이면 LLM이 스스로 판단할 수 있다.

**③ 전 구간을 나열한다**

관측된 시간대 구간을 모두 적는다. 최고·최저 둘만 보이면 나머지 구간의 분포가 버려진다.

**④ 코드의 판정은 `(참고)`로 분리한다**

구간 간 순위는 코드가 계산하되 결론이 아니라 참고 정보로 제시하고, **판정에 쓰인 관측 수를 함께 적는다.**

```
(참고) 구간 평균 기준 가장 혼잡 14-17시(3건) / 가장 한산 00-06시(6건)
```

3건 평균과 17건 평균을 같은 자격으로 비교할 수 없다. 건수를 병기해 LLM이 신뢰도를 가늠하게 한다.

**⑤ 내부 계산값을 노출하지 않는다**

`평균 2.6/4` 같은 표기는 LLM이 해석할 맥락이 없어 판단에 쓰이지 못한다. 등급 이름으로 제시한다.

**⑥ 인구·상권 모두 대상 시점과 같은 요일만 집계한다**

요일을 섞으면 금요일 저녁과 화요일 저녁의 차이가 뭉개진다. 섹션 제목에 `※ OO요일 관측분`으로 집계 범위를 밝힌다.

**⑦ 상권은 같은 `CMRCL_TIME`을 한 번만 센다**

인구는 5분, 상권은 10분 주기로 갱신되는데(서울시 공식) 수집이 5분 간격이라 상권만 2배로 중복된다. 새벽에는 결제가 없어 90～240분간 갱신되지 않아 최대 6.5배가 된다.

거르지 않으면 2회 관측이 9건으로 집계되어 **근거 건수를 함께 밝히는 이 규격 자체가 무의미해진다.** 수집 간격이 30분 이상이던 8/27 이전 데이터에는 중복이 없다.

**⑧ 방문객 구성은 혼잡도와 같은 6구간으로 쪼갠다**

요일 전체로 묶으면 비상주 비율이 `19～65%`처럼 벌어져 대표값이 아무것도 말하지 못한다. 새벽과 저녁이 한 값이 되기 때문이다.

영업시간(15시 이후)만 남기지 않는다. 재료 납품은 시간대가 무관하고 콘텐츠 촬영은 낮에 하므로, **어느 구간이 쓸모 있는지는 코드가 아니라 LLM이 판단한다.**

비율은 평균을 쓴다. 연령대마다 중앙값을 따로 내면 서로 다른 회차의 값이 섞여 합이 61%나 101%가 된다. 각 회차의 합이 100이므로 평균의 합은 100이 된다.

**⑨ 인구 비중과 소비 비중을 구분한다**

`ppltn_rates`는 그곳에 있던 사람, `cmrcl_rates`는 결제한 사람이다. 뚝섬역 40대는 인구 16% / 소비 31%로 엇갈린다. 한쪽만 보면 이 차이가 드러나지 않는다.

같은 구간이라도 인구와 소비의 근거 수가 다르다. 인구는 수집한 횟수만큼 쌓이지만, 상권은 갱신 주기가 길어 중복을 걷어내면 그보다 줄어든다(원칙 ⑦). 6번 수집한 구간의 소비 비율이 실제로는 3개 시점의 값일 수 있다.

그래서 `(소비는 6건 중 상권 갱신 3건 기준)`으로 두 수를 나란히 적는다. `(결제 N건)`은 그 시점들의 실제 결제 규모다. 결제가 적으면 몇 사람이 비율 전체를 좌우한다.

**⑩ 분기 매출은 바틀링·협력사 업종만 싣는다**

업종을 지정하지 않으면 44종 중 앞의 셋이 순서대로 잘려 협업과 무관한 업종이 실린다. `BOTTLING_INDUSTRY`(호프-간이주점)와 `INDUSTRY_MAP`으로 옮긴 협력사 업종 둘만 싣는다.

매출·건수는 분기를 모두 적고 비중은 최신 분기만 적는다. 금액에서 추세가 드러나므로 코드가 증감을 판정할 필요가 없고, 비중은 분기별 차이가 작다(21-24시가 다섯 분기 내내 57～62%).

**모든 비율은 매출 금액 기준이며 방문 인원 비율이 아니다.** 성별·연령은 미상 결제가 3～6% 있어 합이 100%가 되지 않는다.

**⑪ 없는 항목은 "데이터 없음"으로 명시한다**

생략하면 LLM이 지어낸다. 미적재 테이블은 예외를 던지지 않고 `데이터 없음 (적재 전)`을 반환한다.

**⑫ 날씨는 관측 시각과 함께 적는다**

한강 상권에서 강수 여부는 방문객 수를 좌우한다. 다만 이 값은 **대상 시점의 예보가 아니라 최근 관측치**이므로 그 사실을 밝힌다 (U12).

**⑬ 상권 지표는 뚝섬역 기준임을 명시한다**

뚝섬한강공원은 상권 데이터가 없다 (2-3).

**⑭ 생성 문자열을 `plans.context_snapshot`에 저장한다**

재현 및 A3 수치 대조 검증용이다.

#### 조회

`raw` 컬럼을 통째로 받지 않는다. 행당 수십 KB라 280행에 10 MB를 넘어 `statement timeout`(57014)이 실제로 발생했다.

| 방식 | 소요 | 크기 |
|---|---|---|
| `select("*")` | 1.41초 | 10,535 KB |
| 필요 컬럼만 | **0.04초** | **142 KB** |

`raw`에서 필요한 것은 `CMRCL_TIME` 하나뿐이므로 PostgREST의 JSONB 문법으로 그것만 뽑는다. `LIVE_CMRCL_STTS`는 객체로 저장되어 있어 배열 인덱스(`->0`)를 쓰지 않는다.

```
cmrcl_time:raw->LIVE_CMRCL_STTS->>CMRCL_TIME
```

`limit`도 명시한다. 없으면 PostgREST 기본 상한(1,000행)에 걸려 오래된 행이 예외 없이 조용히 잘린다.

#### 제외한 것

**서울시 제공 자연어 문장(`congestion_msg`)** — 일반 시민용 안내라 자체 집계보다 정보량이 적다.

**12시간 예측(`forecast_12h`)** — 오늘 이후 12시간 예보다. 협업 기획은 며칠 뒤를 대상으로 하므로 대상 시점과 무관한 값이 붙는다. 당일 즉흥 이벤트 기능이 생기면 그때 다시 넣는다. 다만 상권 대시보드(T24b)는 "지금 상권이 이렇다"를 보이는 화면이므로 거기서는 쓸 수 있다.

**카테고리별 현재 등급** — 가장 최근 시간 기준이라 협업 시점과 무관하다.

## 8. 이관 설계 (Q7 대응)

### 8-1. 분리 원칙

| 대상 | 위치 | 비개발자 수정 가능성 |
|---|---|---|
| 프롬프트 | `prompts/*.yaml` | 관리 화면에서 편집 |
| 제약조건 | `constraints.yaml` | 관리 화면에서 추가/삭제 |
| few-shot | `fewshot.yaml` | 채택 사례 체크박스 선택 |
| 모델명·키 | 환경변수 | `.env` 한 줄 |
| 스코어링 가중치 | `config.yaml` | 관리 화면 슬라이더 |

코드에 문자열 상수로 프롬프트를 넣지 않는다.

### 8-2. 방치 내구성

사업 종료 후 6개월 방치를 가정한다.

- API 키 만료 임박 시 알림 (수집기에서 401 감지 → 대표님 카톡/이메일)
- GitHub Actions 스케줄 비활성화 방지 — 월 1회 자동 커밋 워크플로
- 수집 실패가 3회 연속이면 알림
- 데이터가 비어도 화면이 죽지 않게 (빈 상태 UI)

### 8-3. 인수인계 문서 목차

기능 설명이 아니라 **장애 대응 중심**으로 쓴다.

```
1. 이 시스템이 하는 일 (1페이지)
2. 증상별 확인 순서
   - 기획안이 안 나온다 → API 키 / 잔여 크레딧 / 로그 위치
   - 상권 정보가 옛날 것이다 → GH Actions 실행 이력
   - 결과가 이상하다 → 프롬프트 수정 방법
3. 정기 점검 (월 1회, 5분)
4. 외주 개발사 인계용 — 저장소 구조 / 배포 / 환경변수
```

### 9-1. 설계상 미해결

기능은 동작하나 구조적으로 더 나은 방법이 있을 수 있는 것들. 지금 손대지 않는 이유를 함께 적는다.

**M1 — 대상 시점이 하나로 고정된다**

체인이 `target_date` 하나만 받아 그 날짜에 대한 기획만 생성한다. 20일에 소규모 행사, 25일에 축제가 있어도 둘 중 하나만 다뤄진다.

더 근본적으로는 **날짜를 사람이 정한다.** 화면(4-2)에서 대표님이 실행 희망일을 고르는 구조인데, *"언제 하면 좋은가"*를 판단하는 것이야말로 AI PM의 역할일 수 있다.

- **2차 방문에서 요구가 나왔다.** *"날짜 지정과 희망 기간 둘 다"* (기획서 3-5 ②)
- **T45로 착수한다 (W4).** 1차 구현은 단순하게 — 기간 안의 각 요일에 (1)만 돌려 비교하고 가장 유리한 날짜를 고른다. 요일이 7개이므로 (1)을 최대 7회 호출한다 (약 30초)
- **남는 문제** — 이 방식은 요일 단위 비교다. 같은 요일의 다른 날짜(행사 유무)를 가리지 못한다. `events` 적재(T10) 후 다시 본다

**M2 — 세 안의 타겟층이 공통 축으로 고정된다**

(3) 마케터가 타겟·공략 시점·채널을 세 안에 공통으로 한 번만 쓴다(1-3, 토큰 절감). 그런데 메뉴에 따라 손님층이 갈릴 수 있다.

**협업 형태를 완제품 매입으로 좁히면서 이 문제가 커졌다.** 「접근」이 단품·세트·미니사이즈로 나뉘는데 **같은 메뉴의 변형이라 차별성이 약하다.**

**해결 방향 — 타겟을 셋으로 나누고 안을 하나씩 만든다.**

```
전   타겟 1개 → 3안 (구성 차이)
후   타겟 3개 → 각 1안
```

**데이터가 이를 뒷받침한다.** 실측 컨텍스트에서 손님층이 장소 × 시간대로 갈린다.

| 구간 | 비상주 | 특징 |
|---|---|---|
| 한강공원 17-21 | **86%** | 나들이객, 20대 |
| 뚝섬역 17-21 | 58% | 퇴근길·주민, 소비 30대 30% |
| 뚝섬역 21-24 | 39% | **매출 61%** — 심야 |

**(4)의 순위는 여전히 매길 수 있다.** 기준이 바뀔 뿐이다.

| 기준 | 타겟이 달라도 비교 가능 |
|---|---|
| 실행 가능성 · 매입가 · 준비 부담 | 가능 |
| **어느 손님이 나은가** | **불가 — 대표님 몫** |

(4)가 *"이 손님층이 낫다"*고 말하지 않고 *"이 안이 실행하기 쉽다"*고 말하면 된다. 그리고 **어느 손님을 노릴지는 대표님이 정하실 문제임을 명시**한다. 지금은 세 안이 대동소이한데 억지로 순위를 매기고 있으므로, 오히려 정직해진다.

- **9/6까지 반영을 시도한다** (T42). 되면 M2는 해결이다
- **밀리면 T18 튜닝(W4)에서 다시 본다.** 지금 구조로도 기획안은 나오므로 9/22 마감에 지장이 없다
- **비용** — (1)의 출력 구조가 바뀌고 (2)(3)(4)가 따라 바뀐다. 공통 축을 못 써 (3)의 출력이 세 배가 된다

**M3 — 축별 객단가를 낼 수 없다**

`sales_profile`의 축별 비중이 매출 금액 기준만 있다. CSV 원본에는 금액과 건수가 모두 있으나 적재 시 금액만 비중으로 변환했다.

그래서 *"어느 시간대 손님이 한 번에 더 많이 쓰는가"*를 볼 수 없다. 실측으로는 2026Q1 호프-간이주점의 21-24시가 금액 61% / 건수 55%로, **심야 손님의 객단가가 저녁보다 높다.** 협업 메뉴 가격대를 정할 때 쓰일 수 있는 정보다.

- **보류 사유** — 스키마 변경(컬럼 4개 추가)과 재적재가 필요하고, A 담당 영역이다
- **판단 시점** — W5～W7에 여유가 있을 때

**M4 — 추천 엔진이 두 항목만 쓴다**

협업 형태를 완제품 매입으로 좁히면서 `S_timing`이 무의미해졌고(3-2), `S_trend`는 데이터가 없다. **네 항목이 둘로 줄었다.**

```
Score = 0.50·S_distance + 0.50·S_complement
```

**변별력이 문제다.** 반경 1km 안의 제과점이 여럿이면 `S_complement`가 모두 1.0으로 같아져 **거리만으로 순위가 정해진다.** 그러면 추천이라기보다 「가까운 순 정렬」에 가깝다.
