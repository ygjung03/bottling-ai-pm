## 0. 선행 설계 결정

시스템 설계 과정에서 답이 필요했던 7가지 쟁점과, 그에 대한 팀 내부 결론.

> **배경** — 8/19 멘토링에서 아래 질문을 준비했으나 실질적인 답변을 얻지 못했다. 착수를 미룰 수 없어 팀 판단으로 결정했다.
> **따라서 D1·D2·D4는 검증되지 않은 판단이며, 3주차(T26·T18)에 실측으로 재검토한다.**

### D1. 사례가 5～10건뿐일 때 어떻게 반영할 것인가

**질문** — 협업 사례가 사업 종료 시점에도 5～10건 수준으로 예상된다. 파인튜닝은 불가능한 규모인데, 프롬프트에 예시로 넣는 few-shot 외에 더 나은 방법이 있는가?

**결정** — **3중 배치.** 용도별로 나눈다.

| 용도 | 방식 | 이유 |
|---|---|---|
| 하드 제약 | 폐기 사유를 규칙으로 추출 → 지시문 | 반드시 지켜야 할 것 |
| 스타일·수준 | few-shot **2～3건만**, 압축 형태 | 사례를 통으로 넣으면 표면 모방 발생 (붕어빵 사례가 많으면 계속 붕어빵류 제안) |
| 최종 검수 | 체크리스트 자가점검 | 출력 직전 스스로 확인 |

> 사례가 쌓여도 전부 넣지 않는다. 예시가 많을수록 출력 다양성이 줄고, 프롬프트 중간부는 주의가 덜 간다.

### D2. 폐기된 기획안을 부정 예시로 넣어도 되는가

**질문** — "이런 결과는 피하라"는 부정 예시가 실제로 효과가 있는가? 있다면 주입 위치나 표현에서 유의할 점은?

**결정** — **원문 그대로 넣지 않고, 폐기 사유를 긍정형 제약으로 변환**해 주입한다.

```
[X]  "이 기획안은 폐기됨: [준비 2주짜리 기획안 전문]"
[O]  "준비 기간은 3일 이내로 제한한다"
```

> LLM은 부정문 처리가 취약하다. "붕어빵을 제안하지 마라"고 하면 오히려 붕어빵이 나올 수 있다.
> 부정 예시를 쓸 경우 사례 전문이 아닌 **폐기 사유 한 줄만**, 긍정 예시와 **물리적으로 분리된 섹션**에 둔다.

### D3. 수치를 어떻게 프롬프트에 넘길 것인가

**질문** — 컨텍스트 빌더가 수치를 문장으로 바꾸는 과정에서 정보 손실이 발생한다. 어느 수준까지 해석해서 전달해야 하는가? 원수치를 함께 주는 편이 나은가? LLM이 없는 값을 만들어내는 것을 어떻게 막는가?

**결정** — **원수치와 해석을 병기**하고, **출력 후 코드로 대조 검증**한다.

```
금요일 19~22시 매출 비중 34% (주중 최고)
```

해석만 주면 근거를 제시하지 못하고, 원수치만 주면 잘못 읽는다. 환각 방지는 세 겹으로 둔다.

1. 없는 항목은 **"데이터 없음"으로 명시** — 누락하면 모델이 지어낸다
2. 지시문에 *"입력에 없는 숫자를 만들지 말 것, 직접 계산하지 말 것"* 명시
3. [중요] **후처리 검증** — 출력의 `추천_근거`에 나온 숫자가 입력 컨텍스트에 존재하는지 정규식으로 대조 (5-1의 A3)

> 3번이 핵심이다. 프롬프트로 막는 데는 한계가 있으나 코드 대조는 확실하다.

### D4. 페르소나를 병렬로 돌릴 것인가 순차로 돌릴 것인가

**질문** — 응답 시간 때문에 (2) 셰프와 (3) 마케터를 병렬로 두면 서로를 참조하지 않아 메뉴와 이벤트가 어긋난다. 순차로 바꾸면 정합성은 나아지나 느려진다. 어느 쪽이 유리한가?

**결정** — **순차 + 3안 병행.** (1)→(2)가 3안 동등 제시→(3)이 3안 각각 홍보 생성→(4)가 순위 결정.

- 시간 차이가 크지 않다. 실측 결과 4단계 순차가 **약 17초**로 확인되어(6-2-3) 병렬화의 실익이 사라졌다
- 반면 정합성 문제는 실질적이다. 마케터가 메뉴를 모르면 "가을 콜라보 이벤트" 같은 공허한 결과가 나온다
- **순위 결정권을 (4)로 일원화**한다

> [주의] **미검증.** T26에서 현행과 병렬안을 각 10회 생성해 정합성을 비교한다.

### D5. 정답이 없는 생성물의 품질을 어떻게 측정할 것인가

**질문** — 기획안처럼 정답이 정의되지 않는 출력의 품질을 어떻게 재는가? 프롬프트 수정이 개선인지 퇴보인지 판별할 방법이 대표님의 주관적 판정뿐이다.

**결정** — **3층 구조.** LLM-as-judge는 채택하지 않는다.

| 층 | 방법 | 주체 | 비용 |
|---|---|---|---|
| 1 | 자동 검증 — 스키마·필수필드·수치대조·제약위반 | 코드 | 0 |
| 2 | 루브릭 채점 — 5항목 × 1～5점 | 대표님 | 건당 2분 |
| 3 | 채택률 — 3안 중 채택 비율 | 자동 집계 | 0 |

> LLM-as-judge는 judge 자체를 검증해야 하고, 같은 모델이면 자기 출력에 후한 편향이 있다.
> [중요] **고정 테스트셋(5-5)이 전제 조건이다.**
> 프롬프트를 수정한 뒤 결과가 나빠졌을 때, 프롬프트 탓인지 입력이 달라진 탓인지 구분할 수 없기 때문이다.
> 입력 8건을 고정해두고 버전마다 같은 8건을 재생성하면, 통과율·평균점수의 차이가 곧 프롬프트의 차이가 된다.

### D6. 대표님이 데이터를 신뢰하지 않는 상황을 어떻게 풀 것인가

**질문** — 현장방문 보고서에 *"상권 데이터를 영업전략에 반영하기 어렵다"*는 대표님 의견이 기록되어 있다. 우리 설계는 공공 상권데이터를 (1) 상권분석가의 주 입력으로 삼는데, 근거를 어떤 형태로 제시해야 수용도가 올라가는가?

**결정** — 네 가지를 적용한다.

1. **일반론이 아니라 행동으로** — "금요일 19～22시 매출 비중이 높습니다" [X] → "이번 금요일 19시에 붕어빵 팝업을 여세요" [O]
2. [중요] **아는 것부터 검증받기** — 대표님이 이미 아는 사실을 먼저 보여주고("맞네"), 그다음 모르는 것을 제시한다
3. **실시간 지표를 앞세우기** — 분기 데이터보다 "지금 뚝섬 혼잡도"가 설득력이 크다 → 대시보드를 W3으로 앞당김(4-4)
4. **예측과 실제를 나란히 기록** — 적중률이 쌓이면 가장 강한 근거가 된다

### D7. 사업 종료 후 비개발자가 유지할 수 있게 하려면

운영 주체가 사업 종료 후 개발 지식이 없는 소상공인 본인이 된다. **프롬프트를 코드 외부 파일로 분리**하고, 목표를 "직접 개발"이 아니라 **"방치해도 돌아감 + 외주가 이어받을 수 있음"**으로 잡는다. 상세는 8장.

### D4 변경에 따른 체인 구조

```
(1) 상권분석가 → (2) 셰프 → (3) 제휴 마케터 → (4) AI 컨설턴트
   상권 진단      메뉴 3안      3안 각각의        3안 재평가·
                 (동등, 순위X)   홍보 기획        순위 확정
    ~1.9초        ~3.7초         ~4.3초           ~7.1초     약 17초
```

**각 단계의 역할 경계**

| 단계 | 하는 것 | 하지 않는 것 |
|---|---|---|
| (2) 셰프 | 서로 다른 접근의 메뉴 **3안을 동등하게** 제시 | 순위를 매기지 않는다 |
| (3) 마케터 | **3안 각각**에 대한 홍보 기획 | 메뉴를 평가하거나 고르지 않는다 |
| (4) 컨설턴트 | 메뉴+홍보 3세트를 받아 **순위 확정** 및 정합성 교정 | 메뉴를 새로 만들지 않는다 |

**왜 이 구조인가**

- **순위 결정권이 (4)로 일원화된다.**
- **대표님이 3안을 동등한 형태로 비교**할 수 있다. 일부만 홍보 기획이 있으면 *"홍보가 없어서 안 골랐다"*는 노이즈가 채택률 지표를 오염시킨다

**(3)의 토큰 절감 방식** — 3안을 독립적으로 쓰면 상권·협력사·시점이 같아 내용의 상당 부분이 중복된다. 프롬프트에서 다음을 지시한다.

```
1. 세 안에 공통 적용되는 홍보 축을 먼저 1개 작성한다.
2. 각 안마다 다른 부분만 별도로 작성한다. 공통 내용을 반복하지 않는다.
```

## 1. 프롬프트 명세

### 1-0. 공통 규칙

모든 프롬프트는 `prompts/` 디렉터리에 **YAML 파일로 분리**한다. 코드에는 파일명만 남긴다.

> ⚠️ **변수 치환에 `str.format()`을 쓰지 않는다.** 프롬프트에 출력 스키마용 중괄호가 있어 충돌한다. 상세는 6-2-4 참조.

```
prompts/
  common_rules.yaml      # 전 페르소나 공통 지시
  p1_analyst.yaml
  p2_chef.yaml
  p3_marketer.yaml
  p4_consultant.yaml
  constraints.yaml       # 폐기 사유에서 추출한 하드 제약 (누적 갱신)
  fewshot.yaml           # 채택 사례 2~3건 (회전)
```

**공통 지시문 (모든 프롬프트 앞단에 삽입)**

```
[출력 규칙]
- 반드시 지정된 JSON 스키마로만 응답한다. 설명 문장을 앞뒤에 붙이지 않는다.
- 입력에 제시되지 않은 수치를 만들어내지 않는다.
- 계산이 필요한 경우 직접 계산하지 않고, 입력에 있는 값을 그대로 인용한다.
- 근거로 인용하는 수치는 반드시 입력 컨텍스트에 존재하는 값이어야 한다.
- 정보가 없는 항목은 추정하지 말고 "데이터 없음"으로 표기한다.
```

### 1-1. (1) 상권분석가

**입력**

| 변수 | 출처 | 예시 |
|---|---|---|
| `{context}` | 컨텍스트 빌더 출력 | 아래 형식 |
| `{target_date}` | 사용자 입력 | 2026-09-18 |

**프롬프트 본문**

```
당신은 서울 광진구 뚝섬유원지 상권을 분석하는 분석가다.
바틀링(셀프탭 크래프트 맥주 테이크아웃 펍, 15시 개점)의 협업 기획을
위해 대상 시점의 상권 상황을 진단한다.

[상권 데이터]
{context}

[지시]
1. 대상 시점에 가장 유리한 공략 시간대를 1~2개 지정한다.
2. 그 시간대의 주 타겟 고객층을 특정한다.
3. 판단 근거가 된 지표를 입력에서 그대로 인용한다.
4. 데이터상 주의해야 할 점이 있으면 기록한다.

[출력 스키마]
{
  "공략_시간대": [{"시작": "19:00", "종료": "22:00", "선정_사유": "..."}],
  "타겟_고객층": {"연령": "...", "성별": "...", "방문_목적": "..."},
  "근거_지표": ["금요일 19~22시 매출 비중 34% (주중 최고)", "..."],
  "주의사항": ["..."],
  "데이터_공백": ["..."]
}
```

### 1-2. (2) AI 셰프

**입력**: (1)의 출력 + 바틀링 맥주 라인업(2-2 `beers`) + 협력사 자원(2-1 `partners`) + `constraints.yaml` + `fewshot.yaml`

```
당신은 소상공인 협업 메뉴를 개발하는 셰프다.
바틀링과 협력사가 각자 보유한 자원만으로 실제 조리 가능한 메뉴를 제안한다.

[상권 분석 결과]
{p1_output}

[바틀링 자원]
- 맥주 라인업: {beer_list}   ← 2-2 `beers` 테이블에서 조회 (메뉴명 / 원·ml / 스타일 / 도수 / 맛 특성)
- 주방 여건: {kitchen_constraints}
- 매장 수용: 7인 내외, 테이크아웃 중심

[협력사 자원]
{partner_resources}

[절대 제약 — 위반 시 해당 안을 폐기하고 다시 만든다]
{constraints}
- 협력사가 명시한 불가 조건: {partner_blockers}

[참고 사례]
{fewshot}

[지시]
1. 메뉴 3안을 제안한다. 서로 다른 접근이어야 한다.
   (예: 조리 최소화형 / 화제성 중심형 / 원가 절감형)
2. **세 안은 동등하다. 순위를 매기지 않는다.** 우열 판단은 이후 단계에서 이뤄진다.
3. 각 안마다 바틀링 맥주 라인업 중 1종을 페어링으로 지정하고 이유를 쓴다.

   - 바틀링 매출의 대부분이 맥주에서 발생하므로, "원가 절감형"이라 하더라도
     메뉴 원가를 낮추는 것이지 저가 맥주를 붙이라는 뜻이 아니다.
     세 안의 페어링이 모두 저가 라인에 몰리지 않게 한다.
4. 예상 원가는 협력사가 제시한 식재료 기준으로 추산하되,
   단가를 모르면 "산출 불가"로 표기한다.

[출력 스키마]
{
  "메뉴안": [
    {
      "안_id": "A",
      "접근": "조리 최소화형",
      "메뉴명": "...",
      "구성": "...",
      "필요_재료": [{"재료": "...", "제공처": "바틀링|협력사"}],
      "필요_장비": [{"장비": "...", "제공처": "..."}],
      "조리_난이도": "상|중|하",

      "판매가_제안": 0,
      "페어링_맥주": {"메뉴명": "갈매기 IPA", "이유": "..."},
      "제약_충족_확인": ["협력사 장비만 사용함", "..."]
    }
  ]
}
```

### 1-3. (3) 제휴 마케터

### 1-5. constraints.yaml — 폐기 사유의 긍정형 변환

폐기가 발생할 때마다 사유를 **긍정 제약**으로 바꿔 누적한다. 원문은 넣지 않는다.

```yaml
    rule: "예상 원가는 판매가의 40%를 넘지 않는다."
```

> [주의] `origin`은 이력 추적용이며 **프롬프트에는 `rule`만 주입**한다.

### 2-1. partners — 협력사 마스터

```sql
CREATE TABLE partners (
```

### 2-2. beers — 바틀링 맥주 라인업 (월 1회 교체)

대표님이 **월 1회 라인업을 교체**하므로 코드에 하드코딩하지 않는다. 과거 기획안 재현을 위해 이력을 남긴다.

```sql
CREATE TABLE beers (
  id            BIGSERIAL PRIMARY KEY,
  name          TEXT NOT NULL,            -- 갈매기 IPA
  price_per_ml  NUMERIC(5,1) NOT NULL,    -- 20.0
  style         TEXT,                     -- IPA / 라거 / 위트에일 / 켈러비어
  abv           NUMERIC(3,1),             -- 도수 %
  ibu           INTEGER,                  -- 쓴맛
  flavor_notes  TEXT[],                   -- {과일향, 시트러스, 쌉쌀함}
  brewery       TEXT,
  is_alcohol    BOOLEAN NOT NULL DEFAULT true,
  valid_from    DATE NOT NULL,            -- 라인업 적용 시작일
  valid_to      DATE,                     -- NULL이면 현재 판매 중
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_beers_valid ON beers (valid_to, valid_from DESC);
```

**조회 규칙**

```sql
-- 현재 라인업
SELECT * FROM beers WHERE valid_to IS NULL;
-- 특정 시점 라인업 (과거 기획안 재현)
SELECT * FROM beers WHERE valid_from <= :d AND (valid_to IS NULL OR valid_to > :d);
```

**교체 절차** — 관리 화면(4-5)에서 처리한다.
1. CSV 업로드 또는 폼 입력으로 신규 라인업 등록
2. 기존 행의 `valid_to`를 교체일로 일괄 갱신
3. `style`·`abv`·`flavor_notes`가 비면 **경고 표시** — 페어링 품질에 직결된다

> [주의] 현재 12종 중 **5종(맘마미아·캄캄·끽비어 삐약·빅웨이브·흔들흔들)의 스타일이 미확인**이다. 비어 있으면 (2) 셰프가 페어링을 추측으로 채운다.

### 2-3. market_context — 상권 시계열 (30분 배치 누적)

> **2026-08-22 갱신.** 실제 API 응답 확인 결과를 반영해 스키마를 재설계했다. 근거는 6-2 참조.

**통합 API(`citydata`) 1회 호출로 인구·상권·날씨를 모두 수신한다.**

```sql
CREATE TABLE market_context (
  id                BIGSERIAL PRIMARY KEY,
  collected_at      TIMESTAMPTZ NOT NULL,   -- API의 PPLTN_TIME (예정 시각 아님)
  spot              TEXT        NOT NULL,   -- 뚝섬한강공원 | 뚝섬역
  area_cd           TEXT,                   -- POI093 | POI025

  -- 인구
  congestion_level  TEXT,                   -- 여유 | 보통 | 약간 붐빔 | 붐빔
  congestion_msg    TEXT,                   -- 서울시가 제공하는 완성 문장
  population_min    INTEGER,
  population_max    INTEGER,
  ppltn_rates       JSONB,                  -- 성별·연령대·거주/비거주 비중
  forecast_12h      JSONB,                  -- 12시간 예측 배열

  -- 상권 (뚝섬한강공원은 데이터 없음 → NULL)
  cmrcl_level       TEXT,                   -- 한산한 | 보통 | 바쁜 | 분주한
  pay_count         INTEGER,
  pay_amt_min       BIGINT,
  pay_amt_max       BIGINT,
  food_pay          JSONB,                  -- 음식·음료 중분류별 결제 현황
  cmrcl_rates       JSONB,                  -- 결제자 성별·연령 비중

  -- 날씨
  temp              NUMERIC(4,1),
  humidity          INTEGER,
  precpt_type       TEXT,                   -- 없음 | 비 | 눈 ...
  pcp_msg           TEXT,

  raw               JSONB,                  -- CITYDATA 원본 전체
  UNIQUE (collected_at, spot)
);
CREATE INDEX idx_mc_spot_time ON market_context (spot, collected_at DESC);
```

**`food_pay` 구조** — 음식 결제가 단일 값이 아니라 중분류 4종으로 온다.

```json
{
  "한식":                  {"level": "한산한", "count": 7,  "amt_min": 250000, "amt_max": 300000, "store_cnt": 148},
  "일식/중식/양식":         {"level": "분주한", "count": 5,  "amt_min": 650000, "amt_max": 700000, "store_cnt": 123},
  "제과/커피/패스트푸드":    {"level": "바쁜",   "count": 12, "amt_min": 200000, "amt_max": 250000, "store_cnt": 68},
  "기타요식":              {"level": "한산한", "count": 7,  "amt_min": 90000,  "amt_max": 100000, "store_cnt": 191}
}
```

> **협력사 업종별 매칭이 가능해진다.** 붕어빵집이면 `제과/커피/패스트푸드`, 피자집이면 `일식/중식/양식`을 보면 되므로, 추천 엔진의 `S_timing`(3-2) 산출이 정교해진다.

**지점별 수신 데이터**

| 지점 | 인구 | 상권 | 날씨 |
|---|---|---|---|
| 뚝섬한강공원 (POI093) | O | **없음** | O |
| 뚝섬역 (POI025) | O | O | O |

한강공원은 상권 데이터 자체가 존재하지 않는다. 개별 상권 API를 직접 호출하면 `ERROR-500`이 반환되지만, 통합 API로 부르면 정상 응답에 해당 필드만 `None`으로 와서 예외 처리가 불필요하다.

→ **한강 상권의 소비 지표는 뚝섬역 데이터를 대리 지표로 사용한다.** 바틀링이 역과 한강 사이에 위치하므로 합리적 근사다.

### 2-4. sales_profile — 분기 매출 프로파일

> **2026-08-25 갱신.** 상권 단위 → **행정동 단위**로 전환. 사유는 아래 참조.

```sql
CREATE TABLE sales_profile (
  id              BIGSERIAL PRIMARY KEY,
  quarter         TEXT NOT NULL,        -- 2026Q2
  dong_code       TEXT NOT NULL,        -- 행정안전부 주민등록 행정기관코드
  dong_name       TEXT NOT NULL,        -- 자양3동
  industry_code   TEXT,
  industry_name   TEXT NOT NULL,
  sales_amount    BIGINT,               -- 매출 금액 (원)
  sales_count     INTEGER,              -- 매출 건수 (거래 건수)
  weekday_ratio   JSONB,                -- {"월": 0.12, ..., "일": 0.18}
  timeband_ratio  JSONB,                -- {"00-06": 0.03, "06-11": ..., "21-24": 0.21}
  gender_ratio    JSONB,                -- {"남": 0.52, "여": 0.48}
  age_ratio       JSONB,                -- {"10": 0.02, ..., "60": 0.09}
  UNIQUE (quarter, dong_code, industry_code)
);
```

**확정 사항 (8/25, A 확인)**

| 항목 | 내용 |
|---|---|
| `sales_count` | **매출 건수(거래 건수)**. 점포 수가 아니다 |
| `timeband_ratio` 키 | `"00-06"` `"06-11"` `"11-14"` `"14-17"` `"17-21"` `"21-24"` 6구간 |
| 비중 | 원본은 금액으로만 오므로 **적재 시 계산**한다 |

> **객단가를 산출할 수 있다.** `sales_amount ÷ sales_count`로 업종별 평균 결제액이 나온다.
> 협력사 업종의 객단가를 알면 콜라보 메뉴의 가격대를 정하는 근거가 되므로, (2) 셰프 프롬프트 입력으로 활용을 검토한다.

#### [중요] 상권 단위를 쓸 수 없다

**바틀링이 서울시 「주요상권 82곳」에 포함되지 않는다.** 반경 3km로 검색해도 뚝섬 관련 상권이 없다. 따라서 상권코드를 전제한 설계를 모두 행정동 단위로 전환한다.

| 대상 | 전환 |
|---|---|
| `sales_profile` | 상권코드 → **행정동 코드 (자양3동)** |
| `S_trend` (3-2) | 상권변화지표-상권 → **상권변화지표-행정동** |
| V5 영역-상권 | **불필요** — 상권코드를 쓰지 않으므로 |

#### [중요] 축이 조합되지 않고 독립 합계로 온다

CSV가 요일·시간대·성별·연령을 **각각 독립 합계**로만 제공한다. `금요일 × 20대 × 여성` 같은 조합은 존재하지 않는다.

```
(불가) weekday × time_band × age_group 조합 행
(가능) 요일별 총합 / 시간대별 총합 / 성별 총합 / 연령별 총합
```

컬럼 조합형 스키마로는 담을 수 없어 **축별 비중을 JSONB**로 저장한다. 원본은 금액으로 오므로 **비중은 적재 시 계산**한다.

**컨텍스트 빌더(6-3)에 미치는 영향** — 조합 표현을 쓸 수 없으므로 축별 순위로 서술한다.

```
(불가) 주류업종 금요일 19～22시 매출 비중 34%
(가능) 주류업종 금요일 매출 비중 22% (주중 최고)
       17～21시 비중 31% (시간대 중 최고)
       20대 비중 25% / 여성 비중 48%
```

정보 손실은 있으나 각 축의 순위는 그대로 파악할 수 있어 실용상 문제가 없다.

## 3. 추천 엔진 — 스코어링

### 3-1. 후보 선정

```
1. nearby_stores에서 바틀링 좌표 기준 반경 1,000m 이내 조회
2. 업종 필터: 음식점업 · 제과업 · 카페 · 소매(식품) 만 유지
3. 프랜차이즈 추정 제외 (동일 상호가 서울시 내 5개 이상)
4. 남은 후보에 대해 3-2 점수 산출
```

### 3-1-1. 데이터 단위가 세 종류로 갈린다

바틀링이 주요상권 82곳에 미포함되어(2-4) 데이터 단위가 통일되지 않는다. **다만 각 항목이 답하는 질문이 달라 정합 문제는 발생하지 않는다.**

| 단위 | 데이터 | 쓰이는 곳 |
|---|---|---|
| **행정동** (자양3동) | 추정매출 · 상권변화지표 | `S_timing` · `S_trend` · 컨텍스트 빌더 |
| **좌표 반경** | 상가정보 · 문화행사 | `S_distance` · 인근 행사 |
| **지점** (POI093/POI025) | 실시간 인구·상권·날씨 | 컨텍스트 빌더 |

```
S_distance    좌표 반경
S_complement  업종 매핑 (단위 무관)
S_timing      행정동
S_trend       행정동
```

#### 결합 연산은 존재한다 — 정규화로 해소된다

추천 엔진은 네 항목을 가중 합산하므로 **서로 다른 단위의 값을 더한다.** 원본 값은 이렇게 제각각이다.

| 항목 | 원본 | 단위 |
|---|---|---|
| 거리 | 320 | 미터 |
| 업종 상보성 | 제과·디저트 | 문자열 |
| 시간대 | 0.31 | 비중 |
| 상권변화 | 3등급 | 등급 |

**각 항목을 0～1로 정규화하면 단위가 사라진다.** 떡붕(320m, 제과·디저트) 기준 계산 예시다.

```
S_distance    1 - (320 / 1000)        = 0.68
S_complement  제과·디저트 → 매핑표      = 1.00
S_timing      14-17·17-21·21-24 합     = 0.72
S_trend       4등급 중 3번째 → 0.67    = 0.67

Score = 0.30×0.68 + 0.30×1.00 + 0.25×0.72 + 0.15×0.67
      = 0.204 + 0.300 + 0.180 + 0.101
      = 0.785
```

가중치 합이 1이므로 최종 점수도 0～1에 놓이며, 다른 후보와 직접 비교할 수 있다.

**정규화하지 않으면** 단위가 큰 항목이 점수를 지배한다.

```
0.30 × 320  = 96.0     ← 거리가 나머지를 압도
0.25 × 0.72 =  0.18
```

가중치가 무의미해지므로 **정규화는 선택이 아니라 전제**다.

#### 해상도 차이는 의도된 것이다

`S_distance`는 점포별로 다르나, 나머지 세 항목은 **같은 업종·같은 행정동이면 동일한 값**이다.

| | 떡붕 (320m) | A카페 (850m) |
|---|---|---|
| `S_distance` | 0.68 | 0.15 |
| `S_timing` | 0.72 | 0.72 |

`S_timing`이 측정하려는 것은 *"이 점포가 저녁에 잘 팔리는가"*가 아니라 **"이 업종이 저녁에 팔리는 업종인가"**다. 바틀링이 15시 개점이므로 저녁형 업종과의 협업이 유리하다는 판단에 쓰이며, 이는 업종 단위로 보는 것이 옳다.

개별 점포의 시간대별 매출은 공공데이터로 취득할 수 없다.

→ 구조상 **「업종 점수 + 거리 보정」**에 가깝다.

**실질적 쟁점은 지역 차이이며, 아래에서 다룬다.**

#### [미확정] 행정동 통계를 반경 전체에 적용하는 문제

`nearby_stores`는 반경 1km 기준이라 **성동구 성수동 점포가 포함**된다. 자양3동 통계를 성수동 점포에 적용하게 된다.

**해결 방향** — V8 응답에 `adongNm`(행정동명)이 있으므로, 점포별 소속 행정동의 통계를 적용할 수 있다. 다만 반경 1km에 걸리는 행정동을 모두 수집해야 한다.

**T15(추천 엔진) 구현 시 결정한다.** 반경 내 행정동이 2～3개면 전부 수집하고, 그보다 많으면 자양3동 통계를 일괄 적용하되 한계로 기록한다.

### 3-2. 점수 산출식

```
Score = 0.30·S_distance + 0.30·S_complement + 0.25·S_timing + 0.15·S_trend
```

| 항목 | 가중 | 산출 방법 | 범위 |
|---|---|---|---|
| `S_distance` | 0.30 | `1 - (distance_m / 1000)` | 0～1 |
| `S_complement` | 0.30 | 업종 상보성 매핑표 (3-3) | 0～1 |
| `S_timing` | 0.25 | `timeband_ratio`의 `14-17`+`17-21`+`21-24` 합 (상한 1.0) | 0～1 |
| `S_trend` | 0.15 | **상권변화지표-행정동** 등급(4종)을 0/0.33/0.67/1로 정규화 | 0～1 |

> **가중치는 임의 설정값이다.** 실제 데이터로 상위 후보를 뽑아본 뒤 대표님 피드백으로 조정한다. 초기값에 근거는 없다.

### 3-3. 업종 상보성 매핑

바틀링(주류 판매, 안주 취약)을 기준으로 한 상보성 점수.

| 상대 업종 | 점수 | 근거 |
|---|---|---|
| 제과·디저트 (붕어빵, 떡, 베이커리) | 1.0 | 기존 협업 실적 있음, 이동식 조리 가능 |
| 피자·튀김·그릴 | 0.9 | 맥주 페어링 적합, 화덕 대여 가능 |
| 분식·스낵 | 0.8 | 간편 조합 |
| 카페 | 0.6 | 논알콜 라인 연계 |
| 한식·중식 (좌석 중심) | 0.4 | 테이크아웃 전환 난이도 |
| 주류 판매점 | 0.1 | 직접 경쟁 |

### 3-4. 출력

```json
{
  "store_id": "...", "name": "...", "distance_m": 320,
  "score": 0.784,
  "score_detail": {
    "S_distance": 0.68, "S_complement": 1.0,
    "S_timing": 0.72, "S_trend": 0.67
  },
  "reason": "도보 4분 거리의 제과업으로 이동식 조리가 가능하며, 저녁 시간대 매출 비중이 바틀링 영업시간과 겹칩니다."
}
```

`reason`은 **템플릿 문자열로 생성**한다. LLM을 쓰지 않는다. (4) 컨설턴트에 그대로 전달된다.

### 4-2. 기획안 생성 (핵심 화면)

**상단 — 입력**

**생성 중 — 진행 표시 (필수)**

```python
with st.status("기획안 생성 중...", expanded=True) as s:
    st.write("(1) 상권 분석 중...")      # ~8초

```

> 실측 4단계 합계 **약 17초**(6-2-3). 동기 방식으로 충분하며 백그라운드 처리가 불필요하다.
> 단계별 표시는 그대로 유지한다 — 17초도 무반응이면 길게 느껴지고, 어느 단계에서 실패했는지 보여야 한다.

**하단 — 결과**

- `st.tabs(["1순위", "2순위", "3순위"])` — **세 탭 모두 동일한 완성도**로 표시한다
- 각 탭 구성: 메뉴명(헤더) → **선정/후순위 사유** → 페어링 맥주(강조 배지, 원/ml 병기) → 구성·재료·장비 표 → 원가/판매가 → 이벤트·홍보문구(복사 버튼) → 준비물·소요기간 → **추천 근거**(expander) → 리스크
- 제외된 안이 있으면 별도 `st.warning`으로 제외 사유 표시
- `st.expander("검수 결과")` — 안별 체크리스트 6항목 O/-
- 하단 고정: **[이 안으로 채택] [전체 폐기]**. 폐기 시 사유 입력 필수(`text_area`)
- 채택 시 → 어느 안을 채택했는지 `plans.adopted_option`에 기록 + 실행일·매출 입력란 노출

> 세 안을 동등하게 보여주는 것이 중요하다. 일부만 홍보 기획이 있으면 *"홍보가 없어서 안 골랐다"*가 채택률 데이터에 섞인다.

### 4-3. 파트너 추천 — 두 경로 병행

대표님이 **이미 협업할 가게를 정해둔 경우**가 실제로는 더 많다. 추천 결과에서만 고르게 하면 시스템을 우회하게 되므로, 직접 지정 경로를 같은 화면에 둔다.

```
┌─ 경로 A: 추천받기 ──────────┐  ┌─ 경로 B: 직접 지정 ──────────┐
│ 필터 → 후보 순위 → 선택      │  │ 가게 이름 검색 또는 직접 입력  │
└──────────┬─────────────────┘  └──────────┬──────────────────┘
           └────────────┬──────────────────┘
                        ▼
              partners 등록 여부 확인
                        ▼
        [등록됨] → 기획안 생성으로
        [미등록] → 초대 링크 생성 → 협력사 입력 대기
```

**경로 A — 추천받기**
- 좌: 필터 (`slider` 반경, `multiselect` 업종)
- 우: `st.dataframe` — 순위 / 상호 / 업종 / 거리 / 점수
- 행 선택 → 상세 패널에 항목별 점수 막대 + `reason` 문장
- 지도는 `st.map`으로 최소 구현

**경로 B — 직접 지정**
- `st.text_input`으로 상호 검색 → `nearby_stores`에서 부분 일치 조회
- 검색 결과에 없으면 **직접 입력 폼** (상호 / 업종 / 주소) — 반경 1km 밖이거나 데이터에 없는 가게 대응
- 직접 지정한 경우에도 **추천 점수를 계산해 함께 표시**한다. 다만 순위 결정에는 쓰지 않고, (4)에 넘기는 `rec_reason`에 *"대표님 직접 지정"*을 명시한다

**공통 — 이후 처리**
- `partners`에 이미 있으면 → 바로 4-2로
- 없으면 → `invite_code` 발급 후 초대 링크 표시 (복사 버튼)
- 링크를 협력사에 전달 → 입력 완료 시 대표님 화면에 알림

> `plans` 테이블에 `partner_source` 컬럼(`recommended` | `manual`)을 추가해, 추천 경로와 직접 지정 경로의 결과 품질을 나중에 비교할 수 있게 한다.

## 5. 품질 검증 체계

### 5-1. 1층 — 자동 검증 (코드)

생성 직후 실행하여 `plans.auto_check`에 저장한다.

| # | 검사 | 실패 시 |
|---|---|---|
| A1 | JSON 스키마 준수 | 1회 재생성 |
| A2 | 필수 필드 존재 및 비어있지 않음 | 1회 재생성 |
| A3 | **수치 근거 대조** — 출력의 숫자가 `context_snapshot`에 존재하는가 | 경고 표시 |
| A4 | 협력사 `blockers` 위반 여부 (키워드 매칭) | 경고 표시 |
| A5 | 페어링 맥주가 실제 12종 목록에 있는가 | 경고 표시 |
| A6 | 예상 원가 <= 판매가 × 0.4 | 경고 표시 |

**A3 구현**

```python
import re
def check_numbers(output_json, context_text):
    nums = re.findall(r'\d[\d,\.]*', json.dumps(output_json, ensure_ascii=False))
    ctx  = context_text.replace(',', '')
    missing = [n for n in set(nums)
               if len(n) >= 2 and n.replace(',', '') not in ctx]
    return {"passed": not missing, "missing": missing}
```

> 판매가·원가처럼 새로 만드는 숫자는 대조 대상에서 제외해야 한다. `추천_근거` 필드만 검사하는 것이 현실적이다.

### 5-4. 퍼널 분석 — 두 축

멘토링에서 제안받은 항목. 성격이 다른 두 퍼널을 각각 구성한다.

#### 퍼널 A — 협업 이벤트 성과 (외부 데이터)

```
인스타 도달 ─→ 저장·공유 ─→ 신규 적립 ─→ 재방문 적립
  (노출)        (관심)       (획득)       (유지)
```

| 단계 | 지표 | 출처 |
|---|---|---|
| 노출 | 게시물 도달 수 | 인스타 인사이트 캡처 |
| 관심 | 저장·공유·프로필 방문 | 인스타 인사이트 |
| 참고 | 뚝섬 유동인구 | **실시간 도시데이터** (대리 지표) |
| 획득 | 신규 적립 건수 | 쿠폰 앱 대시보드 |
| **유지** | **재방문 적립 비율** | 쿠폰 앱 대시보드 |

**마지막 단계가 핵심이다.** 협업으로 온 손님이 다시 오는가 — 대표님 과제가 "한강 상권 비수기 극복"이므로, 일회성 화제로 끝나는지 단골이 되는지가 사업 목적과 직결된다.

**한계**
- "매장 방문" 단계는 측정 수단이 없다 (입장객 카운트 불가)
- 쿠폰 앱 이용률이 100%가 아니므로 절대 수치는 왜곡된다 → **상대 비교로만 해석**
- 표본이 협업 1～3건이므로 통계적 유의성은 주장하지 않는다

#### 퍼널 B — AI PM 시스템 (내부 데이터) [중요]

```
추천 노출 ─→ 파트너 선택 ─→ 기획안 생성 ─→ 채택 ─→ 실행 ─→ 성과 기록
  10곳         1곳          3안         1안     ?건     ?건
```

| 단계 | 지표 | 산출 |
|---|---|---|
| 노출 | 추천 후보 표시 수 | 화면 로그 |
| 선택 | 파트너 확정 건수 | `plans.partner_id` |
| 생성 | 기획안 생성 건수 | `plans` 행 수 |
| **채택** | `adopted / generated` | `plans.status` |
| 실행 | `executed / adopted` | `plans.executed_at` |
| 기록 | 성과 입력 완료 건수 | `plans.performance` |

**퍼널 B를 주 지표로 삼는다.** 이유:

1. **데이터가 전부 내부에 있다.** 대표님께 추가 요청이 필요 없다
2. 매출이 평가 기준이 아니라면, 심사에서 볼 것은 *"AI PM이 실제로 작동했는가"*이며 퍼널 B가 그것을 직접 보여준다
3. **어느 단계에서 새는지가 곧 개선 방향이다** — 생성은 많은데 채택이 없으면 프롬프트 품질 문제, 채택은 되는데 실행이 안 되면 현실성 문제
4. 추천 경로(`partner_source='recommended'`)와 직접 지정(`manual`)을 분리해 비교할 수 있다

**최종보고서 서술 예시**

> 기획안 12건 생성 → 5건 채택(42%) → 3건 실행(60%) → 실행 3건 중 2건에서 재방문 증가 확인

### 6-2-1. V1·V2·V3 검증 결과 (2026-08-22, 완료)

**결론: 통합 API(`citydata`) 단독 사용으로 확정한다.**

```
GET http://openapi.seoul.go.kr:8088/{KEY}/json/citydata/1/5/{장소명}
```

**대조 방법** — 개별 API 응답(V1·V2)과 통합 API 응답을 필드 경로 및 값 단위로 전수 비교했다. 리스트는 첫 원소가 아니라 전 원소를 포함했다.

| 비교 대상 | 결과 |
|---|---|
| 인구 데이터 블록 | **완전 일치** (파이썬 객체 `==` 비교 True) |
| 상권 데이터 블록 | **완전 일치** |
| `CMRCL_RSB` 5개 항목 | 완전 일치 |
| `FCST_PPLTN` 12개 항목 | 완전 일치 |
| 개별에만 있는 필드 | **없음** |

래퍼(최상위) 구조만 다르다. 개별 상권 API의 `AREA_NM`·`AREA_CD`는 통합에서 `CITYDATA` 하위로 이동했고, `list_total_count`는 의미가 다르다(개별=`CMRCL_RSB` 개수, 통합=조회 장소 수). 정보 손실은 없다.

**통합 API를 채택하는 근거 4가지**

| # | 근거 |
|---|---|
| 1 | **호출 횟수 절감** — 4회(2지점 × 2API) → **2회** |
| 2 | **날씨 데이터 확보** — `WEATHER_STTS`가 함께 온다. 기온·습도·강수형태·강수메시지. **한강 상권에서 날씨는 결정적 변수**이므로 이득이 크다 |
| 3 | **응답 형식 통일** — 개별 API는 결과 코드 키가 서로 다르다(`RESULT.CODE` vs `resultCode`). 통합만 쓰면 파싱 분기가 사라진다 |
| 4 | **에러 처리 단순화** — 뚝섬한강공원 상권을 개별 호출하면 `ERROR-500`이지만, 통합에서는 정상 응답에 해당 필드만 `None`이다 |

추가로 `EVENT_STTS`(행사), `ROAD_TRAFFIC_STTS`(교통), `PRK_STTS`(주차) 등도 함께 오지만 현재는 사용하지 않는다. `raw` 컬럼에 `CITYDATA` 전체를 보존하므로 나중에 필요하면 파싱만 추가하면 된다.

**확인된 응답 특성**

| 항목 | 내용 | 대응 |
|---|---|---|
| 숫자가 문자열 | `"3000"` 형태 | `_int()` / `_float()` 헬퍼로 변환 |
| 혼잡도 자연어 문장 | `AREA_CONGEST_MSG`에 완성 문장 제공 | `congestion_msg`에 보존. 컨텍스트 빌더에서 참고 인용 |
| 시각 필드 | `PPLTN_TIME` (5분 단위 갱신) | `collected_at`에 사용. 30분 주기 수집에서 중복 없음 |
| 지점 코드 | 뚝섬한강공원 `POI093` / 뚝섬역 `POI025` | 호출은 한글명으로 한다 |

**남은 한계** — 위 검증은 **한 시점 스냅샷 1건** 기준이다. 시간대·요일에 따라 필드 구성이 달라질 가능성은 배제하지 못한다. `raw`에 원본을 보존하는 이유다.

#### 결정 근거

**① 모델 — `gemini-3.5-flash-lite`**

상위 모델(`3.6-flash`) 대비 **7배 빠르며 품질 검사를 모두 통과**했다. lite 3종 간 시간 차이(15.0～17.0초)는 편차 범위 안이라 유의미하지 않다. 3.5가 3.1보다 최신이므로 3.5를 택한다.

**② thinking 옵션 — 사용하지 않는다**

| 확인 | 결과 |
|---|---|
| 구 SDK(`google-generativeai`) | `thinking_config` 지원 안 함 (`Unknown field`) |
| `thinking_budget=0` | 400 에러. 모델이 완전 비활성화를 허용하지 않음 |
| 상위 모델 + `budget=128` | 단일 호출 25.6초 → 16.7초 (**35% 단축**) |
| **lite + `budget=128`** | **17.0초 → 15.0초. 이득 없고 편차만 0.7 → 2.3으로 증가** |

lite 계열은 원래 추론을 거의 하지 않아 조절 여지가 없다. **옵션이 불안정성만 키우므로 쓰지 않는다.**

**③ SDK — `google-genai`로 교체**

thinking 옵션 검증을 위해 신 SDK가 필요했다. 구 SDK는 지원 종료 예정이므로 어차피 교체 대상이었다. 영향 범위는 `chain/gemini.py` 한 파일이며, 나머지 코드는 `call()`을 통해서만 호출하므로 변경이 없다.

> ⚠️ `google-genai` 설치 시 `httpx`가 0.28로 올라가 supabase 계열과 의존성 경고가 발생한다. **실동작에는 문제가 없음을 확인**했다(수집기 정상 적재).

**④ 무료 티어 한도**

`gemini-3.6-flash`는 반복 측정 중 **일일 할당량이 소진**되어 3회 측정을 완료하지 못했다. lite 계열은 한도가 넉넉해 전 조건 3/3 성공했다.

**[중요] 프롬프트 수정으로 해결한 문제** — 초기 측정에서 `3.5-flash-lite`가 "원가 절감형" 안에 **논알콜(체리에이드)을 반복 선택**했다. 원가만 보면 타당하나 **바틀링 매출의 대부분이 맥주**이므로 실익이 없다.

#### [주의] 프롬프트 렌더링에 `str.format()`을 쓰지 않는다

프롬프트 본문에 출력 스키마용 JSON 중괄호가 포함되어 있어, `format()`이 이를 치환 변수로 오인한다.

```
[출력 스키마]
{"공략_시간대": [...], "타겟_고객층": {...}}
     ↑ format() 이 변수명으로 읽어 KeyError 발생
```

**전달된 변수명만 골라 문자열 치환**하는 방식으로 대체했다.

```python
for k, v in vars_.items():
    out = out.replace("{" + k + "}", str(v))
```

추가로 YAML의 `inputs` 목록과 대조해 **치환되지 않은 변수가 남으면 예외를 낸다.** 변수명 오타·전달 누락을 조기에 잡기 위함이다.

```
- 기온 29.3도, 습도 66%, 강수 없음

[분기 매출 프로파일]  ※ 자양3동 기준
- 데이터 없음 (적재 전)

[인근 행사 (30일 내)]
- 데이터 없음
```

분량은 약 1,100자 / 35줄이다.

#### 초기 규격을 폐기한 이유

초안은 `"주류업종 금요일 19～22시 매출 비중 34% (주중 최고)"` 형태를 전제했으나, **그런 데이터가 존재하지 않는다.**

| 전제 | 실제 |
|---|---|
| 요일 × 시간대 조합 매출 | **각 축의 독립 합계만 제공** (2-4) |
| 상권 단위 통계 | 바틀링이 주요상권 82곳에 미포함 → 행정동 (2-4) |
| 정밀 인구 수치 | 구간값으로 제공 (`10000～12000`) |

조합 데이터가 없으므로 축별 순위로 서술한다. 정보 손실은 있으나 각 축의 순위는 그대로 파악할 수 있다.

#### 출력 원칙

**① 관측 사실을 그대로 제시한다**

표본이 적다는 이유로 항목을 생략하거나 다른 값으로 대체하지 않는다. 건수를 밝히고 해석은 LLM에 맡긴다.

초기에는 *"같은 요일 표본이 6건 미만이면 전체 평균으로 대체"* 같은 임계값을 두었으나 폐기했다. 전체 수집 기간이 4주 남짓이라 어떤 기준을 두어도 근거가 약하고, **조건을 넘었다는 이유로 "금요일 피크는 19시" 같은 단정을 만들면 오히려 왜곡된다.**

**② 내부 계산값을 노출하지 않는다**

`평균 2.6/4` 같은 표기는 LLM이 해석할 맥락이 없어 판단에 쓰이지 못한다. 등급 이름으로 제시한다.

**③ 평균을 반올림해 등급으로 바꾸지 않는다**

`'보통'`과 `'붐빔'`의 평균을 `'약간 붐빔'`으로 표기하면 **실제로 한 번도 관측되지 않은 등급이 출력된다.** 구간 간 순위 결정에만 평균을 쓰고, 표시되는 등급은 실제 관측값에서 가져온다.

**④ 대표 등급은 최빈값이 과반일 때만 세운다**

| 조건 | 표기 |
|---|---|
| 최빈값 과반 | `'여유' (6건 중 5건)` · `'여유' (6건 전부)` |
| 과반 미달 | `관측 6건 — '분주한' 2 / '바쁜' 2 / '보통' 1 / '한산한' 1` |

근거가 약한 대표값을 세우느니 분포를 보이는 편이 판단에 도움이 된다. **건수가 아니라 흩어진 정도가 기준이다.**

**⑤ 등급 이름을 함께 표기한다**

`"가장 혼잡"`처럼 상대적 위치만 밝히면, 실제 수준이 `'보통'`인데도 붐비는 것으로 읽힐 수 있다.

**⑥ 대비가 성립하지 않으면 하지 않는다**

두 경우에 최고·최저 구분을 생략하고 *"시간대에 따른 차이 없음"*으로 서술한다.

- 구간별 평균이 모두 같음
- 평균은 다르나 **표시될 대표 등급이 같음** — `'여유'인데 가장 혼잡`으로 읽혀 오해를 부른다

시간대에 따른 차이가 없다는 것 자체가 판단 재료다. 하루 종일 한산하다면 특정 시간을 노릴 이유가 없고, 사람을 끌어올 이벤트가 필요하다는 뜻이 된다.

**⑦ 없는 항목은 "데이터 없음"으로 명시한다**

생략하면 LLM이 지어낸다. 미적재 테이블(`sales_profile`·`events`)은 예외를 던지지 않고 `데이터 없음 (적재 전)`을 반환한다.

**⑧ 날씨를 포함한다**

한강 상권에서 강수 여부는 방문객 수를 좌우한다.

**⑨ 상권 지표는 뚝섬역 기준임을 명시한다**

뚝섬한강공원은 상권 데이터가 없다 (2-3).

**⑩ 생성 문자열을 `plans.context_snapshot`에 저장한다**

재현 및 A3 수치 대조 검증용이다.

#### 제외한 것

**서울시 제공 자연어 문장(`congestion_msg`)** — 초기 규격에는 참고 인용으로 넣었으나 제거했다. 일반 시민용 안내라 자체 집계보다 정보량이 적고, 어느 시점 문구인지 밝히면 문장만 길어진다.

#### 검증

`tests/test_context.py`가 구조와 원칙 위반을 함께 점검한다.

| 검사 | 잡는 것 |
|---|---|
| 구획 7종 존재 | 섹션 누락 |
| 중괄호 없음 | 치환 안 된 변수 |
| `None` 없음 | 빈 값 처리 누락 |
| 내부 계산값 패턴 | `평균 2.6/4` 형태 (원칙 ②) |
| 관측 건수 표기 | 판단 근거 누락 (원칙 ①) |
| 등급 이름 존재 | 최상급만 남은 표기 (원칙 ⑤) |
| 과반 검사 | 근거 약한 대표값 (원칙 ④) |
| 대비 무의미 | 최고·최저 등급 동일 (원칙 ⑥) |

#### 남은 한계

- **금요일 데이터가 없다.** 수집을 8/23(토)에 시작해 8/28이 첫 금요일이다. 명세서 여러 곳이 "금요일 저녁"을 전제하므로 8/31 방문 시점에는 하루치뿐임을 감안한다
- 수집 간격이 불규칙하다. `PPLTN_TIME` 중복 제거로 시간당 1～2건이며, 새벽 구간에 몰리는 경향이 있다

## 8. 이관 설계 (Q7 대응)

### 8-1. 분리 원칙

| 대상 | 위치 | 비개발자 수정 가능성 |
|---|---|---|
| 프롬프트 | `prompts/*.yaml` | 관리 화면에서 편집 |
| 제약조건 | `constraints.yaml` | 관리 화면에서 추가/삭제 |
| few-shot | `fewshot.yaml` | 채택 사례 체크박스 선택 |
| 모델명·키 | 환경변수 | `.env` 한 줄 |
| 스코어링 가중치 | `config.yaml` | 관리 화면 슬라이더 |

코드에 문자열 상수로 프롬프트를 넣지 않는다.

### 8-2. 방치 내구성

사업 종료 후 6개월 방치를 가정한다.

- API 키 만료 임박 시 알림 (수집기에서 401 감지 → 대표님 카톡/이메일)
- GitHub Actions 스케줄 비활성화 방지 — 월 1회 자동 커밋 워크플로
- 수집 실패가 3회 연속이면 알림
- 데이터가 비어도 화면이 죽지 않게 (빈 상태 UI)

### 8-3. 인수인계 문서 목차

기능 설명이 아니라 **장애 대응 중심**으로 쓴다.

```
1. 이 시스템이 하는 일 (1페이지)
2. 증상별 확인 순서
   - 기획안이 안 나온다 → API 키 / 잔여 크레딧 / 로그 위치
   - 상권 정보가 옛날 것이다 → GH Actions 실행 이력
   - 결과가 이상하다 → 프롬프트 수정 방법
3. 정기 점검 (월 1회, 5분)
4. 외주 개발사 인계용 — 저장소 구조 / 배포 / 환경변수
```
