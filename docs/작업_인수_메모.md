## ① 상권 대시보드 보완

`app/pages/4_상권_대시보드.py` — 9/7 멘토링 시연을 위해 급히 만들었다. **동작하나 아래 여섯 가지가 남았다.**

### 정확성 — 먼저 고친다

**a. 「지금 뚝섬」의 기온·결제가 어느 지점 값인지 드러나지 않는다**

`기온 28.2℃`만 적혀 있으나 실제로는 **뚝섬역 관측치**다. 한강공원에는 상권·날씨 데이터가 없어 뚝섬역 기준으로만 나온다(명세서 2-3). 화면에 그 사실이 없으면 두 지점 평균으로 오해한다.

**b. 「지금」이 실제로 지금이 아닐 수 있다**

`groupby("spot").last()`로 최신 행을 뽑는데, **수집이 스케줄에 걸릴 때만 이뤄져 몇 시간 전 값일 수 있다.** GitHub Actions 크론이 하루 3～4회만 걸린다.

「지금 뚝섬」이라 적어두고 3시간 전 값을 보이면 오해를 부른다. **관측 시각을 함께 표시**하고, 오래된 값이면 그 사실을 밝혀야 한다.

**c. 상권 데이터 중복이 걸러지지 않는다**

인구는 5분, **상권은 10분 주기로 갱신**되는데 수집은 5분 간격이다. 같은 `pay_count` 값이 두 번 이상 저장된다. 새벽에는 90～240분간 갱신되지 않아 최대 6.5배가 된다.

컨텍스트 빌더는 `raw->LIVE_CMRCL_STTS->>CMRCL_TIME`으로 중복을 거른다(`context/builder.py`의 `_dedup_cmrcl()`, 명세서 6-3 원칙 ⑦). **대시보드는 거르지 않아 결제 추세가 실제보다 촘촘하고 평균이 왜곡된다.**

같은 방식으로 걸러야 한다. 조회 컬럼에 `cmrcl_time:raw->LIVE_CMRCL_STTS->>CMRCL_TIME`을 더하고, 지점·`cmrcl_time` 조합으로 중복을 제거한다.

### 활용도 — 그다음

**d. 강수 여부를 보여주지 않는다**

`precpt_type`을 조회는 하나 화면에 쓰지 않는다. **한강 상권에서 비 여부가 방문객 수를 크게 좌우한다**(기획서 4장). 「지금 뚝섬」에 넣는다.

**e. 두 지점을 겹쳐 볼 수 없다**

지금은 라디오로 한 지점만 고른다. **두 지점을 한 차트에 겹쳐 그리면** *"공원은 저녁에 붐비고 역은 낮에 붐빈다"* 같은 대비가 한눈에 보인다. 그것이 협업 시간대 판단의 근거가 된다.

지점 선택에 「둘 다」를 더하고, 선택 시 색을 나눠 두 선을 그린다.

**f. 인구 수치를 상단에서만 쓴다**

`population_min`·`population_max`가 상단 지표에만 쓰인다. **혼잡도 등급(1～4)보다 인구 수가 직관적일 수 있다.** 요일·시간대 차트에 「혼잡도 / 인구」 전환을 두는 방법을 검토한다.

> **주의** — 인구는 구간값(`10000～12000`)으로 온다. 평균을 쓰되 구간이라는 사실을 밝혀야 한다.

### 참고

- 조회는 `raw` 컬럼을 통째로 받지 않는다. 행당 수십 KB라 `statement timeout`이 난다
- `food_pay`는 숫자가 아니라 **dict**다. 업종별 등급이 담겨 있다. 결제 건수는 `pay_count`를 쓴다
- `matplotlib`이 설치되어 있지 않다. `st.vega_lite_chart`(Streamlit 내장)를 쓴다
- 12시간 예측은 뺐다. 화면이 복잡해지는 데 비해 협업 기획과 무관하다

## 이 프로젝트의 작업 원칙

문서 전반에 일관되게 적용된 것들. **새 코드도 이것을 따른다.**

**① 코드는 사실 집계만, 해석은 LLM에 맡긴다**

컨텍스트 빌더가 *"가장 혼잡한 시간대는 X"*라고 결론짓지 않는다. 전 구간 분포를 나열하고 판정은 `(참고)` 줄로 분리한다. 근거 건수를 함께 적어 LLM이 신뢰도를 가늠하게 한다.

**② 근거 없는 임계값을 두지 않는다**

*"표본 3배 차이"*, *"3건 이상만"* 같은 기준을 정할 근거가 없으면 두지 않는다. 실제로 8/27 규격에서 임계값을 전부 걷어냈다.

**③ 없는 값을 지어내지 않는다**

미확보 항목은 `데이터 없음`으로 명시한다. 생략하면 LLM이 채워 넣는다. 흔들흔들 맥주 단가를 몰라 아예 적재하지 않은 것이 그 예다.

**④ 비교하려면 잣대가 같아야 한다**

추천 엔진에서 데이터가 없는 업종을 제외하는 이유, (4)가 세 안을 비교할 수 있는 이유가 모두 이것이다.

**⑤ 실패해도 흐름이 멈추지 않게 한다**

메뉴 이미지 생성 실패는 오류가 아니라 정상 흐름이다. `null`로 두고 그 자리를 생략한다.

**⑥ 문서에 사람을 주어로 세우지 않는다**

팀원이 볼 문서다. 상황과 대응만 적고 진척 평가는 쓰지 않는다.

## 알아두면 좋은 것

**환경**

```
.venv\Scripts\activate      Windows
streamlit run app/main.py   웹
python -m tests.test_p4     체인 검증
```

**주의**

- `raw` 컬럼을 통째로 조회하면 `statement timeout`이 난다. 필요한 컬럼만 명시한다 (명세서 6-3)
- `str.format()`을 프롬프트에 쓰지 않는다. 출력 스키마의 중괄호와 충돌한다
- 폴더 분담 — A: `collectors/` `ingest/` `recommender/` / B: `context/` `prompts/` `chain/` `app/` `scripts/`
- A의 브랜치(`feat/t07-area-code`)가 `main`보다 25커밋 뒤처져 있다. **머지하면 충돌 3건이 난다** — `app/pages/4_상권_대시보드.py`(양쪽이 각자 만듦) · `db/schema.sql` · `ingest/sales_profile.py`

  > **9/8 정정.** 이 자리에 *"그대로 머지하면 8/30 이후 작업이 지워진다"*고 적혀 있었으나 사실이 아니다. `git merge`는 3-way merge라 브랜치가 건드리지 않은 곳은 `main` 것이 그대로 남는다. `merge-tree`로 확인했고, `main`에만 있던 `beers.is_fixed`가 머지 결과에 살아 있다.
  >
  > **위험한 것은 머지가 아니라 충돌 해결이다.** `db/schema.sql`을 브랜치 쪽으로 통째로 받으면 `sales_profile`의 `count_ratio` 4컬럼이 사라진다. 그래서 **답을 아는 쪽이 푼다** — 대시보드는 A 것, `db/schema.sql`과 `ingest/sales_profile.py`는 `main` 것을 쓴다.

**미확보**

- 바틀링 SNS 자산 (U13) — (3)이 도달 목표를 세울 근거가 없다
- 협력사 실제 자원 (U14) — 지금은 가상 데이터. T21 폼으로 받는다
- 메뉴 이미지 모델 (U16) — 실제 호출·품질 확인이 먼저다
- 블로그 검색 유효성 (U17) — 「가게명 + 메뉴명」이 실제로 유효한지
