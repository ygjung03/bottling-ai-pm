**작성** 2026-09-08 ｜ **대상** `chain/runner.py` · `chain/gemini.py` · `prompts/p4_consultant.yaml`
**계기** 기획서 v5·개발명세서·체인 코드를 읽고 「자동 검증 → 재생성」 구조를 어디에 어떻게 붙일지 검토했다.

## 0. 세 줄 요약

1. **루프의 신호선은 이미 깔려 있다.** `p4_consultant.yaml`에 `재생성_필요` 필드가 있는데 `runner.py`가 그 값을 아예 읽지 않는다.
2. **검사도 이미 짜여 있다.** `tests/test_p4.py`의 `check()`가 명세서 A3~A10을 사실상 구현했는데 테스트 파일 안에 갇혀 운영 경로에서 못 쓴다.
3. **붙일 자리는 `runner.py` 한 곳이다.** 검증 실패 유형에 따라 되돌아갈 단계를 정하는 라우팅을 넣는다. 대부분은 (4) 재호출 하나로 끝난다.

## 1. 현재 구조 진단

### 1-1. 지금은 에이전트가 아니라 체인이다

`chain/runner.py`가 전부다.

```python
p1 = step(1, "상권 분석 중...",    "p1_analyst",    ...)
p2 = step(2, "협업 메뉴 개발 중...", "p2_chef",       p1_output=p1, ...)
p3 = step(3, "홍보 기획 중...",     "p3_marketer",   p1_output=p1, p2_output=p2, ...)
p4 = step(4, "최종 검토 중...",     "p4_consultant", p1_output=p1, p2_output=p2, p3_output=p3, ...)
```

분기도 루프도 없이 코드가 1→2→3→4를 고정 순서로 부른다. 페르소나가 넷이라 멀티에이전트처럼 보이지만 이건 **프롬프트 체이닝(prompt chaining)** 이다. LLM이 다음 행동을 정하지 않는다.

**이것 자체는 흠이 아니다.** 명세서 D4에 "순위 결정권을 (4)로 일원화한다"는 근거가 있고, 각 단계의 "하는 것 / 하지 않는 것"도 적혀 있다. 고민하고 고른 구조다.

다만 **용어는 정확히 쓴다.** 지금 상태를 "멀티에이전트"라고 부르면 "에이전트끼리 어떻게 조율하나"에서 막힌다. 지금은 **"4단계 프롬프트 체인"** 이 정확하고, 아래 루프를 붙이면 **"평가자-최적화 루프를 가진 체인"** 이 된다.

### 1-2. (4)는 이미 평가자 역할을 하고 있다

`p4_consultant.yaml`의 지시에 이미 들어 있다.

```
1. 메뉴와 홍보가 어긋난 안이 있으면 홍보 쪽을 고치고 수정 내역에 적는다.
4. 3·4·5번 위반은 고칠 수 있으면 고치고 수정 내역에 적는다.
5. 세 안이 모두 제외되면 "재생성_필요"를 true 로 두고 사유를 남긴다.
```

평가하고 교정하고 기록하는 역할을 이미 맡고 있다. 다만 **LLM 호출 한 번 안에서** 하니 자기가 놓친 것은 자기가 못 잡는다.

> 그래서 이 작업은 **새 개념을 들여오는 것이 아니라, 이미 프롬프트 안에 있는 것을 코드로 끌어올리는 일**이다.

## 2. 확인된 결함 넷

### 2-1. `재생성_필요`를 아무도 받지 않는다 — [높음]

`chain/runner.py:45`

```python
return {"p1": p1, "p2": p2, "p3": p3, "final": p4, "latency_ms": total_ms}
```

`재생성_필요`가 `true`로 와도 그대로 화면에 간다. 그러면 **순위가 빈 기획안**이 뜨고 대표님은 빈 화면을 보게 된다.

그리고 이 경우 **되돌아갈 곳은 (4)가 아니다.** 세 안이 전부 실행 불가라는 뜻이므로 원인은 (2) 셰프다. (4)를 다시 불러도 같은 결론이 나온다.

### 2-2. 4콜 중 하나가 죽으면 앞의 결과를 전부 잃는다 — [높음]

`chain/runner.py:24`가 `call()`을 방어 없이 부르고, `chain/gemini.py:72`가 재시도를 소진하면 `RuntimeError`를 던진다. **p3에서 죽으면 p1·p2가 통째로 사라진다.** 17~20초짜리 체인에서 이건 그냥 손해다.

429일 때는 더 나쁘다. `gemini.py:66`의 `time.sleep(20 * (attempt + 1))`이 20초를 기다린 뒤 실패하는데, 그 대기가 `on_step` 콜백을 안 거치니 **화면에는 "홍보 기획 중..."이 멈춘 채로 20초**가 흐른다.

> W4의 T30(부하·오류 처리)이 이걸 다루려는 것 같은데, 그 주가 곧 9/22 기획안 마감 주다. **마감 직전에 처음 만나는 순서**라 앞당기는 편이 낫다.

### 2-3. 운영 경로와 검증 스크립트가 다른 입력을 준다 — [중간]

`chain/loader.py:25`

```python
out = out.replace("{" + k + "}", str(v))       # str(v)
```

| 경로 | 넘기는 값 | 프롬프트에 들어가는 문자열 |
|---|---|---|
| `runner.py:32` | `p1_output=p1` (dict) | `{'공략_시간대': ['19~22시'], ...}` — 파이썬 repr |
| `test_p4.py:191` | `p1_output=json.dumps(p1, ensure_ascii=False)` | `{"공략_시간대": ["19~22시"], ...}` — JSON |

작은따옴표와 `True`/`False`/`None`이 섞인다. 깨지지는 않지만 **두 경로가 다른 입력을 주고 있다.**

이게 명세서 5-5(고정 테스트셋 8건으로 통과율 측정)의 전제를 흔든다. 테스트에서 잰 통과율이 운영에서 그대로 나온다는 보장이 없다. **`json.dumps`로 통일한다.**

## 3. 결론 — 실패 유형이 되감을 단계를 정한다

이게 설계의 핵심이다. 단순 재시도와 평가자-최적화 루프를 가르는 지점이다.

| 검증 실패 | 진짜 원인 | 되감을 곳 | 추가 비용 |
|---|---|---|---|
| 라인업 밖 맥주 · 단가 오기 | (4)가 옮기다 틀림 | **(4) 재호출** | 7.1초 |
| 1위 필드 누락 (A10) | (4)가 빠뜨림 | **(4) 재호출** | 7.1초 |
| 순위 번호 이상 · 제외 남용 | (4)의 판단 | **(4) 재호출** | 7.1초 |
| (2)에 없는 메뉴명 | (4)가 지어냄 | **(4) 재호출** | 7.1초 |

## 4. 붙이는 순서

### 1단계 — 결함부터 (반나절) [먼저]

되감기 없이 결함만 고친다. **이것만으로도 마감 리스크가 줄어든다.**

1. `_j()` 헬퍼로 JSON 직렬화 통일 (2-3)
2. `run()` 전체를 `try`로 감싸 중간 결과 보존 (2-2)
3. `재생성_필요`를 읽어 `issues`에 실어 반환 (2-1) — 되감기는 아직 안 한다
4. 429 대기를 `on_step`으로 노출 (2-2)

### 2단계 — (4) 재호출 루프 (하루)

1. `tests/test_p4.py`의 `check()`·`parse_beer_prices()`를 `chain/checks.py`로 이동
   - `test_p4.py`는 거기서 import 해서 쓴다. **검사가 두 벌이 되면 갈라진다.**
2. `p4_consultant.yaml`에 `issues` 입력 추가
3. `runner.py`에 되감기 루프 (아래 5장)

**여기까지가 9/22 마감 전 목표다.** A5(맥주·단가)와 A10(1위 필드)이 이 루프로 잡히는데, A10은 제안서 4필드라 **T46(협업 제안서 도출)을 직접 막는 실패**다. 기능 추가가 아니라 마감 보험으로 봐야 한다.

### 3단계 — 나머지 되감기 (여유 있으면)

1. `재생성_필요` → (2)부터 되감기
2. A4·A6 → (2), A7~A9 → (3)
3. `p2_chef.yaml`·`p3_marketer.yaml`에도 `issues` 입력 추가

> **T18(프롬프트 튜닝 1차)보다 먼저 한다.** 순서가 반대면 A3~A10 실패를 전부 프롬프트로 잡아야 해서 튜닝이 훨씬 어려워진다.

## 5. `chain/runner.py` 수정안

2단계까지 반영한 형태다. **그대로 붙여넣지 말고 현재 파일과 대조해서 반영할 것.**

```python
"""
페르소나 체인 실행기 — (1) → (2) → (3) → (4) 순차 + 검증 되감기

[담당] B
[소요] 약 17초 (4콜). (4) 재호출이 걸리면 약 24초
[되감기] 검증 실패 유형에 따라 되돌아갈 단계가 다르다. 지금은 (4) 재호출만 한다.
         (2)·(3) 되감기는 3단계에서 붙인다 — docs/검증루프_도입안.md 참조
"""
import json

from chain.checks import check_final
from chain.gemini import call
from chain.loader import build

# 되감기 최대 횟수. 늘리면 지연이 선형으로 는다.
MAX_REWIND = 1

NO_ISSUES = "(없음 — 첫 생성이다)"


def _j(obj) -> str:
    """프롬프트에 넣을 JSON 문자열.

    dict 를 그대로 넘기면 loader.render() 의 str(v) 가 파이썬 repr 로 만들어
    검증 스크립트(json.dumps)와 다른 입력이 된다. 명세서 5-5 의 고정 테스트셋이
    운영과 같은 조건을 재려면 여기서 통일해야 한다.
    """
    return obj if isinstance(obj, str) else json.dumps(obj, ensure_ascii=False)


def run(context: str, target_date: str, beer_list: str, kitchen: str,
        partner_res: str, partner_blockers: str, constraints: str,
        fewshot: str, bottling_sns: str, partner_sns: str,
        events: str, rec_reason: str, on_step=None) -> dict:
    """
    on_step: 진행 상황 콜백 (Streamlit st.status 연동용)

    반환에 rewinds·issues·error 가 추가됐다.
      rewinds  되감기마다 그때 걸린 항목 목록. 비어 있으면 한 번에 통과한 것
      issues   마지막 검증에 남은 항목. 화면은 이것을 경고로 표시한다 (명세서 5-1)
      error    체인이 중간에 끊긴 경우의 사유. 이때도 p1~p3 는 살아 있다
    """
    ms_total = 0
    result: dict = {
        "p1": None, "p2": None, "p3": None, "final": None,
        "latency_ms": 0, "rewinds": [], "issues": [], "error": None,
    }

    def step(n: int, label: str, name: str, **kw) -> dict:
        nonlocal ms_total
        if on_step:
            on_step(n, label)
        out, ms = call(build(name, **kw))
        ms_total += ms
        return out

    def call_p4(note: str = "") -> dict:
        return step(4, "최종 검토 중...", "p4_consultant",
                    p1_output=_j(result["p1"]),
                    p2_output=_j(result["p2"]),
                    p3_output=_j(result["p3"]),
                    beer_list=beer_list, rec_reason=rec_reason,
                    constraints=constraints, fewshot=fewshot,
                    issues=note or NO_ISSUES)

    try:
        result["p1"] = step(1, "상권 분석 중...", "p1_analyst",
                            context=context, target_date=target_date)

        result["p2"] = step(2, "협업 메뉴 개발 중...", "p2_chef",
                            p1_output=_j(result["p1"]),
                            beer_list=beer_list, kitchen_constraints=kitchen,
                            partner_resources=partner_res,
                            partner_blockers=partner_blockers,
                            constraints=constraints, fewshot=fewshot)

        result["p3"] = step(3, "홍보 기획 중...", "p3_marketer",
                            p1_output=_j(result["p1"]),
                            p2_output=_j(result["p2"]),
                            bottling_sns=bottling_sns, partner_sns=partner_sns,
                            events=events)

        result["final"] = call_p4()

        # (4) 를 다시 불러도 못 고치는 실패다. 원인이 (2) 의 3안에 있다.
        # 3단계에서 (2) 되감기를 붙이기 전까지는 화면에 알리는 데서 멈춘다.
        if result["final"].get("재생성_필요"):
            result["issues"] = [
                "세 안이 모두 실행 불가 — 메뉴 생성부터 다시 해야 한다 "
                f"({result['final'].get('재생성_사유') or '사유 없음'})"
            ]
            result["latency_ms"] = ms_total
            return result

        # 검증 → (4) 재호출. 걸린 항목을 그대로 다음 호출에 넘긴다.
        for _ in range(MAX_REWIND):
            issues = check_final(result["final"], result["p2"], beer_list)
            if not issues:
                break
            result["rewinds"].append(issues)
            if on_step:
                on_step(4, f"검토 결과 보완 중... ({len(issues)}건)")
            result["final"] = call_p4("\n".join(f"- {i}" for i in issues))

        # 재호출 뒤에도 남은 것은 경고로 넘긴다. 무한히 돌리지 않는다.
        result["issues"] = check_final(result["final"], result["p2"], beer_list)

    except Exception as error:
        # 중간 결과를 버리지 않는다. (3) 에서 죽어도 (1)·(2) 는 살린다.
        result["error"] = f"{type(error).__name__}: {error}"

    result["latency_ms"] = ms_total
    return result
```

### 바뀐 점

| | 전 | 후 |
|---|---|---|
| 반환 | `p1~p3, final, latency_ms` | `+ rewinds, issues, error` |
| 예외 | 그대로 전파 — 앞 결과 유실 | 잡아서 `error`에 담고 앞 결과 보존 |
| dict 전달 | `p1_output=p1` | `p1_output=_j(result["p1"])` |
| `재생성_필요` | 안 봄 | 읽고 `issues`에 실어 조기 반환 |
| 검증 | 없음 | `check_final` → 실패 시 (4) 재호출 1회 |

## 7. `prompts/p4_consultant.yaml` 수정안

### 7-1. `inputs`에 추가

```yaml
inputs: [p1_output, p2_output, p3_output, beer_list, rec_reason, constraints, fewshot, issues]
```

## 8. 검증 방법

판이 이미 깔려 있다.

```
고정 테스트셋 8건        명세서 5-5
1층 통과율이 지표         기획서 7-2
버전별 누적 저장          tests/results_{prompt_version}.json
```

**루프를 붙이기 전후로 같은 8건을 돌리면 효과가 그대로 숫자로 나온다.** 그리고 T18(프롬프트 튜닝)이 뒤에 오므로 **"루프로 올린 통과율"과 "프롬프트로 올린 통과율"을 분리해서 말할 수 있다.**

재는 값은 셋이다.

| | |
|---|---|
| 1층 통과율 | 붙이기 전 / 후 |
| 되감기 발생률 | 8건 중 몇 건이 재호출까지 갔는가 |
| 재호출 성공률 | 재호출한 것 중 몇 건이 통과로 바뀌었는가 |

세 번째가 핵심이다. **재호출해도 안 고쳐지는 실패 유형이 있으면 그건 프롬프트로 풀 문제**라는 뜻이고, 곧 T18의 작업 목록이 된다.

## 9. 하지 말 것

- **되감기 횟수를 늘리지 말 것.** `MAX_REWIND = 1`로 시작한다. 2 이상은 지연이 선형으로 늘고, 두 번 불러 안 고쳐지면 세 번째도 대개 안 고쳐진다.
- **A3(수치 근거 대조)를 되감기에 넣지 말 것.** 명세서 2045줄대로 `추천_근거`만 검사해야 하는데 오탐 여지가 있다. 경고로만 남긴다.
- **`gemini.py`의 `retry`를 이 루프와 섞지 말 것.** 그건 전송 계층 재시도(파싱 실패·429)고 같은 프롬프트를 그대로 다시 보낸다. 내용 오류는 못 잡는다. **층위가 다르다.**
- **검사를 두 벌 만들지 말 것.** `chain/checks.py` 하나만 두고 테스트가 그것을 import 한다.

## 10. 포트폴리오에서 이걸 뭐라고 부르나

"재시도를 넣었다"가 아니라 이렇게 말할 수 있다.

> 검증 실패를 유형별로 분류해 **어느 단계로 되감을지를 정하는 라우팅**을 넣었다.
> 대부분은 마지막 단계 재호출로 해결되지만, 세 안이 전부 실행 불가인 경우는
> 메뉴 생성 단계까지 되감아야 한다 — 원인이 거기 있기 때문이다.

그리고 **소상공인 나침반**과 정확히 대비된다.

```
나침반   검증 실패 → 폐기 → 사용자에게 "다시 시도" 버튼
바틀링   검증 실패 → 원인 단계로 되감기 → 자동 교정 → 통과율 기록
```

같은 문제(LLM 출력을 코드가 검증한다)에 **구조가 달라 답이 달라진 사례**다. 한쪽은 단발 호출이라 되돌릴 데가 없었고, 다른 쪽은 체인이라 가능했다. 그 차이를 설명할 수 있으면 도구를 써 봤다는 것과는 다른 층위의 이야기가 된다.

명세서 5-1의 *"LLM-as-judge는 judge 자체를 검증해야 하고, 같은 모델이면 자기 출력에 후한 편향이 있다"* 도 그대로 좋은 재료다. 왜 코드 검증을 골랐는지가 적혀 있다.
