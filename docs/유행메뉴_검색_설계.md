# 유행 메뉴 검색 — 설계

**2026.9.3** ｜ 기획서 3-5 ⑤·⑥ 상세

> **개정** — 8/31 초안에서 「가게가 그 메뉴를 파는지」 확인 방법을 미정으로 두었다. 9/3에 네이버 플레이스 수집을 실제로 시험해 **채택하지 않기로 결정**했다. 근거는 아래 「검토했으나 채택하지 않은 것」 참조.

---

## 무엇을 하는 기능인가

대표님이 **떠오르는 메뉴 이름을 직접 넣으면**, 반경 안에서 그 메뉴를 다루는 가게를 찾아 협업 후보로 올려준다.

```
대표님 입력   "두바이 초콜릿"
        ↓
반경 1km 점포 중 관련 업종만 추림 (제과점·커피-음료 등)
        ↓
블로그 언급 수로 정렬
        ↓
후보 목록 + 지도 링크  →  대표님이 확인하고 선택
```

**그 메뉴를 다루는 곳을 골라 오는 흐름이다.** 협력사가 먼저 정해지고 메뉴를 맞추는 것이 아니라, 메뉴가 먼저이고 그것을 하는 곳을 찾는다.

## 왜 사용자 입력이 먼저인가

방문에서 나온 요구는 **「유행하는 메뉴를 해당 가게가 팔고 있는지」**였다. 두 갈래로 나눌 수 있다.

| | 방식 | 유행 판단 주체 |
|---|---|---|
| **A** | 블로그 언급 급증으로 자동 탐지 | 시스템 |
| **B** | **대표님이 메뉴명을 입력** | **사람** |

**B를 먼저 만든다.** 이유가 셋이다.

**① 유행 판단은 사람이 더 낫다.** 대표님은 매일 손님을 보고 동네 가게를 안다. *"요즘 저게 뜨더라"*는 감각이 블로그 언급 수보다 정확할 수 있다.

**② A는 기준을 정할 근거가 없다.** *"언급이 갑자기 늘었다"*의 기준을 우리가 정해야 하는데, 몇 배 이상을 급증으로 볼지에 근거가 없다. 임계값을 근거 없이 두는 것은 이 프로젝트에서 계속 피해온 방식이다.

**③ B가 A의 뼈대가 된다.** 「메뉴명으로 가게를 찾는」 부분은 두 방식이 같다. A는 그 앞에 「메뉴명을 자동으로 뽑는」 단계가 붙을 뿐이다.

## 그 가게가 그 메뉴를 파는지 어떻게 아는가

`nearby_stores`에는 **상호·업종·좌표**만 있다. 메뉴 정보가 없다.

### 채택 — 블로그 언급 + 지도 링크

**세 단계로 나눈다.** 시스템이 단정하지 않고 사람이 확인하는 구조다.

| 단계 | 방식 | 성격 |
|---|---|---|
| **1** | 네이버 블로그 검색 API로 「가게명 + 메뉴명」 언급 수 | **공식 API.** 후보 정렬용 |
| **2** | 화면에 **네이버 지도 링크** 제공 | 대표님이 눌러서 직접 확인 |
| **3** | 협력사 입력 폼에서 확정 | 협력사가 직접 적음 |

```
검색어:  "블랙스미스 두바이 초콜릿"
        ↓
네이버 블로그 검색 API
        ↓
언급 12건  →  "관련 언급 있음"  (판다고 단정하지 않음)
```

지도 링크는 `nearby_stores`의 상호와 주소로 만든다. 크롤링이 필요 없다.

```
https://map.naver.com/p/search/{상호} {주소}
```

> **언급이 없다고 안 파는 것이 아니다.** 작은 가게는 언급 자체가 적다. **가게를 걸러내는 데 쓰지 않고 정렬에만 쓴다.**

> **2단계가 가장 정확하다.** 우리가 긁는 대신 링크를 걸어주면 대표님이 한 번 눌러 확인하신다. 후보가 5～10곳이므로 부담이 크지 않고, 자동 수집보다 정확도가 높다.

### 검토했으나 채택하지 않은 것

**네이버 플레이스 메뉴 수집 — 9/3 시험 결과 불가**

공식 API(지역 검색·지도)는 메뉴를 제공하지 않아 비공식 경로를 시험했다. `tests/probe_naver_menu.py`로 확인했다.

```
GET map.naver.com/p/api/search/allSearch?query=블랙스미스 자양동

응답 200 / 359 bytes
{
  "result": {
    "metaInfo": { "pageId": "ncaptcha-all-search-no-result" },
    "place": null,
    "ncaptcha": { "confirmRules": "CE_EMPTY_TOKEN", ... }
  }
}
```

**첫 요청부터 캡차가 걸린다.** `CE_EMPTY_TOKEN`은 인증 토큰이 없다는 뜻이고, 그 토큰은 브라우저 세션에서만 발급된다. `requests`로는 얻을 수 없다.

**차단이 아니라 애초에 막혀 있다.** 지연을 늘리거나 헤더를 바꿔도 통과되지 않는다. `placeId`를 얻지 못하므로 그다음 단계(GraphQL 메뉴 조회)는 시도할 수도 없었다.

남는 길은 Selenium/Playwright로 실제 브라우저를 띄우는 것뿐인데, **우리 환경에 맞지 않는다.**

| | 문제 |
|---|---|
| GitHub Actions | 브라우저 구동이 무겁고, 공용 IP라 캡차가 더 자주 뜬다 |
| Streamlit 화면 | 사용자가 버튼을 누르면 그때 브라우저를 띄워야 해 응답이 수십 초 |
| 10월 실증 | 실증 중에 막히면 고칠 시간이 없다 |
| 공공사업 산출물 | 캡차를 우회하는 코드가 결과물에 들어간다 |

> **시험 스크립트는 지우지 않는다.** `tests/probe_naver_menu.py`가 이 판단의 근거다. 나중에 "왜 크롤링을 안 했나"라는 물음에 답할 수 있어야 한다.

**참고한 자료** — `github.com/kkobooc/Crawling_Matzip` (2020～21). 다만 이 저장소는 상호·전화·주소·별점·좌표를 수집할 뿐 **메뉴는 다루지 않는다.** 5개 소스 중 망고플레이트는 2024년에 서비스를 종료했다.

## 화면 흐름

파트너 추천 화면(4-3)에 경로 선택을 둔다.

```
┌─────────────────────────────────────────────┐
│  협업 후보 찾기                              │
│                                              │
│  ○ 추천받기   ○ 직접 지정   ● 메뉴로 찾기    │
│                                              │
│  메뉴명  [ 두바이 초콜릿          ] [검색]   │
│  업종    [ 제과점 ×] [커피-음료 ×]           │
│                                              │
│  ─────────────────────────────────────────  │
│  관련 언급이 확인된 곳  2곳                  │
│                                              │
│  블랙스미스 (커피-음료, 도보 7분)            │
│    관련 언급 12건 · 추천 점수 0.81           │
│    [네이버 지도에서 메뉴 보기 →]             │
│                                              │
│  ○○베이커리 (제과점, 도보 8분)              │
│    관련 언급 3건 · 추천 점수 0.65            │
│    [네이버 지도에서 메뉴 보기 →]             │
│                                              │
│  [ 언급이 확인되지 않은 곳 8곳 더 보기 ▾ ]   │
└─────────────────────────────────────────────┘
```

**0건인 후보는 지우지 않고 접는다.** 작은 가게는 블로그에 이름이 오르지 않아, 지우면 가까운 제과점이 통째로 사라질 수 있다. 접어두면 **필터가 작동하면서도 무엇이 걸러졌는지 보인다.**

펼친 목록에는 안내를 붙인다.

```
※ 블로그에 언급이 없어도 취급할 수 있습니다. 지도에서 확인해 보세요.
```

**추천 점수를 함께 보여준다.** 메뉴가 맞아도 거리가 멀거나 상보성이 낮으면 협업이 어렵다. 두 값을 나란히 놓고 대표님이 판단하시게 한다. **하나로 합치지 않는다.**

> **임계값을 두지 않는다.** *"3건 이상만"* 같은 기준을 정할 근거가 없다. 검색어에 따라 결과가 크게 달라진다 — *"두바이 초콜릿"*은 언급이 많겠지만 *"흑임자 크림"*은 0건일 수 있다. **0건이냐 아니냐로만 나눈다.**

> **직접 지정 경로에서는 추천 점수를 계산하지 않는다** (기획서 3-1). 상대가 이미 정해져 있어 비교 대상이 없고, 반경 밖의 가게일 수도 있다. **메뉴로 찾기는 후보가 여럿이므로 점수를 보여준다.**

## 이후 흐름

가게를 고르면 협력사 입력 폼(4-1)으로 이어진다. **메뉴 검색은 「누구와 협업할지」를 정하는 단계일 뿐이고, 그 뒤 기획안 생성은 기존 구조 그대로다.**

다만 (2) 셰프에게 **대표님이 이 메뉴를 염두에 두고 이 가게를 골랐다**는 맥락을 전달한다.

```
{trend_menu}  →  "두바이 초콜릿 (대표님 지정)"
```

**세 안 모두 그 메뉴를 축으로 삼는다.** 그 메뉴를 다루는 곳을 골라 온 것이므로 다른 메뉴를 제안하면 검색한 의미가 없다. 접근을 달리하는 것은 조리 방식과 구성이지 메뉴 자체가 아니다.

```
A안  두바이 초콜릿 붕어빵        (조리 최소화형)
B안  두바이 초콜릿 화덕 디저트   (화제성)
C안  두바이 초콜릿 스프레드 세트 (원가 절감형)
```

메뉴 검색 경로가 아니면 `데이터 없음`으로 넘긴다.

> **한계** — 블로그 언급이 있다고 지금도 파는 것은 아니다. 작년에 한 번 팔았을 수도 있다. 이는 협력사 입력 폼에서 걸러진다. 협력사가 자기 재료를 적을 때 관련 재료가 없으면 드러난다. **(2) 셰프가 처리할 문제가 아니라 앞 단계 문제다.**

## 자동 탐지(A)는 나중에

B가 동작한 뒤, 여유가 있으면 **메뉴명을 자동으로 뽑는 단계**를 앞에 붙인다.

```
네이버 블로그 검색 — 최근 1개월 / 지역 키워드
        ↓
자주 등장하는 명사 추출
        ↓
직전 기간과 비교해 증가폭이 큰 것
        ↓
후보 메뉴 목록  →  대표님이 고름
```

**끝에 「대표님이 고름」이 있는 것이 중요하다.** 시스템이 유행이라고 단정하지 않고 후보만 제시한다. 그러면 급증의 기준을 엄밀히 정하지 않아도 되고, 노이즈가 섞여도 사람이 걸러낸다.

**보류 사유** — 기간별 언급 수를 API가 직접 주지 않아 날짜별로 세어야 하고, 명사 추출에 형태소 분석기가 필요하다. 작업량이 B의 몇 배다.

## 확인이 필요한 것

| # | 확인 | 상태 |
|---|---|---|
| 1 | 네이버 지도 API가 메뉴를 주는가 | **불가 확인 (9/3)** |
| 2 | 비공식 경로로 메뉴를 얻을 수 있는가 | **불가 확인 (9/3)** — 캡차 |
| 3 | 블로그 검색 API의 일일 호출 제한 | 문서 확인 필요 |
| 4 | **「가게명 + 메뉴명」 검색이 유효한가** | **미확인 (U17)** |

**4번이 이 기능의 성패를 가른다.** 실제로 검색해 보고 결과가 쓸 만한지 확인한 뒤에 만든다. 검색 결과가 엉뚱하면 언급 수 정렬을 빼고 **지도 링크만 제공**하는 형태로 축소한다.
