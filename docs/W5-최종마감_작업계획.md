# A 작업

## 1. (제안) 파트너 추천 두 탭을 에이전트로

**에이전트 형태로 바꾸는 것이 어떤지 제안한다. 만약 시간이 빠듯하다고 판단된다면 1번은 진행하지 않아도 된다.(기획안 생성에 사용되는 멀티 에이전트와는 별개로 만드는 에이전트)**

`app/pages/3_파트너_추천.py`에 탭이 셋 있다. 그중 **「추천받기」와 「메뉴로 찾기」**를
각각 다른 방식의 에이전트로 만드는 것이 어떤지 제안한다. 「직접 지정」은 그대로 둔다.

### 1-1. 추천받기 — 날짜·가게·메뉴를 함께 추천한다

지금은 점수 표만 보여준다. 여기에 **기간과 행사**를 넣어, 언제 누구와 무엇을 할지
한 번에 제안한다.

```
협업 가능한 기간 선택 (캘린더에서 시작일~종료일 선택,숙박 예약 화면처럼)
   ↓
그 기간 안의 행사를 보고 AI 가 협업 시작 날짜를 고른다
   ↓
그 행사의 특성에 맞는 가게를 네이버 검색 API 로 찾는다
   ↓
1~5위로 보여준다 — 날짜 · 가게 · 메뉴 · 추천 이유 3줄
```

**추천 점수는 그대로 쓴다.** `nearby_stores.score`·`score_detail` 이 왜 그 가게인지를
설명한다. AI 가 점수를 새로 매긴다기 보다, 기간·행사에 맞춰 **고르고 설명하는**
몫을 맡는다.

**미리 알아야 할 것 — 행사 데이터가 아직 약하다.**

```
events 34건이 거의 장기 전시다. 드론쇼처럼 하루짜리 행사가 거의 없다
→ 구글 제미나이 또는 서울 열린데이터 광장의 서울시 문화행사 정보를 통해 보충
→ 네이버 검색 api를 통해 자양동과 뚝섬 한강공원 근처 행사 검색해서 행사 정보 업데이트 되게끔 하면 좋을 것 같음
```

### 1-2. 메뉴로 찾기 — 그 메뉴를 파는 곳을 점수 순으로

```
메뉴 이름 입력
   ↓
그 메뉴를 파는 가게로 거른다 (네이버 검색 API)
   ↓
현재 추천 로직을 바탕으로 추천 점수가 높은 순으로 순위를 보여준다
   ↓
하나 고르면 기획안 생성 화면으로 넘어간다
```

**메뉴 필터로 거르는 단계는 10/6 뒤에 붙인다.** 「이 가게가 그 메뉴를 파나」를 알 데이터가 아직
없다. B가 10/6에 블로그 후기에서 메뉴·가격을 뽑아 담는 작업을 한다. 그 이후 진행 가능하다. 

**그 전에도 나머지는 할 수 있다.** 화면·점수 순 정렬·고르면 넘어가기는 지금 데이터로
된다. 일단은 업종 필터로 후보를 내놓다가, 10/6 뒤에 그 자리를 메뉴 필터로 바꾸면
된다.

### 두 탭에서 공통으로 지킬 것

**AI나 검색이 찾아온 상호는 `nearby_stores`와 대조해서 존재해야한다. DB에 있으면 진행, 없으면
추천에서 제외한다.

### 고른 가게·메뉴를 기획안 생성 화면으로 넘기기

고른 가게로 기획안 생성 화면이 열리게 하는 것은 **B가 10/4~10/5에 붙인다.**
`3_파트너_추천.py` 에 한 줄이 들어간다 — 넘어가기 전에 협력사 `id` 를
`st.session_state["partner_pick"]` 에 넣는 것이다.

**그 줄이 A가 고칠 파일에 있다.** 이 탭을 에이전트로 다시 만들 때 그 줄을 살려 두면
된다. 없으면 가게를 고르고 넘어가도 기획안 생성 화면에서 또 골라야 한다.

**고른 메뉴는 받을 자리가 아직 없다. A가 이름을 정해 주면 B가 붙인다.**

기획안 생성 화면은 지금 메뉴를 「지정 없음」으로 고정해서 AI에 넘긴다
(`2_기획안_생성.py:500`). 메뉴로 찾기에서 고른 메뉴가 들어갈 통로가 없다.

```
A   고른 메뉴 이름을 st.session_state 의 어느 자리에 넣을지 정한다
    예:  st.session_state["picked_menu"] = "라볶이"
B   기획안 생성 화면이 그 자리를 읽어 AI 에 넘기게 고친다
```

**자리 이름만 알려주면 된다.** 이름이 어긋나면 오류가 나지 않고 메뉴만 조용히 빠진
기획안이 만들어진다.

## 2. 관리 화면 — 맥주 라인업

`app/pages/9_관리.py`는 지금 36줄짜리 껍데기다. 탭 셋이 모두 「구현 예정」 안내뿐이다.

**예시 화면은 `docs/ref/맥주 라인업 화면_피그마.pdf`이고, 그대로 만들면 된다.**

맥주 라인업은 월 1회 3종을 교체한다. 지금은 바뀔 때마다 DB를 직접 고쳐야 해서,
화면에서 할 수 있게 하는 것이 목적이다.

**받아야 할 값** (`beers` 테이블)

| 칸 | 컬럼 | 필수 | 왜 필요한가 |
|---|---|---|---|
| 맥주 이름 | `name` | ✔ | 제안서·메뉴명에 그대로 나간다 |
| 원/ml | `price_per_ml` | ✔ | 세트 값을 계산한다 (맥주 500ml = 단가 × 500) |
| 스타일 | `style` | | 라거 / IPA / 윗비어 / 켈러비어 … 페어링을 고르는 기준 |
| 도수 | `abv` | | `0`이면 논알콜로 적히고, 논알콜은 페어링에서 뺀다 |
| 맛 특성 | `flavor_notes` | | 여러 개. 「시트러스, 상쾌함」처럼. **페어링의 실제 근거** |
| 교체 가능 여부 | `is_fixed` | | 고정 / 교체 가능 |
| 판매 중인가 | `valid_to` | ✔ | 비어 있으면 판매 중. 판매 종료 날짜를 넣으면 해당일 이후로는 판매중이지 않는걸로 판정해 목록에서 내려간다 |

**지켜야 할 것 **

```
   교체는 지우는 것이 아니라 목록에서 내리는 것
   valid_to 에 날짜를 넣어 목록에서 내리는 방식으로 진행. 지우면 그 맥주로 만든
   지난 기획안을 되짚을 수 없다
```

지금 AI에 들어가는 줄은 이 모양이다. 화면에서 넣은 값이 그대로 이렇게 된다.

```
- 바틀링 라거 / 12원/ml / 라거 / 4.5도 / 가벼움, 탄산감 있음 [고정]
```

* 끝의 고정은 고정적으로 파는 메뉴라는 뜻이다.
