> **개정 이력** — **2차 현장방문(8/31), 3차 현장방문(10/4) 결과**를 반영했다. 현장에서 받은 요구는 협업 형태와 실증 일정에 대한 적합성을 기준으로 검토해 반영 범위와 방식을 정했다.

## 1. 프로젝트 정의

> 공공 상권 데이터로 협업 후보를 찾아주고, 그 후보와의 **콜라보 기획안 초안까지 자동으로 뽑아주는 웹 서비스.**

**산출물은 단품·세트·포장 각각을 주력으로 한 기획안 세 안이다.** 협력사와 협업 실행
희망일이 정해지면 **네 개의 AI 페르소나**가 순차로 동작해 약 25초 뒤에 기획안 3안이 화면에 나온다. 

| 페르소나 | 하는 일 |
|---|---|
| (1) 상권분석가 | 공략 시간대·타겟 손님 선정, 업종별 소비 수준 반영 |
| (2) 셰프 | 협업 방식이 완제품 매입이므로 , 협력사가 이미 파는 메뉴로 **단품·세트·포장** 각각을 주력으로 한 3 안 구성 |
| (3) 마케터 | 안마다 이벤트·홍보 기획 — 문구·해시태그·홍보 일정 제안|
| (4) 컨설턴트 | 세 안 검수, 매입가 제안, 제안서에 들어갈 문장 작성 |

세 안은 우열을 가리지 않는다. 접근이 다른 선택지이며, **그중 사장님이 고른 하나가
협업 제안서가 되어 협력사에 나간다.**

### 1-1. 해결하려는 문제

바틀링 소개자료에 기재된 고민은 다음과 같았다.

> *"협업하고자 하는 파트너사는 많으나, 실행까지 이어지기 위해 필요한 기획안을 내기까지 소요가 많음"*

대형 프랜차이즈는 전담 인력이 콜라보 마케팅을 기획하지만, 소상공인은 매장 운영만으로 자원이 소진되어 기획에 쓸 여력이 없다. 따라서 **기획 리드타임이 병목**이라는 점을 알 수 있다.

### 1-2. 현장방문에서 확인한 사항

세 차례 방문에서 받은 요청과 **반영 결과**를 적는다. 초기 계획과 달라진
항목, 구체적인 구현 과정은 가리킨 절에 경위를 둔다.

**1차 (8/17)**

| 확인 내용 | 반영 결과 |
|---|---|
| 애로사항 — **페어링 메뉴 선정의 어려움** | AI 셰프 출력에 `페어링_맥주` 필드 추가. |
| **상권 데이터를 영업전략에 바로 반영하기 어렵다는 의견** | 상권 수치를 공략 시간대·타겟 손님으로 변환해 제시 (5장 참고) |
| 매장 수용 7인 내외, 테이크아웃 중심 | 세 안 중 하나를 포장으로 고정. 조리 여건은 완제품 매입 한정에 따라 보관여건·보유기구로 축소 (6-1 참고) |

**2차 (8/31)**

| 확인 내용 | 반영 결과 |
|---|---|
| [중요] **협업 형태는 「완제품 매입 후 판매」가 가장 적합** | **협업을 이 형태로 한정**. (6-1·6-2 참고) |
| [중요] **기존 협업 3건 모두 홍보 부족으로 아쉬웠음** | 세 건이 홍보에서 어떻게 아쉬웠는지를 AI 마케터 프롬프트에 규칙으로 추가 (3-4 참고) |
| **메뉴 이미지를 함께 생성해달라는 요청이 있었음** | 미채택 (3-5 참고) |
| **유행하는 메뉴를 파는 가게를 알려주는 기능이 있으면 좋겠다는 요청** | 파트너 추천 화면에 메뉴로 찾기 추가 (3-5 참고) |
| **분배율도 AI가 추천해달라는 요청이 있었음** | 협업형태를 완제품 매입으로 한정하면서 협력사가 판매량과 무관하게 대금을 받게 되어, 분배율이 아니라 **개당 매입가 제안**으로 바꾸어 반영 (3-5 참고) |
| **협업 실행일을 직접 지정하는 방식과 AI에게 추천받는 방식을 함께 두어달라는 요청** | 두 방식 모두 반영. 실행일 직접 지정 가능, 희망 기간을 주면 AI가 인근 행사 정보 등을 근거로 협업 날짜·가게·메뉴를 제안하는 기능 구축 (3-5 참고) |
| **협업 제안서에 역할분담과 상호 이익을 명시해달라는 요청이 있었음** | (4) 컨설턴트 출력에 역할분담·상호_이익·배경 필드 추가 |

**3차 (10/4) — 실증 구간 중간 점검**

3차 방문 시점 까지 완성된 웹서비스 시연을 하고 받은 피드백이다.

| 확인 내용 | 반영 결과 |
|---|---|
| [중요] **협업 매장에 더 특화된 기획안이 나왔으면 좋겠다는 요구를 받음** | 기존 협력사 정보는 바틀링까지의 거리와 업종 분류가 전부여서 AI가 그 가게에 특화된 문장을 만들어내기에 어려움이 있었다. 블로그 후기에서 가게 특성(분위기·손님층·위치·붐비는 때 등)을 수집하여 AI 컨설턴트의 제안 배경 입력으로 투입하도록 하여 해당 요구를 반영함 (3-6 참고) |
| **바틀링 자체 신규 메뉴 추천 기능을 만들어달라는 요구를 받음** | 협업 기획이 아닌 자체 메뉴 개발 영역이어서 이번 범위 밖으로 둠 |
| **가게에서 사용 중인 앱과 디자인을 통일해달라는 요구를 받음** | 기존 앱에 쓰인 캐릭터를 AI PM 화면 전반에 적용하여 반영함 |

→ **9/22에 기획안과 협업 제안서를 도출해 일정을 지켰다.**

**(3) 예선 심사가 서면·영상으로 진행되므로 개발 우선순위를 조정해야 한다.**

→ 화면 구현은 Streamlit으로 유지하고, 기획안 생성부터 제안서 출력까지의 핵심 흐름을 먼저 구현했다. 점주님이 요청한 **웹 디자인 개선**은 실증 구간 이후 반영했다.

## 3. 시스템 개요

> **처리 흐름도** — `img/ai_pm_flow.png` (부록 참조)
> 바틀링 AI PM의 최종 시스템 구조이다.

### 3-1. 파트너 선정 — 세 경로

기획안을 만들기 전에 **누구와 협업할지**를 먼저 정한다.

| 경로 | 흐름 | 적용 상황 |
|---|---|---|
| **추천받기** | 협업 가능 기간 입력 → AI가 날짜·가게·메뉴를 1～5위로 제안 | 협업 상대를 아직 정하지 않았을 때 |
| **직접 지정** | 상호 검색 또는 직접 입력 | 협업할 곳을 이미 정해두었을 때 |
| **메뉴로 찾기** | 메뉴명 입력 → 블로그 후기에서 해당 메뉴를 파는 가게 탐색 | 특정 메뉴로 협업하고 싶을 때 |

세 경로 모두 가게를 선택하면 협력사로 등록되고 기획안 생성 화면으로 이어진다.

### 3-2. 기획안 생성 — 4단계 페르소나 체인

역할이 다른 페르소나 4종을 순차 체인으로 구성했다. 앞 단계의 출력이 다음 단계의 입력이 된다.

| 페르소나 | 역할 | 주요 출력 |
|---|---|---|
| **(1) AI 상권 분석가** | 대상 시점의 공략 시간대와 타겟 고객층 도출 | 공략 시간대 · 타겟 고객층 · 업종별 소비 수준 |
| **(2) AI 셰프** | 협력사 메뉴로 단품·세트·포장 3안 구성 | 메뉴명 · 구성 · 판매가 · 페어링 맥주 |
| **(3) 제휴 마케터** | 3안 각각의 이벤트·홍보 기획 | 이벤트안 · 홍보 문구 · 해시태그 · 홍보 일정 |
| **(4) AI 컨설턴트** | 3안 검수, 매입가 제안, 제안서 문장 작성 | 역할분담 · 상호 이익 · 제안 배경 · 개당 매입가 |

**3안 생성에 약 25초** 소요된다.

### 3-3. AI 대신 코드 연산을 적용한 주요 로직

| 구분 | 주요 수행 기능 | 규칙 기반 코드 적용 이유 |
|---|---|---|
| **데이터 전처리** | DB 내 수치 데이터를 AI 전용 프롬프트 문맥으로 변환 | 수치 집계 및 단순 연산 작업을 AI에 위임할 경우 발생하는 부정확성 방지 |
| **협업 후보 점수 산출** | 반경 내 후보 매장 대상 스코어링 및 순위 책정 | 정량적 수치 계산의 정확성 및 연산 결과의 결정론적 반복성(Determinism) 보장 |
| **생성 결과 검증** | 출력 결과의 규칙 위반 여부 탐지 및 해당 단계 재실행 | 명확한 도메인 규칙(Rule)에 따른 검증 결과의 신뢰성 및 일관성 확보 |

* **AI와 코드 간 역할 분담의 명확화**
  * 수치 연산, 후보 매장 선별, 규칙 검증 로직은 코드가 수행하며, AI는 문맥 해석 및 맞춤형 문장 생성 영역에만 전담 배치하여 시스템 안정성을 극대화하였다.

* **협업 후보 점수 산출 로직**
  * 협업 후보 점수는 물리적 거리와 업종 적합도를 결합하여 산출한다. 업종 적합도는 점주가 12개 업종 범주에 대해 0~10점 척도로 직접 입력한 선호도 데이터를 반영한다. 

* **검증 위반 시 단계별 재시도(Retry) 로직**
  * 출력 검증 단계에서 위반 항목이 탐지되면, 위반 사유(Feedback)를 입력 문맥에 포함하여 해당 연관 단계만 선택적으로 재실행한다. 이를 통해 기존에 정상 생성된 문맥은 유지하면서 문제 요소만 국소적으로 수정하도록 구현하였다.

> **[주요 생성 결과 검증 항목]**
> * 협력사 미판매 메뉴 포함 여부
> * 동일 기획안 내 맥주 제품명 명칭 불일치 여부
> * 매입가가 판매가를 초과하는 가격 역전 여부
> * 세트 구성 가격이 낱개 품목 합산 가격보다 높은 정산 오류 여부
> * 제공된 상권 데이터에 존재하지 않는 수치 허구 기입(환각 현상) 여부

### 3-4. 협업 실행 결과의 아쉬운 점 분석을 통한 긍정형 제약 규칙 설계

초기 협업 데이터가 5～10건 규모에 그쳐 모델을 직접 재학습(Fine-Tuning)하는 방식은 적용할 수 없었다. 따라서 실행 과정에서 도출된 아쉬운 점을 정제하여 프롬프트의 제약 조건으로 주입하는 피드백 루프를 구축하였다. AI의 부정문 처리 한계를 고려해 모든 피드백은 긍정형 지침으로 변환한 뒤 검토를 거쳐 적용하며, 현재 9건의 개선 규칙을 운용하고 있다.

```
기획안 생성 → 채택 여부와 사유 → 실행 → 결과 입력 → 사례 저장
                                                      ↓
                        다음 생성 시 참고 사례 · 제약 조건으로 재투입
```

* **규칙 변환은 사람이 수행한다**
  * 사례에서 규칙을 자동 추출하지 않고, 검토를 거쳐 제약 조건 파일에 직접 기재하는 방식이다. 규칙 문구가 그대로 제안서 품질에 반영되므로 자동화 대상에서 제외하였다.

**아쉬운 점이 제약 규칙으로 전환된 실제 사례 3건**

| 협업 | 아쉬웠던 점 | 추출한 규칙 |
|---|---|---|
| **제과·디저트 협업** (대형 행사 기간) | 행사 당일 현장 홍보(현수막)만 진행하여, 유동인구가 방문 계획을 세우고 실제 매장을 찾기까지의 시간이 부족했음 | 홍보는 실행 1주 전부터 시작한다 |
| **화덕 요리 협업** | 메뉴의 실험성이 강하고 대중성이 떨어져, 흥미 유발에 비해 지속적인 구매 전환율이 낮았음 | 익숙한 맛을 기본으로 하고 변형은 최소화한다 |
| **카페 협업** | 협업 오픈 전 사전 노출 채널이 부재하여 모객 효과를 거두지 못하고 기획이 소진됨 | 사전 콘텐츠로 협업이 있음을 인지시킨다 |

### 3-5. 2차 방문으로 추가된 기능

#### ① 매입가 제안 기능

점주님이 알려주신 기존 협업의 분배 방식은 다음과 같다.

| 협업 | 분배 |
|---|---|
| 제과·디저트 | 바틀링 20% / 협력사 80% |
| 화덕 요리 | 바틀링 100% (재료를 직접 구매, 조리기구만 지원받음) |
| 카페 협업 | 바틀링 100% (매입 후 판매) |

**초기 계획** — 점주님 요청은 **AI가 판매가를 산정하고, 메뉴 하나당 들어가는 재료비와 마진율을 근거로 분배율까지 추천하는 방식**이었다. 판매가에서 원가를 뺀 몫을 양측이 나누는 구조를 전제한 요청이다.

**실제 반영 방식 — 분배율이 아니라 개당 매입가 제안으로 구현했다.** 협업형태를 완제품 매입으로 한정하면서 협력사가 납품 시점에 대금을 받고 거래가 끝나는 구조가 되어, 판매량에 따라 나눌 몫이 생기지 않는다. 따라서 **협력사 정가**를 기준으로 개당 매입가를 제안하는 방식으로 구현하였다. 

| 단계 | 출력 | 산출 근거 |
|---|---|---|
| **(2) 셰프** | 매입한 메뉴의 바틀링 판매가 | 단품·포장 안의 경우 협력사 정가를 그대로 쓰고, 세트 안의 경우 정가에 맥주 500ml 값을 더한 뒤 일정금액 할인한 금액을 제시한다. |
| **(4) 컨설턴트** | 협력사에 줄 개당 매입가 | 협력사 희망가와 정가 대비 비율, 업종별 구간 객단가를 고려하여 제안한다. |

> **매입가는 결국 양측이 협의해 정하는 값이다.** 그래서 1차에서는 **협의 필요** 표시를 넣고, 이후 구글 폼으로 합의된 값이 들어오면 그 값을 2차 제안서에 반영한다.


#### ② 실행일 지정 및 AI 추천 기능

| 구분 | 적용 상황 |
|---|---|
| **날짜 지정** | 실행일이 이미 정해진 경우 |
| **AI 추천** | 실행일이 정해지지 않아 AI에게 추천받고 싶은 경우 |

**AI 추천은 날짜뿐만 아니라 협업할 가게와 메뉴도 함께 제안한다.** 협업 가능 기간을 입력하면, 그 기간의 인근 행사와 함께 **바틀링까지의 거리, 점주님이 업종별로 매긴 협업 적합도**를 고려해 1～5위까지 순위를 제시한다. 각 순위마다 추천하는 가게이름과 협업 시작일·연계 행사·메뉴 안과 선정 이유가 함께 나오도록 구현하였다.

#### ③ 협업 제안서에 역할분담·상호 이익·제안배경을 추가

AI 컨설턴트 출력에 **역할분담 · 상호 이익 · 제안 배경** 세 항목을 추가했다. 협력사가 검토하고 수락 여부를 판단하는 문서이므로, 양측이 각각 무엇을 담당하고 협업을 통해 무엇을 얻는지가 명확히 제시되도록 하였다. 

이 시점의 제안 배경은 **상권 데이터를 근거로 작성**하도록 구현하였다. 다만 이 방식은 3차 방문에서 매장별 특화가 부족하다는 지적을 받아 구성을 다시 설계하게 된다 (3-6 참고).

#### ④ 메뉴 이미지 생성 — **미채택**

제안서의 이해도를 높이기 위해 AI 기반 메뉴 이미지 생성을 구현해 달라는 점주 측 요청이 있었으나, 아래 두 가지 사유로 최종 채택하지 않았다.

**생성 이미지는 실물과 다르다.** 완제품을 그대로 매입해 판매하는 협업이므로, 생성한 이미지가 실제 상품과 다르면 협의 문서와 홍보물에 실제가 아닌 상품이미지가 실리게 된다.

실제 메뉴 사진을 활용하는 방안도 검토했으나, 이를 구할 방법은 지도 서비스나 후기 플랫폼에 올라온 사진을 크롤링하는 것뿐이다. 해당 사진들은 게시자에게 저작권이 있어 무단으로 수집해 사용하면 저작권 침해 소지가 있으므로 제외하였다.

#### ⑤ 메뉴로 가게 찾기 기능

메뉴 이름을 입력하면 해당 메뉴가 후기에서 확인된 인근 매장을 제시한다. 유행하는 메뉴를 파는 가게를 알고 싶다는 점주측 요청을 반영한 기능이다.

```
입력     "붕어빵"
검색     궁합 점수 상위 매장별로 「상호 + 붕어빵 + 구 이름」을 검색어로 하여 블로그 후기를 수집
집계     글 제목에 그 상호가 있는 글만 확인

```

**초기 구현방식에서 오탐이 확인되어 집계 기준을 변경하였다.** 초기에는 글 본문에서 상호를 확인했는데, 이 방식으로는 가게 이름이 지나가듯 언급된 글까지 집계되어 해당 메뉴를 팔지 않는 매장이 상위에 노출되는 문제가 있었다. 이에 상호를 글 제목에서 확인하도록 기준을 바꾸어 해당 문제를 완화했고, 검색어에 구 이름을 추가해 상호가 일반명사일 때 다른 지역의 글이 섞이는 문제도 함께 해결하였다. 

### 3-6. 3차 방문으로 추가된 기능

#### 제안배경 - 블로그 후기 기반의 매장 특성 반영

본 기능은 기획안이 특정 협업 매장에 더욱 특화된 내용으로 작성되어야 한다는 요구사항을 반영해 구현되었다. 기존 협력사 데이터는 '바틀링과의 거리' 및 '업종 분류'에 국한되어 있어, AI가 개별 가게의 고유한 맥락을 반영한 문장을 생성하는 데 한계가 있었다.

**수집 프로세스 효율화** — 기존 메뉴 및 가격 수집용 블로그 후기 수집 파이프라인에 '매장 특성' 항목을 추가하여, 단일 호출로 동시 수집되도록 최적화하였다. 별도 수집 시 발생하는 API 호출 수 2배 증가를 방지하기 위한 조치다.

**수집 데이터 항목** — 분위기, 손님층, 포장 여부, 위치, 혼잡 시간대 등을 추출한다.

**제안서 반영 및 구조 재정의** — 수집된 매장 특성은 제안 배경 도입부에 우선 배치하였다. 상권 데이터 위주로 의존하던 기존 제안 배경(3-5 ③ 참고)을 4단계 구조의 단일 문단으로 재규정하고, 문두에 매장 특성을 배치함으로써 해당 가게에 최적화된 맞춤형 사실로 내용이 시작되도록 구성하였다.

| 순서 | 작성 내용 | 작성 근거 |
|---|---|---|
| ① | 이 가게에 협업을 제안하는 이유 | 블로그 후기에서 확인된 가게 특성 |
| ② | 협업 실행일 제안 | 실행일 전후 인근 행사 정보 |
| ③ | 해당 메뉴가 이번 협업에 적합한 이유 | 메뉴의 성질 - 먹기 간편하다, 맥주와 궁합이 좋다 등 |
| ④ | 단기 시범 판매 제안으로 마무리 | 제안하는 판매 기간 |

**데이터 신뢰성 확보를 위한 검증 로직**

- **교차 검증을 통한 정보의 대표성 확보** — 최소 2건 이상의 블로그 후기에서 공통으로 언급된 진술만 최종 추출하여 사용한다. 단일 후기에만 언급된 진술은 매장의 객관적 특성으로 보기 어렵고 작성자의 개인적 의견일 수 있어 활용 대상에서 제외하였다.

- **대상 매장 정합성 검증 (타 매장 정보 유입 방지)** — 수집된 후기가 실제 대상 매장에 관한 글인지 출처를 검증한다. 메뉴 정보는 다수 게시물의 공통 키워드로 자동 정량화·필터링되나, 단어 단위인 메뉴명과 달리 매장 특성은 서술형 문장 구조로 이루어져 있어 타 매장의 정보가 섞일 경우 이를 자동으로 걸러내기 어렵다. 이에 따라 AI 기반 대상 매장 판정 프로세스를 별도로 구축하였다.

  > **[AI 검증 절차]** 후기에서 매장 특성을 추출할 때, AI가 아래 2가지 근거를 기준으로 해당 글이 대상 매장을 다룬 글인지 판정하며, 비대상 글의 추출 특성은 즉시 폐기한다.
  >
  > 1) **본문 맥락** — 타 가게가 주된 내용이거나, 대상 매장의 상호만 단순 언급된 글이면 비대상으로 판정
  > 2) **위치 일치성** — 글에 기술된 장소·위치가 실제 매장 주소와 맞지 않으면 비대상으로 판정

| **협업 형태** | **완제품 매입 후 판매만** | 공동 조리, 수익 배분, 장기 계약 |
| **분배** | **매입가 제안까지** | 정산 시스템, 계약서 자동화 |
| 학습 | 사례 축적 | 모델 파인튜닝 |

### 6-1. 협업 형태를 하나로 좁힌다

2차 방문에서 점주님이 *"협업사에서 완성한 걸 가지고 와서 파는 게 제일 적합하다"*고 하셨다. **이것만 다룬다.**

| 형태 | 이번 범위 | 사유 |
|---|---|---|
| **완제품 매입 후 판매** | **다룬다** | 점주님이 가장 적합하다고 판단하신 형태 |
| 반제품 + 바틀링 마무리 | 다루지 않음 | 조리 제약이 개입해 판단이 복잡해진다 |
| 공동 조리·팝업 출장 | 다루지 않음 | 협력사 일정·이동·장비가 모두 변수가 된다 |

**시간이 부족해 내린 결정이다.** 9/22 기획안 마감까지 19일이고, 형태가 셋이면 (2) 셰프의 판단이 세 갈래로 갈린다. 각 갈래마다 다른 제약과 다른 원가 구조를 다뤄야 한다.

**하나로 좁히면 여러 곳이 단순해진다.**

| | |
|---|---|
| **원가** | 매입가가 곧 원가다. 식재료 단가를 몰라도 된다 |
| **분배** | 「비율」이 아니라 매입가 협상 하나다 |
| **조리 제약** | 4분 제한·화구 수가 협업 기획에 개입하지 않는다 |
| **추천 엔진** | 협력사 영업시간이 무관해진다 (명세서 3-2) |

> **기존 협업 3건 중 매입 형태는 하나였다** (카페 협업). 제과·디저트 건은 20:80 분배였고 화덕피자는 기계를 빌려 바틀링이 직접 만들었다. **다른 형태를 못 한다는 뜻이 아니라 이번 시스템이 다루지 않는다는 뜻이다.**

## 7. 성과 측정

**실증 협업이 1건이므로 측정 설계를 조정한다.**

당초 계획은 협업 2～3건을 실행해 「생성 → 채택 → 실행 → 성과」의 비율을 보는 것이었다. 그러나 8/31 확정된 일정으로는 AI PM을 써서 실행하는 협업이 **10/9 한 건**이다. 1건으로는 실행률이나 성공률이 의미를 갖지 못한다.

### 7-1. 주 지표 — 기획 리드타임

**문제 정의가 「기획안을 내기까지 소요가 많음」이었으므로 이것이 본래의 지표다.**

| 비교 | 방식 |
|---|---|
| **9/12 협업** | AI PM 없이 사람이 기획 — **기준선** |
| **10/9 협업** | AI PM으로 기획 |

기획 착수부터 협력사에 보낼 제안서가 나오기까지의 시간을 잰다. 1건 대 1건이지만 **같은 팀이 같은 매장을 대상으로 한 것**이라 비교가 성립한다.

> 점주님께 기존 협업의 준비 기간 자료를 받기로 했다. 그것이 있으면 기준선이 더 두터워진다.

### 7-2. 보조 지표 — 기획안 품질

**생성은 여러 건, 실행은 1건**이므로 생성 단계의 지표는 살아 있다.

| 지표 | 측정 |
|---|---|
| 생성 → 채택률 | 여러 안을 만들어 점주님이 고르는 비율 |
| **루브릭 점수** | 5항목 × 1～5점. 프롬프트 버전별 추이 |
| 자동 검증 통과율 | 6종 검사 (개발명세서 5-1) |

### 8-3. 인력 배분

| 시기 | 배분 |
|---|---|
| 8월 | 개발 2명 모두 데이터·API에 투입 |
| **9월** | **A 데이터 적재·추천엔진 / B 체인·웹·화면** |

| **9/12 협업** | **기획·콘텐츠 2명이 직접 기획·실행** |

**분담은 유지하되 진척에 따라 조정한다.** 9/9 기준으로 데이터 적재(T09·T10)가 끝나 `nearby_stores` 841건과 `events` 34건이 들어왔고, 그에 막혀 있던 추천 엔진(T15·T16)의 선행 조건이 풀렸다.

**9/22 마감 셋은 한 사람이 쥔다** (8-4). 화면 셋이 서로 물려 있어 나누면 붙일 때 왕복이 생긴다. 대신 채점은 분리한다 — 자기가 고친 프롬프트를 자기가 채점하면 후해진다.

### 8-4. 지금 시점의 실질적 마감

**9/22가 실질적인 시스템 완성 기한이다.** 명목상 마감은 9/20이나, 그 전에 기획안을 뽑아 협력사에 보내야 10/9 실행이 가능하다.

그때까지 반드시 되어야 하는 것은 셋이다.

```
① 기획안 생성 화면      — 점주님이 직접 눌러 만들 수 있어야 한다
② 협력사 입력 폼        — 실제 자원으로 기획해야 실행 가능한 안이 나온다
③ 협업 제안서 출력      — 역할분담·상호 이익·메뉴 이미지 포함
```

**나머지는 없어도 10/9 협업을 진행할 수 있다.**
