## 1. 프로젝트 정의

> 공공 상권 데이터로 협업 후보를 찾아주고, 그 후보와의 **콜라보 기획안 초안까지 자동으로 뽑아주는 웹 서비스.**
> 그리고 그 서비스를 **실제 협업 실행에 투입해 변화를 측정한 기록.**

### 1-1. 해결하려는 문제

바틀링 소개자료에 기재된 고민은 다음과 같다.

> *"협업하고자 하는 파트너사는 많으나, 실행까지 이어지기 위해 필요한 기획안을 내기까지 소요가 많음"*

대형 프랜차이즈는 전담 인력이 콜라보 마케팅을 기획하지만, 소상공인은 매장 운영만으로 자원이 소진되어 기획에 쓸 여력이 없다. **기획 리드타임이 병목**이다.

## 3. 시스템 개요

> **처리 흐름도** — `img/ai_pm_flow.png` (부록 참조)
> [주의] v4 기준 그림이다. 파트너 선정이 2경로에서 3경로로 늘고 추가 기능이 들어가 **갱신이 필요하다.**

### 3-1. 파트너 선정 — 세 경로

기획안을 만들기 전에 **누구와 협업할지**를 먼저 정한다.

| 경로 | 흐름 | 언제 |
|---|---|---|
| **추천받기** | 반경 점포를 점수화 → 후보 순위 → 선택 | 협업 상대를 아직 못 정했을 때 |
| **직접 지정** | 상호 검색 또는 직접 입력 | **이미 협업할 곳을 정해두셨을 때** |
| **메뉴로 찾기** | 메뉴명 입력 → 취급 가게 탐색 → 선택 | **유행하는 메뉴를 해보고 싶을 때** |

세 경로 모두 파트너가 확정되면 협력사 입력 폼으로 이어진다.

**직접 지정한 경우에는 추천 점수를 계산하지 않는다.** 상대가 이미 정해져 있어 비교 대상이 없고, 반경 1km 밖의 가게일 수도 있어 점수를 낼 근거 자체가 없다. **메뉴로 찾기는 후보가 여럿이므로 점수를 함께 보여준다.**

어느 경로로 시작했는지는 기록해두어 나중에 결과 품질을 비교한다. 추천으로 고른 협업과 직접 지정한 협업 중 어느 쪽이 잘 됐는지를 보면 추천 엔진의 값어치를 판단할 수 있다.

> **직접 지정 경로가 없으면 시스템을 우회하게 된다.** 대표님이 이미 마음에 둔 가게가 추천 목록에 없으면 아예 쓰지 않게 되므로, 세 경로를 같은 화면에 배치한다.

### 3-2. 네 단계

바틀링 사업계획서에 명시된 페르소나 4종을 순차 체인으로 구성했다.

| 페르소나 | 역할 |
|---|---|
| **(1) AI 상권 분석가** | 대상 시점의 공략 시간대와 타겟 고객층 도출 |
| **(2) AI 셰프** | 양측 보유 자원으로 실현 가능한 콜라보 메뉴 3안 |
| **(3) 제휴 마케터** | 3안 각각의 이벤트·홍보 기획 |
| **(4) AI 컨설턴트** | 3안 재평가, 순위 확정, 정합성 교정 |

**1회 생성에 약 20초** 소요된다 (8/29 실측).

### 3-3. LLM을 쓰지 않는 두 컴포넌트

| 컴포넌트 | 역할 | 왜 코드인가 |
|---|---|---|
| **컨텍스트 빌더** | DB 수치를 LLM이 읽을 문장으로 변환 | 숫자 집계를 LLM에 맡기면 값이 부정확해질 수 있다 |
| **추천 엔진** | 협업 후보를 점수화해 순위 제시 | 계산은 코드가 정확하고 재현 가능하다 |

**LLM은 해석과 생성만 담당한다.** 수치 계산과 후보 선정은 코드가 한다.

### 3-4. 사업계획서 Step 6 '재학습'의 실현 방식

파인튜닝이 아니라 **사례 축적**이다. 사례가 5～10건 규모로 예상되어 모델 학습은 불가능하다.

```
기획안 생성 → 채택/폐기 + 사유 → 실행 → 결과 입력 → 사례 저장
                                                        ↓
                              다음 생성 시 (4)의 참고 자료로 재투입
                                채택 사례 → 좋은 예시
                                폐기 사유 → 지켜야 할 제약으로 변환
```

> 폐기 사례는 원문 그대로 넣지 않고 **"준비 기간은 3일 이내로 제한한다"** 같은 긍정형 규칙으로 바꿔 주입한다. LLM은 부정문 처리가 취약하기 때문이다.

**기존 협업 3건이 첫 사례가 된다 (8/31 청취).**

| 협업 | 결과 | 추출한 규칙 |
|---|---|---|
| **떡붕** (드론쇼 기간) | 유동인구는 많았으나 유인 요인 부족. 현수막만으로는 부족 | 홍보는 실행 1주 전부터 시작한다 |
| **YARR 화덕피자** | 반응 괜찮았으나 맛이 대중적이지 않았음 | 익숙한 맛을 기본으로 하고 변형은 하나만 둔다 |
| **카페 위켄드** | 파는지도 모를 정도로 인지 부족. 소요 대비 효과 없어 중단 | 짧게 한 번보다 길게 꾸준히, 또는 사전 콘텐츠로 인지시킨다 |

> **세 건 모두 홍보에서 아쉬웠다.** 대표님 말씀이 *"길게 꾸준히 하든가, 하기 전에 사람들이 많이 인지할 수 있게 콘텐츠를 뽑든가"*였다. 이것을 (3) 마케터의 제약으로 넣는다.

> **세 건 모두 세트로는 팔지 않았다.** 다만 안 되는 것은 아니라고 하셨다. 세트 구성은 (2) 셰프가 선택할 수 있는 형태로 둔다.

**기술 상세는 「개발명세서」 1～4장 참조.**

### 3-5. 2차 방문으로 추가된 기능

우선순위 순으로 적는다. 아래로 갈수록 시간이 부족할 때 먼저 뺀다.

#### ① 매입가 제안 — **높음**

기존 협업의 분배 방식이 제각각이었다.

| 협업 | 분배 |
|---|---|
| 떡붕 | 바틀링 20% / 떡붕 80% |
| 화덕피자 | 바틀링 100% (재료를 직접 구매, 기계만 지원받음) |
| 카페 위켄드 | 바틀링 100% (매입 후 판매) |

**AI가 판매가와 함께 매입가도 제안한다.** 대표님 말씀이 *"AI가 판매가를 주고, 하나 팔 때 재료비가 얼마 들어가니까 마진율을 참고해서 분배율을 추천하는 식으로"*였다. 두 단계로 나뉜다.

```
① 재료비 + 마진율  →  판매가      — (2) 셰프
② 판매가 - 매입가  →  각자의 몫   — (4) 컨설턴트
```

**협업을 완제품 매입으로 한정했으므로**(6-1) 「분배율」이 아니라 **매입가**가 협의 대상이다. 협력사는 판매량과 무관하게 매입가를 받는다.

> **매입가는 AI가 정할 수 없다.** 협력사의 원가를 모르고 결국 양측이 협의할 값이다. 제안값과 근거를 내되 **협의가 필요함을 함께 표시**한다.

**마진 기준값 (8/31 청취)**

| 메뉴 | 마진율 |
|---|---|
| 감자튀김 | 70% |
| 닭다리 | 50～60% |
| **화덕피자 도우** | **원가 500원** — 도우를 많이 쓰는 형태면 마진이 남는다 |

#### ② 날짜 지정 / 희망일 병행 — **높음**

지금은 `target_date` 하나만 받아 그 날짜의 기획만 만든다. **두 방식을 함께 둔다.**

| 방식 | 쓰임 |
|---|---|
| **날짜 지정** | 실행일이 정해진 경우 |
| **희망 기간** | *"9월 중 아무 때나"* — AI가 후보 날짜를 제안 |

행사·요일·날씨를 근거로 **어느 날이 좋은지 AI가 판단**하는 것이 후자다. 지금까지는 사람이 날짜를 정했으나, *"언제 하면 좋은가"*를 판단하는 것이 AI PM의 역할일 수 있다.

#### ③ 협업 제안서에 역할분담과 상호 이익 — **높음**

대표님 요구는 *"역할분담, 얻어가는 게 서로 뭔지 확실히. 직관적으로 이해할 수 있게. 배경 설명"*이었다.

**협력사에 보내는 제안서**이므로 상대가 읽고 판단할 수 있어야 한다. (4) 컨설턴트 출력에 필드를 더한다.

```
역할분담   바틀링이 하는 것 / 협력사가 하는 것
상호 이익  바틀링이 얻는 것 / 협력사가 얻는 것
배경       왜 이 협업을 제안하는가 (상권 근거 요약)
```

#### ④ 메뉴 이미지 생성 — **높음**

대표님 직접 요구다. 기획안에 메뉴 이미지를 함께 넣는다. 협력사에 제안서를 보낼 때 **글만 있는 것보다 이해가 빠르다.**

> **모델 선정이 필요하다.** 지금 Gemini를 쓰고 있어 같은 계열이 자연스러우나, 실제 호출과 품질 확인이 먼저다 (10장 U16).

#### ⑤ 유행 메뉴 검색 — 사용자 입력 방식 — **중간**

대표님이 메뉴명을 입력하면 반경 안에서 그 메뉴를 다루는 가게를 찾는다.

```
"두바이 초콜릿" 입력 → 관련 업종 점포 추림 → 취급 여부 확인 → 후보 목록
```

**취급 여부는 단정하지 않는다.** `nearby_stores`에 메뉴 정보가 없고 네이버 공식 API도 메뉴를 주지 않는다. 블로그 검색으로 **「가게명 + 메뉴명」 언급 수를 세어 참고로 표시**하고, **가게마다 지도 링크를 걸어** 대표님이 직접 확인하시게 한다.

> **메뉴 자동 수집은 시험 후 채택하지 않았다 (9/3).** 네이버 플레이스에 비공식 경로로 접근해 보았으나 첫 요청부터 캡차가 걸린다. 브라우저 세션에서만 발급되는 토큰이 필요해 서버에서는 얻을 수 없다. 근거는 `tests/probe_naver_menu.py`와 「유행메뉴 검색 설계」 참조.

> 블로그 언급이 없다고 안 파는 것이 아니다. 작은 가게는 언급 자체가 적다. **가게를 걸러내는 데 쓰지 않고 정렬에만 쓴다.**

**상세는 「유행메뉴 검색 설계」 참조.**

#### ⑥ 유행 메뉴 자동 탐지 — **낮음**

블로그 최근 글에서 언급이 늘어난 메뉴를 시스템이 뽑아 후보로 제시한다.

**보류 사유** — *"언급이 갑자기 늘었다"*의 기준을 정할 근거가 없다. 그리고 기간별 언급 수를 API가 직접 주지 않아 날짜별로 세어야 하고, 명사 추출에 형태소 분석기가 필요하다. **⑤가 동작한 뒤 여유가 있으면** 그 앞에 붙인다.

#### ⑦ 가게 자체 메뉴 개발 (협업 아님) — **낮음**

협업이 아니라 **바틀링이 직접 만들 메뉴**를 제안하는 기능이다.

**협업 기획에서 조리를 떼어낸 자리다** (6-2). 협업은 완제품 매입만 다루므로, 바틀링이 직접 만드는 경우는 여기로 온다.

| | 협업 기획 | 자체 메뉴 개발 |
|---|---|---|
| 만드는 주체 | 협력사 | **바틀링** |
| 핵심 제약 | 협력사 자원·불가조건 | **주방 여건 (4분, 화구 1개, 냉장 용량)** |
| 쓰이는 장비 | 없음 | **전기화덕피자오븐·어묵중탕기·착즙기·그릴** |
| 원가 | 매입가 | 식재료비 + 마진율 |
| 산출물 | 협업 제안서 | 메뉴안 + 원가 계산 |

**입력은 협업 기획과 대부분 같다.** 상권 컨텍스트, 맥주 라인업, 주방 여건, 마진 기준값. 협력사 자원만 빠진다.

> **(2) 셰프의 변형으로 만들 수 있다.** 프롬프트를 새로 쓰기보다 협력사 관련 입력을 비우고 주방 여건을 강조하는 쪽이 빠르다.

> **붕어빵기계 대여가 여기로 온다.** 대여해서 바틀링이 직접 만든다면 그것은 자체 메뉴다. 1주 전 예약이라는 제약도 이쪽 제약이 된다.

**보류 사유** — 이 프로젝트의 목적이 「협업 기획」이고 실증 대상도 협업이다. 자체 메뉴는 성과 측정 설계(7장)에도 들어가 있지 않다. **협업 기획이 완성된 뒤에 만든다.**

| 구분 | 이번 범위 | 범위 밖 |
|---|---|---|

| 파트너 선정 | 공공데이터 기반 **추천 + 직접 지정 + 메뉴 검색** | 전국 단위 매칭, 제휴 성사 자동화 |

### 6-1. 협업 형태를 하나로 좁힌다

2차 방문에서 대표님이 *"협업사에서 완성한 걸 가지고 와서 파는 게 제일 적합하다"*고 하셨다. **이것만 다룬다.**

| 형태 | 이번 범위 | 사유 |
|---|---|---|
| **완제품 매입 후 판매** | **다룬다** | 대표님이 가장 적합하다고 판단하신 형태 |
| 반제품 + 바틀링 마무리 | 다루지 않음 | 조리 제약이 개입해 판단이 복잡해진다 |
| 공동 조리·팝업 출장 | 다루지 않음 | 협력사 일정·이동·장비가 모두 변수가 된다 |

**시간이 부족해 내린 결정이다.** 9/22 기획안 마감까지 19일이고, 형태가 셋이면 (2) 셰프의 판단이 세 갈래로 갈린다. 각 갈래마다 다른 제약과 다른 원가 구조를 다뤄야 한다.

**하나로 좁히면 여러 곳이 단순해진다.**

| | |
|---|---|
| **원가** | 매입가가 곧 원가다. 식재료 단가를 몰라도 된다 |
| **분배** | 「비율」이 아니라 매입가 협상 하나다 |
| **조리 제약** | 4분 제한·화구 수가 협업 기획에 개입하지 않는다 |
| **추천 엔진** | 협력사 영업시간이 무관해진다 (명세서 3-2) |

> **기존 협업 3건 중 매입 형태는 하나였다** (카페 위켄드). 떡붕은 20:80 분배였고 화덕피자는 기계를 빌려 바틀링이 직접 만들었다. **다른 형태를 못 한다는 뜻이 아니라 이번 시스템이 다루지 않는다는 뜻이다.**

### 6-2. 조리는 「가게 자체 메뉴 개발」로 분리한다

바틀링이 직접 만드는 경우는 **협업이 아니라 단독 메뉴 개발**이다. 별도 기능으로 뺀다 (3-5 ⑦).

```
협업 기획          완제품 매입 후 판매 — 상대가 만들고 바틀링이 판다
가게 자체 메뉴 개발  바틀링이 직접 만든다 — 주방 여건이 여기서 쓰인다
```

**주방 여건(4분 제한, 화구 1개, 전기화덕피자오븐, 냉장 용량)이 자체 메뉴 개발의 핵심 제약이 된다.** 협업 기획에서는 대부분 쓰이지 않는다 — 완제품을 데워 내는 정도이므로.

**붕어빵기계 대여도 자체 메뉴 쪽이다.** 매입 형태면 협력사가 자기 기계로 만들어 오므로 바틀링이 빌릴 이유가 없다. 빌려서 직접 만든다면 그것은 자체 메뉴다.

> **자체 메뉴 개발은 후순위다** (3-5 ⑦). 다만 여기로 옮겨두면 **협업 기획에서 조리 관련 판단을 걷어낼 수 있다.** 버리는 것이 아니라 자리를 옮기는 것이다.

### 6-3. 파트너 선정에 세 경로를 둔다

대표님이 이미 협업할 곳을 정해둔 경우가 실제로는 더 많다. 추천 결과에서만 고르게 하면 시스템을 우회하게 되므로, 직접 지정과 메뉴 검색을 같은 화면에 배치한다.

> [주의] **2차 방문으로 범위가 늘었다.** 기능 네 가지가 「높음」으로 추가되었고 두 가지가 후순위로 남았다. 9/20 마감을 지키기 위해 **3-5의 우선순위를 따른다.** 시간이 부족하면 아래에서부터 뺀다.

## 7. 성과 측정

**실증 협업이 1건이므로 측정 설계를 조정한다.**

당초 계획은 협업 2～3건을 실행해 「생성 → 채택 → 실행 → 성과」의 비율을 보는 것이었다. 그러나 8/31 확정된 일정으로는 AI PM을 써서 실행하는 협업이 **10/9 한 건**이다. 1건으로는 실행률이나 성공률이 의미를 갖지 못한다.

### 7-1. 주 지표 — 기획 리드타임

**문제 정의가 「기획안을 내기까지 소요가 많음」이었으므로 이것이 본래의 지표다.**

| 비교 | 방식 |
|---|---|
| **9/12 블랙스미스** | AI PM 없이 사람이 기획 — **기준선** |
| **10/9 협업** | AI PM으로 기획 |

기획 착수부터 협력사에 보낼 제안서가 나오기까지의 시간을 잰다. 1건 대 1건이지만 **같은 팀이 같은 매장을 대상으로 한 것**이라 비교가 성립한다.

> 대표님께 기존 협업의 준비 기간 자료를 받기로 했다. 그것이 있으면 기준선이 더 두터워진다.

### 7-2. 보조 지표 — 기획안 품질

**생성은 여러 건, 실행은 1건**이므로 생성 단계의 지표는 살아 있다.

| 지표 | 측정 |
|---|---|
| 생성 → 채택률 | 여러 안을 만들어 대표님이 고르는 비율 |
| **루브릭 점수** | 5항목 × 1～5점. 프롬프트 버전별 추이 |
| 자동 검증 통과율 | 6종 검사 (개발명세서 5-1) |

### 7-3. 퍼널 A — 협업 이벤트 성과

```
인스타 도달 → 저장·공유 → 도장 적립 → 재방문 적립
  (노출)       (관심)      (획득)      (유지)
```

**쿠폰 앱 관리자 사이트 접근을 허용받았다 (8/31).** 전화번호로 사람이 구분되므로 재방문 추적이 가능하다.

**협업 전용 쿠폰을 만들 수 있다.** 기존 쿠폰과 섞이지 않아 그 협업으로 온 손님을 정확히 셀 수 있다.

> **마지막 단계가 핵심이다** — 협업으로 온 손님이 다시 오는가. 대표님 과제가 "한강 상권 비수기 극복"이므로 일회성 화제로 끝나는지 단골이 되는지가 사업 목적과 직결된다.

> POS 원본 데이터는 요청하지 않는다. 실행일과 직전 같은 요일의 총매출 두 값이면 충분하다.

### 7-4. 퍼널 B — AI PM 시스템

```
추천 노출 → 파트너 선택 → 기획안 생성 → 채택 → 실행 → 성과 기록
```

**실행 단계는 1건이므로 그 앞까지를 본다.** 어느 단계에서 이탈하는지가 곧 개선 방향이 된다. 생성은 많은데 채택이 없으면 기획안 품질 문제다.

**최종보고서 서술 예시**

> 기획안 N건 생성 → M건 채택 → 1건 실행.
> 기획 리드타임은 AI PM 없이 X시간, AI PM으로 Y분.
> 실행 1건에서 협업 전용 쿠폰 발급 A건 / 사용 B건 / 재방문 C명 확인.

[주의] 표본이 1건이므로 **통계적 유의성은 주장하지 않는다.** 쿠폰 앱 이용률이 100%가 아니므로 절대 수치가 아닌 상대 비교로만 해석한다.
