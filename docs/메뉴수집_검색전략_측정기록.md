# 메뉴 자동 수집 — 검색 전략 측정 기록

> 2026-10-06 측정. `collectors/menu_reviews.py` (U17, 담당 B)

블로그 후기에서 협력사 메뉴·가격을 모으는 기능이다. **네이버가 준 글 목록에서
어떤 글을 제미나이에게 넘길지**를 네 가지로 바꿔 보고 결과를 재 봤다.

이 기능을 다시 손볼 때, 그리고 「메뉴로 가게 찾기」를 만들 때 같은 데서 막히지
않도록 수치를 남겨 둔다.

---

## 1. 문제

등록된 협력사 일곱 곳에 자동 수집을 돌렸더니 **네 곳이 0개**였다. 그런데
네이버에서 직접 손으로 찾아보면 메뉴와 가격이 적혀진 블로그 후기를 찾을 수 있었다.

글 하나씩 들여다보니 두 문제가 겹쳐 있었다.

**① 받은 글의 7할이 버려진다.**
블로그 검색에 30건을 달라고 하면 30건이 오는데, 그중 20건쯤이 네이버 블로그가
아니었다. 본문을 읽는 방법이 네이버 블로그용(`PostView.naver`)뿐이라 통째로
버려진다. 실제로 누룽지통닭뚝섬유원지점은 30건 중 **9건**만 남았다.

버려진 글이 뭔지 보니 전부 티스토리 목록 글이었다.

| 글 | 본문 길이 |
|---|---|
| 「서울중심 수도권 맛집리스트」 | 271,214자 |
| 「2016 전국 음식점 정보」 | 442,761자 |

**② 걸러지고 나서 남은 글도 대부분 그 가게 관련 글이 아니었다.**
누룽지통닭의 9건은 「250901 서울.경기 맛집 신장개업」·「07월 러닝일지」·
「드론쇼 꿀팁」처럼 가게 이름만 의미없이 포함된 글이었다. 진짜 그 가게 후기는 2건뿐이라,
「서로 다른 글 2건 이상에 나온 메뉴만 쓴다」는 기준에 걸려 메뉴 6개가 전부
빠졌다.

여기서 **글 제목에 가게 이름이 들어간 경우 메뉴 정보가 포함되어 있을 확률이 높다** 는
경향을 확인했다. 
누룽지통닭으로 검색했을 때 나온 블로그 글 9건 중 제목에 가게 이름이 포함된 글이 2건이었는데, **메뉴 정보가 나온 글이 딱 그 2건**이었다. 나머지 7건은 전부 0개였다.

## 2. 네 가지 방식

네 방식 모두 **네이버 검색 호출은 1회로 같다.** 다른 것은 어떤 글을
제미나이에게 넘길지뿐이다.

검색어는 네 방식 모두 같다 — 지역검색으로 찾은 **정식 상호 + 구**, 관련도순
(`sort=sim`).

### 기존

```
호출로 30건 달라고 한다 → 네이버 블로그만 남긴다 → 관련도순 그대로 앞에서부터 읽는다
```

### ㄱ — 제목에 가게 이름이 든 글만

```
100건 달라고 한다 → 네이버 블로그만 남긴다 → 제목에 가게 이름이 포함된 글만 읽는다
```

`display` 는 100까지 받는다 (`start` 는 1000까지). 네이버 검색 api 호출 수는 1회로
같다. 제목과 가게 이름은 띄어쓰기를 제거하고 맞춘다 — 같은 가게라도 사람마다 띄어쓰기를 다르게 작성해서 같은 가게에 관한 글임을 확인하기 위해 아예 띄어쓰기를 제거하고 맞추는 방식을 선택했다.

**받는 건수를 늘리면 관련도 순서 자체가 달라졌다.** 왜 그런지는 네이버 쪽
사정이라 확인하지 못했다.

| 요청 건수 | 요청으로 불러와진 글중 네이버 블로그 글의 개수 | 제목에 가게 이름이 포함된 글의 개수 |
|---|---|---|
| 30건 | 9건 | 2건 |
| 100건 | 75건 | 39건 |

### ㄴ — 제목에 지점 이름까지 든 글만

ㄱ과 나머지는 동일한데, 「누룽지통닭」이 아니라 「누룽지통닭 뚝섬유원지점」처럼 지점까지 제목에
있어야 읽는 방법이다. 같은 이름 다른 가게(「구의역 맛집 누룽지통닭」·「계림원
누룽지통닭」)를 막으려는 의도였다.

### ㄷ — 제목에 가게이름이 든 글을 앞으로 당기고 나머지로 채우기

```
100건 달라고 한다 → 제목에 가게이름이 든 글 먼저 채움 → 30자리중 자리가 남으면 나머지를 관련도순으로 채운다
```

ㄱ 처럼 제목에 가게 이름이 없을 경우 거르는 방법이 아니라 그저 30건 중 채우는 순서만 바꾼다. 아예 읽지 못하게 걸러지는 경우가 없으므로 기존보다 나쁠 수 없다.

협력사 일곱 곳을 전부 돌려 봤다.

**표에 나오는 숫자가 뭘 뜻하는지부터 적는다.**

| 칸 | 뜻 |
|---|---|
| 고른 글 | 해당 방식이 읽어 보기로 고른 글 수 (최대 30건) |
| 읽은 글 | 그중 본문이 실제로 읽힌 글 수. **제미나이를 부른 횟수와 같다** |
| 메뉴 | 실제로 등록되는 메뉴 개수. 「서로 다른 글 2건 이상에 나온 것」을 통과한 것들 |

### 가격이 붙는 건 가게마다 다르다

| 가게 | 메뉴 | 가격 |
|---|---|---|
| 봉평메밀막국수자양역점 (ㄷ) | 12개 | 11개 |
| 누룽지통닭뚝섬유원지점 (ㄱ) | 13개 | 9개 |
| 라쿤피자건대 (ㄱ) | 38개 | 6개 |
| 프레즐 (ㄷ) | 14개 | 1개 |

봉평메밀은 12개 중 11개에 가격이 붙는데 프레즐은 14개 중 1개다. 방식을 바꿔도
안 늘어난다 — 블로그에 가격이 안 적혀 있는 것이다. 빈 가격을 화면에서 채우게
해 둔 게 이래서 필요하다 (작업 원칙 ③).

**라쿤피자건대는 ㄱ으로 바꾸면 가격이 오히려 줄어든다** (9개 → 6개). 메뉴는 24개
에서 38개로 늘었는데 가격은 거꾸로다. 일곱 곳 중 이 가게만 그렇다. 기존 9개
안에 틀린 2,500원이 끼어 있던 건 확인했지만(4장 ⑤), 줄어든 세 개가 다 그런
값이었는지는 확인하지 못했다.

### 같은 방식이라도 돌릴 때마다 조금씩 다르다

라쿤피자건대를 기존 방식으로 두 번 돌렸더니 메뉴는 24개로 같았는데 가격이 6개와
9개로 달랐다. `temperature=0` 을 줘도 이 정도는 왔다 갔다 한다. **한 번만 재서
1~3개 차이가 났다면 방식 때문이라고 보기 어렵다.**

## 3-2. 다시 잰 것 (10/7) — 오류를 고치고 ㄹ 을 넣어서

3장은 **7장의 오류를 고치기 전에** 잰 것이다. 고른 글이 3.7%쯤 조용히 사라지던
상태였고, ㄹ 도 아직 없었다. 그래서 같은 가게 일곱 곳을 처음부터 다시 쟀다.

3장을 지우지 않고 남겨 둔다. **같은 방식을 두 번 재면 얼마나 흔들리는지**가
그 자체로 쓸모 있는 값이다 (3장 끝 참고).

### ㄹ — ㄱ 에 보험을 하나 붙인 것

```
100건 달라고 한다 → 제목에 가게 이름이 든 글을 읽는다
                  → 그런 글이 한 건도 없으면 기존처럼 관련도순으로 읽는다
```

ㄱ 은 제목에 걸리는 글이 없는 가게에서 아무것도 읽지 않는다. 지역검색이 정식
상호를 못 찾아 생기는 이름 불일치를 막으려고, 0건일 때만 기존 방식으로
돌아가게 한 것이다. 제목에 걸리는 글이 있는 가게에서는 ㄱ 과 완전히 같다.

### 두 측정이 얼마나 다른가

오류 수정으로 **고른 글을 하나도 흘리지 않게 됐다.** 누룽지통닭 ㄱ 은 읽은 글이
25 → 30건으로 늘었다. 메뉴 수는 가게마다 ±2개 안에서 움직였다.

| 가게 | 기존 (3장 → 3-2장) | ㄱ (3장 → 3-2장) |
|---|---|---|
| 누룽지통닭뚝섬유원지점 | 0 → 1개 | 13 → 15개 |
| 봉평메밀막국수자양역점 | 0 → 0개 | 11 → 11개 |
| 프레즐 | 7 → 8개 | 10 → 11개 |
| 커피더쏠 | 0 → 0개 | 0 → 0개 |
| 라쿤피자건대 | 24 → 23개 | 38 → 36개 |
| 팔자좀피자 | 1 → 2개 | 1 → 2개 |
| 저스트런잇 | 3 → 3개 | 3 → 3개 |
| 합계 | 35 → 37개 | 76 → 78개 |

**방식 사이의 우열은 두 번 다 같았다.** 절대 개수는 ±2개 흔들리지만 순서는
바뀌지 않는다. 그래서 아래 결론은 ±2개 차이에 기대지 않는 것만 근거로 삼았다.

### 두 번째 측정 조건

3장과 같고, 달라진 것은 둘이다.

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-07 |
| 키 | **무료 키** (다른 구글 계정에서 새로 받은 것) |
| 오류 수정 | `extract_menus` 반영됨 (7장) |
| 전체 | 제미나이 268회 / 1,146초 (호출당 4.3초) |
| 실패 | 0건. 429 도 0건. 분당 한도 대기 13회 |

키를 바꿔도 메뉴 수가 달라지지 않았다. **같은 모델이면 키는 결과와 무관하다**는
것이 한 번 더 확인됐다.

## 4. 알게 된 것

**① ㄱ 은 메뉴를 더 뽑으면서 제미나이 호출은 덜 쓴다.** 모든 가게에서 메뉴가
기존보다 같거나 많이 나왔다.

```
메뉴    35개  →  76개    (2배)
호출   134회  →  93회    (30% 적게)
```

제목으로 고르면 **읽는 글은 줄어드는데 뽑히는 메뉴는 늘어난다.** 잡다한 글을
읽는 데 쓰던 호출이 그 가게 후기를 읽는 쪽으로 옮겨 가기 때문이다.

**② 제목에 안 걸리는 가게는 애초에 모을 게 없는 가게였다.**

ㄱ을 쓰면 제목에 걸리는 글이 0건인 가게(커피더쏠)는 아무것도 읽지 않는다.
처음에는 그것을 손실로 봤지만, 그 가게는 **기존 방식으로도 14건을 읽어 0개**
였다. 지역검색도 블로그 검색도 그 가게를 모른다.

다만 지역검색이 정식 상호를 못 찾아 생기는 이름 불일치를 막으려면, **제목에 든
글이 0건일 때만 기존처럼 나머지를 읽는 보험**을 둘 만하다. 후기 있는 가게에는
영향이 없고, 후기 없는 가게에서만 14회쯤 더 쓴다.

**③ ㄷ는 쓴 만큼 못 건진다.**

ㄱ보다 5개 더 얻으려고 호출을 2배(93 → 187회) 쓴다. 그 5개는 프레즐 4개와
봉평메밀 1개인데, 뒤쪽 잡다한 글을 전부 읽어서 겨우 「2건」을 넘긴 것들이다.

**④ ㄴ는 오히려 손해다.**

69개로 ㄱ보다 적다. 글을 좁히면 겹치는 메뉴가 덜 생겨서다 — 누룽지통닭 13 →
8개, 팔자좀피자는 읽을 글이 1건으로 줄어 1 → 0개가 됐다. **지점 이름은 쓰지
않는게 낫다.**

같은 이름 다른 가게가 섞일 위험은 실제로 있지만, 프롬프트에 「이 가게에서 파는
메뉴만」이라고 적어 두었고 같은 브랜드면 메뉴도 거의 같다. 섞인 메뉴 때문에
틀린 값이 들어갔는지는 확인하지 못했다.

**⑤ 목록 글이 빠지면서 틀린 가격도 같이 빠졌다.**

라쿤피자건대에서 전부터 의심하던 값이 있었다.

```
기존   바질마스카포네 피자(R)  2,500원   ← 틀린 값
ㄱ     바질마스카포네 피자     가격 없음  ← 그 값이 안 들어왔다
```

목록이 보이는 글(이하 목록 글이라 칭함)이 가격을 엉뚱하게 옮겨 적었던 것으로 보인다. 다만 「목록 글이 원인」은
정황일 뿐이고, 그 2,500원이 어느 글에서 왔는지 끝까지 짚지는 않았다.

### 티스토리도 읽게 하면 어떤가

**읽을 수는 있다.** 네이버와 달리 iframe 이 없어 본문이 바로 나온다 (HTTP 200).
그런데 **일곱 협력사로 실제 검색해봤을때, 7곳 전부 검색결과에서 네이버 블로그를 제외하면 글 제목에 가게 이름이 포함된 경우가 없었다. 검색에
걸리는 건 전부 수십만 자짜리 목록 글이고, 본문을 6,000자까지만 읽으니 그 가게
얘기가 나오는 부분은 아예 안 읽힌다. 추가해도 얻는 게 없다.

```
① 네이버에 100건 달라고 한다              네이버 검색 호출은 1회로 지금과 같다
② 네이버 블로그 글만 남긴다

④ 그런 글이 한 건도 없으면 수집하지 않고
   화면에 「후기를 찾지 못했습니다」로 알린다
```

### 근거

**① 메뉴는 더 나오고, 제미나이 호출 수는 줄어든다.** 일곱 곳 가운데 메뉴가
기존보다 줄어든 가게는 한 곳도 없었다. 두 번 재서 두 번 다 그랬다.

| | 기존 | ㄱ |
|---|---|---|
| 등록된 메뉴 | 37개 | 78개 (2.1배) |
| 가격이 채워진 메뉴 | 7개 | 25개 (3.6배) |
| 제미나이 호출 | 139회 | 98회 (30% 줄었다) |

읽는 글은 줄어드는데 뽑히는 메뉴는 늘어난다. 잡다한 글을 읽는 데 쓰던 호출이
그 가게 후기를 읽는 쪽으로 옮겨 가기 때문이다.

**② 메뉴 개수보다 메뉴 이름의 질이 더 크게 달라진다.** 프레즐이 그 예다.

```
기존   나쵸, 빵, 샐러드, 치즈, 치킨, 프레즐, 핫윙
ㄱ     새우 프레즐, 스페셜 프레즐 갈릭, 스페셜 프레즐 크림치즈, 오리지널 프레즐,
       이탈리아노 프레즐 고구마 / 콘 / 페퍼로니 / 핫, 플레인 프레즐, 핫치킨 프레즐
```

기존이 뽑은 8개는 목록 글에서 스쳐 간 낱말이라 협력사 메뉴로 쓸 수 없다.
개수로는 8개 대 11개지만, **쓸 수 있는 메뉴로 세면 0개 대 11개다.**

**③ ㄷ 가 더 얻는 메뉴 7개는 쓸 수 있는 메뉴가 아니다.** 7개 가운데 6개가
프레즐에서 나왔고, 그 6개가 「식빵」·「샌드위치」·「마카롱」처럼 제목에 안 걸린
뒤쪽 글에서 나온 낱말이다. 기존 방식이 「빵·치즈·샐러드」를 뽑던 것과 같은
성격이다. 그 6개를 얻으려고 **제미나이 호출이 98회에서 197회로 2배가 된다.**

**④ ㄹ 의 보험은 받을 것이 없었다.** ㄹ 로 나온 메뉴와 가격은 ㄱ 과 완전히 같고,
제미나이 호출만 14회 더 든다. 보험이 작동하는 가게는 커피더쏠 하나인데, 그
가게는 기존 방식으로 14건을 읽어도 메뉴가 0개였다.

**⑤ ㄴ 는 아예 못 건지는 가게를 만든다.** 팔자좀피자는 읽을 글이 1건으로 줄어
메뉴가 2개에서 0개가 되고, 누룽지통닭은 15개에서 9개가 된다. 메뉴 1개당 호출이
1.1회로 가장 적지만, 그 값은 메뉴가 나온 가게만 셈한 것이다. 못 건지는 가게가
생기는 것은 그 값에 나타나지 않는다. **지점 이름은 쓰지 않는다.**

### 남는 위험

**지역검색이 정식 상호를 못 찾는 가게는 수집을 건너뛴다.** 커피더쏠이 이름이
안 맞는 경우인지, 후기가 정말 없는 경우인지 가려내지 못했다. 둘 다 결과가
0개라서 이번 표본으로는 구분되지 않는다.

이름 불일치 자체는 ㉛(직접 입력 등록에 주소 칸, `남은_작업_0917.md`)이 처리되면
줄어든다. 주소가 비어 있으면 검색어에 구가 붙지 않아 엉뚱한 글이 섞이기
때문이다. 그래도 건너뛰는 가게가 생기면 화면에서 수동 등록으로 넘어갈 수 있다.

**같은 이름 다른 가게가 섞일 여지는 남는다.** ㄴ 를 버렸으므로 「구의역 맛집
누룽지통닭」·「계림원 누룽지통닭」 같은 글이 들어온다. 프롬프트에 「이 가게에서
파는 메뉴만」이라고 적어 두었고 같은 브랜드면 메뉴도 거의 같지만, 그 때문에
틀린 값이 들어갔는지는 확인하지 못했다.

## 5. 제미나이 무료 키 한도

### 한도

| 항목 | 값 |
|---|---|
| 분당 호출 (RPM) | 15 |
| 분당 토큰 (TPM) | 250,000 |
| 하루 호출 (RPD) | 500 ~ 1,000 |

하루 한도는 **미국 태평양 자정**에 리셋된다 (한국시간 16:00, 서머타임 기준).
UTC 자정이 아니다.

### 발목을 잡는 건 분당 한도다

수집은 가게 하나에 제미나이를 최대 30회 부른다. 분당 15회가 한도니까
**호출 사이에 최소 4초**가 필요하고, 30회면 120초다.

실제로 재 보니 **호출당 3.6 ~ 4.2초**였다 (269회에 1,072초). 지금 쓰는 20초·40초
대기 재시도가 투박해 보여도 평균은 한도에 거의 맞아떨어진다. **미리 간격을
두고 천천히 불러도 120초로 똑같다 — 더 줄일 방법이 없다.**

토큰은 안 걸린다. 호출당 4,000 토큰이라 분당 15회면 60,000이고, 한도 25만에
한참 못 미친다. **발목을 잡는 건 분당 호출 수 하나뿐이다.**

### 글 여러 개를 한 번에 넘기면

호출 수가 줄어서 한도에 안 걸리게 된다 (글 6건씩 묶으면 30회 → 5회). 지시문을
30번 반복할 필요도 없으니 토큰도 조금 줄어든다. 다만 **아직 재 보지 않았다.**
두 가지가 걱정돼서 미뤘다.

- 본문을 길게 넘기면 결과가 나빠진 적이 있다. `BODY_LIMIT` 을 6,000자에서
  20,000자로 올렸더니 뽑히는 메뉴가 **오히려 줄어서** 되돌렸다. 글 6건을 묶으면
  한 번에 36,000자다.
- 「서로 다른 글 2건 이상」이라는 기준이 글을 하나씩 따로 뽑는 데 기대고 있다.
  한 번에 여섯 글을 다 보여 주면 모델이 알아서 합쳐 버려서, 몇 글에서 겹쳤는지
  셀 수 없게 된다. 메뉴마다 몇 번째 글인지 적어 달라고 할 수는 있지만, 긴 글
  여섯 개를 짚어 가며 번호를 매기는 건 flash-lite 가 가장 흔들리는 일이다.

재 보려면 2~3건씩 묶는 게 적당해 보인다 (30회 → 10~15회면 한도 안에 들어온다).

## 6. 유료 키를 쓰는 이유 — 두 곳이 이유가 다르다

### 기획안 생성 — 처음부터 유료로 정해 둔 것

**협의 내용이 제미나이 학습에 쓰이는 걸 막으려는 것이다.** 무료 키로 보낸
입력은 모델 개선에 쓰일 수 있고, 기획안에는 협력사가 알려준 매입가처럼 밖으로
나가면 안 되는 값이 들어간다. 유료 키를 쓰자고 제안해 **대표님이 동의한
것이다.**

유료 키로 바꾸면 분당·하루 한도에 걸리지 않아 생성이 빠르고 중간에 끊기지도
않는다. 그 이점도 분명하다. 다만 키를 가르는 기준은 위의 한 가지다. 정확도는
키와 상관없다 — 같은 모델이면 출력이 달라지지 않는다.

### 수집 — 속도 때문에 나중에 바꾼 것

이쪽은 사정이 다르다. 수집은 가게 하나에 제미나이를 최대 30회 부르는데, 무료
키는 분당 15회가 한도라 중간에 대기가 걸린다. 처음에는 **한 가게에 10분이 넘게
걸렸고**, 화면에는 진행 표시만 돌고 있어서 멈춘 것처럼 보였다.

나중에 하루 한도가 리셋된 다음 다시 재 보니 **무료 116초 / 유료 51초**였다.
10분이나 걸린 건 하루 한도까지 같이 걸렸던 탓으로 보인다. 같은 조건이면 무료
키로도 2분 안에 끝나고, 메뉴는 23개가 나왔다.

**수집은 무료 키로 되돌려도 원칙에 어긋나지 않는다.** 블로그에 공개된 메뉴와
가격만 넘기기 때문에, 학습에 쓰여도 곤란할 것이 없다. 되돌리지 않은 이유는
속도 하나뿐이다.

### 지금 상태

`collectors/menu_reviews.py` 와 `chain/runner.py` 가 `paid=True` 로 되어 있다.
그 둘을 거치는 건 전부 유료 키를 쓴다.

수집을 무료 키로 되돌리고 **한도에 여러 번 걸릴 때만 유료로 넘어가게** 하는
쪽이 낫겠다고 봤지만, 아직 안 넣었다.

### 단가

실제 토큰 수로 계산한 값이다 (`gemini-3.5-flash-lite`, 입력 $0.30/M ·
출력 $2.50/M, 환율 1,350원).

| 항목 | 금액 |
|---|---|
| 수집 — 호출 1회 | 약 2.3원 |
| 수집 — 가게 1곳 (기존, 평균 19회) | 약 43원 |
| 수집 — 가게 1곳 (ㄱ, 평균 13회) | 약 30원 |
| 수집 — 가게 1곳 (ㄷ, 평균 22회) | 약 51원 |
| 기획안 1건 | 약 60원 |

**ㄱ으로 바꾸면 결과가 2배가 되면서 가게당 단가는 43원 → 30원으로 내려간다.**

## 7. 같이 드러난 오류

```
AttributeError: 'list' object has no attribute 'get'
```

약 300회 중 **11회(3.7%)** 났다. 메뉴를 「이름·가격·설명」이 든 묶음으로 달라고
시켰는데(`{"메뉴": [{...}]}`), 제미나이가 묶음 없이 이름만 목록으로
(`["누룽지통닭", "불닭"]`) 보낼 때 깨진다. 가격도 설명도 안 적힌 글에서 잘
나는 것 같다.

`collect()` 가 `except Exception: continue` 로 받고 있어서 **그 글이 조용히
사라진다.** 화면에는 아무 표시도 안 난다. 라쿤피자건대에서는 「[자양역맛집]
라쿤피자 건대본점」·「건대 피자 맛집ㅣ라쿤피자 건대본점」 두 건이 그렇게
날아갔다. 둘 다 제목에 가게 이름이 든 진짜 후기다.

> **한 글을 반복해서 돌려서는 안 잡힌다.** 터진 글 하나를 4번 다시 돌렸더니
> 4번 다 멀쩡했고, 그것을 보고 「재현되지 않는다」고 판단했다가 틀렸다. 다른
> 실행에서 **다른 글**에서 또 났다. 글마다 드물게 나는 오류는 글을 바꿔 가며
> 재야 한다.

---

## 8. 확인하지 못한 것

- 받는 건수에 따라 관련도 순서가 달라지는 이유
- 같은 이름 다른 가게의 메뉴가 섞여 실제로 틀린 값을 만들었는지
- 라쿤피자건대의 2,500원이 정확히 어느 글에서 왔는지
- 글을 2~3건씩 묶어 넘기면 결과가 어떻게 되는지
- `start` 로 쪽을 넘겨 100건 이상 모으면 더 나아지는지
